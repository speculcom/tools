它是什么：「Semantic Kernel 与 AutoGen 合并后的微软官方 agent 底座」。

全名 Microsoft Agent Framework（本站下称 MAF）。

官方公告页把这层血缘关系写得最清楚：

Microsoft Agent Framework doesn't replace Semantic Kernel and AutoGen — it builds on them.

官方 overview 页同样直白（原文）：

"It brings together and extends ideas from Semantic Kernel and AutoGen projects... Built by the same teams, it is the unified foundation for building AI agents going forward."

理解它只需要记住一件事。

它不是「又一个新框架」，而是微软把两条产品线收编成了一条。

What it is: "the Microsoft-official agent foundation that merged Semantic Kernel and AutoGen". Full name Microsoft Agent Framework (MAF below). The official announcement page puts the lineage most plainly — "Microsoft Agent Framework doesn't replace Semantic Kernel and AutoGen — it builds on them" — and the official overview is just as direct: "It brings together and extends ideas from Semantic Kernel and AutoGen projects... Built by the same teams, it is the unified foundation for building AI agents going forward." One thing is enough to remember: it is not "yet another new framework" — Microsoft folded two product lines into one.

It is a graph-workflow orchestration framework — a fit for five cases.

  • Organizing multiple agents into a deterministic graph workflow with branching, human-in-the-loop, and checkpoint-based recovery
  • Needing a consistent API across .NET and Python
  • Teams already inside the Azure / Microsoft Foundry ecosystem
  • Requiring observability (built-in OpenTelemetry), durability, governance, and provider flexibility
  • Needing MCP and A2A cross-runtime interop, or migrating from Semantic Kernel / AutoGen

Not a fit for running just a single agent without a graph (OpenAI Agents SDK is lighter); needing a framework-level file or process sandbox (not provided — default permissions come from the chosen provider); wanting a stack with no Azure dependency (Ollama and Foundry Local exist, but the official hosting path is still Azure-centric); requiring a stable GA API (currently public preview, so breaking changes are possible).

关机后的任务Tasks after shutdown

「关机后还能跑」在本站是靠官方 Durable 扩展兑现的，粒度是 superstep。

① 状态落盘（官方 workflows/checkpoints 页原文）：

官方原文："workflows are executed in supersteps... Checkpoints are created at the end of each superstep, after all executors in that superstep have completed"

一次 checkpoint 捕获四样东西：

  • 所有 executor 状态
  • 待处理消息
  • pending 请求/响应
  • 共享状态

② 落盘后端三档已核到：

  • InMemoryCheckpointStorage —— 进程内
  • FileCheckpointStorage —— 本地磁盘，storage_path 必填、无默认目录
  • CosmosCheckpointStorage —— Azure Cosmos DB，分布式跨进程，推荐托管身份/RBAC 认证

Python 1.13.0 起还增加 entry checkpoint。

整轮运行因此「replayable」。

③ 真后台：官方 Durable Task 扩展提供持久会话、崩溃/重启后恢复， 以及 Azure Functions 的 scale-to-zero 与 session TTL。

官方原文（等待人工时）："Pause for human input or external events without consuming compute or model tokens"

纯 SDK 不托管后台：不接 Durable 扩展，就必须自己让进程常驻。

"Still running after shutdown" is delivered here by the official Durable extension, at superstep granularity.

① State persistence (official workflows/checkpoints page, verbatim):

Official wording: "workflows are executed in supersteps... Checkpoints are created at the end of each superstep, after all executors in that superstep have completed"

One checkpoint captures four things:

  • all executor states
  • pending messages
  • pending requests/responses
  • shared state

② Three persistence backends verified:

  • InMemoryCheckpointStorage — in-process
  • FileCheckpointStorage — local disk, storage_path required, no default directory
  • CosmosCheckpointStorage — Azure Cosmos DB, distributed cross-process, managed identity/RBAC auth recommended

Python 1.13.0 also adds entry checkpoints.

A full run therefore becomes "replayable".

③ True background: the official Durable Task extension provides durable sessions, recovery after crash/restart, plus Azure Functions scale-to-zero and session TTL.

Official wording (when waiting on a human): "Pause for human input or external events without consuming compute or model tokens"

The pure SDK does not host background: without the Durable extension, you must keep the process resident yourself.

上下文与记忆Context & memory

官方把「会话状态」与「记忆」拆成两组原语。

workflow 另有 superstep 级 checkpoint。

这两件事正好对应本站「状态 ≠ 上下文」的主张。

overview 页原文列出基础积木：

官方原文："an agent session for state management, context providers for agent memory, middleware..., and MCP clients for tool integration."

公告页给出记忆的可插拔后端：

官方原文："Developers can choose Redis, Pinecone, Qdrant, Weaviate, Elasticsearch, Postgres, or their own store for conversational memory." "Agent Framework provides the abstraction; you decide the backend."

这一层是本站说的「上下文/记忆」。

workflow checkpoint 是另一回事。

它落盘的是 executor 状态与待处理消息。

这属「流程状态」，见 background 轴。

两套机制官方分节描述，不可混为一谈。

⚠ 未知：长历史如何压缩进窗口，官方未在概览层给出统一机制。 （已查 overview 页与 checkpoints 页，未见类似 ADK Context Compaction 的专章。）

The official docs split "session state" and "memory" into two primitive groups.

Workflows additionally have superstep-level checkpoints.

These two map exactly onto our "state ≠ context" claim.

The overview page lists the basic building blocks, verbatim:

Official wording: "an agent session for state management, context providers for agent memory, middleware..., and MCP clients for tool integration."

The announcement page gives pluggable memory backends:

Official wording: "Developers can choose Redis, Pinecone, Qdrant, Weaviate, Elasticsearch, Postgres, or their own store for conversational memory." "Agent Framework provides the abstraction; you decide the backend."

This layer is what we call "context/memory".

The workflow checkpoint is a different thing.

It persists executor states and pending messages.

That is "flow state" — see the background axis.

The two mechanisms are described in separate official sections and must not be conflated.

⚠ Unknown: how long histories get compacted into the window — the official docs give no unified mechanism at the overview level. (Overview and checkpoints pages checked; no dedicated chapter like ADK's Context Compaction found.)

权限与限制Permissions & limits

官方明确的机制是「HITL 请求/响应 + 工具级人工审批」。

两者都属拦执行，不是边界划定。

① 工作流层 HITL（官方 workflows/human-in-the-loop 页）：

官方原文：HITL "is achieved through the request and response handling mechanism"

.NET 用 RequestPort（发 RequestInfoEvent）。 Python 用 ctx.request_info() 配 @response_handler。

checkpoint 会一并保存 pending 请求，恢复时重新发出。

② 工具级审批（官方公告页原文）：

官方原文："tools can be marked as requiring human approval." "Agent Framework automatically emits a pending approval request that can be routed to a UI or queue, then continues or denies execution accordingly."

③ 安全样例（官方 02-agents/security）：

  • SecureAgentConfig + quarantined_llm 防 prompt injection
  • SecureMCPToolProxy 加固外部 MCP 工具
  • 跨工具机密数据外泄防护

⚠ 未知：框架级的进程/容器沙箱默认值，官方未说明。 （已查 overview、checkpoints、a2a 三页。）

The officially explicit mechanisms are "HITL request/response + tool-level human approval".

Both are execution interception, not boundary setting.

① Workflow-layer HITL (official workflows/human-in-the-loop page):

Official wording: HITL "is achieved through the request and response handling mechanism"

.NET uses RequestPort (emits RequestInfoEvent). Python uses ctx.request_info() with @response_handler.

Checkpoints also save pending requests and re-emit them on resume.

② Tool-level approval (official announcement page, verbatim):

Official wording: "tools can be marked as requiring human approval." "Agent Framework automatically emits a pending approval request that can be routed to a UI or queue, then continues or denies execution accordingly."

③ Security samples (official 02-agents/security):

  • SecureAgentConfig + quarantined_llm for prompt-injection defense
  • SecureMCPToolProxy hardening external MCP tools
  • cross-tool confidential-data exfiltration protection

⚠ Unknown: framework-level process/container sandbox defaults are not stated by the official docs. (Overview, checkpoints, and a2a pages checked.)

The workflow layer uses RequestPort (.NET) or ctx.request_info() (Python). Checkpoints also save pending requests and re-emit them on resume.

The tool layer, official wording:

tools "can be marked as requiring human approval"

The framework automatically emits a pending approval request, routed to a UI or queue. Then execution continues or is denied.

Note: this is only "ask before executing", not a sandbox.
