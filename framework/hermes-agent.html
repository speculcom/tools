适合与不适合When to use it, when not to

适合这六类场景。

  • 想要常驻的跨平台个人助手
  • 放云 VM / serverless，不绑在自己的笔记本
  • 需要定时任务无人值守
  • 需要跨会话记忆与技能自积累
  • 想用自建 endpoint 或多 provider
  • 需要命令级审批 + DM 配对做安全边界

不适合这四类场景。

  • 只做编程任务
  • 需要当嵌入式 SDK
  • 需要「状态 vs 上下文」分层保证
  • 需要企业级多用户与审计

A fit for these six cases.

  • A resident cross-platform personal assistant (six platforms: Telegram / Discord / Slack / WhatsApp / Signal / Email)
  • Running it on a cloud VM or serverless, rather than tied to your laptop
  • Scheduled tasks that must run unattended
  • Cross-session memory and self-accumulating skills
  • Using your own endpoint or multiple providers such as OpenRouter
  • Command-level approval plus DM pairing as a security boundary

Not a fit for these four cases.

  • Coding tasks only — it is a general assistant; coding is one of many things
  • Using it as an embedded SDK — it is a complete runtime, not a library
  • A detailed "state vs context" layered guarantee — it has many mechanisms, but the vendor does not split them along those two layers

⚠ Unknown: enterprise multi-user and audit. The vendor provides no separate documentation.

Checked the security and messaging pages: both cover only single-owner allowlist / DM pairing authorization, not multi-tenant audit.

关机后的任务Tasks after shutdown

这一维它的机制最厚，官方给了三重机制。

① 内建 cron 调度器。 官方特性表原文：

"Built-in cron scheduler with delivery to any platform. Daily reports, nightly backups, weekly audits — all in natural language, running unattended."

（文档 features/cron）

② serverless 休眠后唤醒。 Daytona / Modal / Vercel 后端空闲时休眠、需唤醒， 官方原话是这两个词： 官方原文："hibernates when idle and wakes on demand"

③ 常驻网关进程。 gateway 一旦运行，就能从多个消息平台随时触发。

补偿与补跑机制官方已写明（features/cron）：

  • 有 misfire catch-up 扫描
  • resume 之后 "the next tick fires one catch-up run"
  • 补跑可关：cron.catch_up_missed: false
  • 全局 hermes pause 期间，托管 cron 的 fire webhook 返 503 Retry-After: 60， 让调度器重投
  • 官方称 "nothing is lost: due work catches up on the first tick"
  • 运行中的任务 "never killed"

网关侧还有 event-loop liveness watchdog。 它连续 3 次探针无响应就以 code 75 退出，由 supervisor 重启。 另有 60s 心跳。

⚠ 未知：跨休眠 / 唤醒的状态一致性，官方未说明。

核验：已查 features/cron、features/tools、user-guide/messaging 三页。

Its mechanism is thickest on this dimension: the official docs give three layers.

① Built-in cron scheduler. Official feature-table wording:

"Built-in cron scheduler with delivery to any platform. Daily reports, nightly backups, weekly audits — all in natural language, running unattended."

(docs features/cron)

② Serverless hibernate-and-wake. Daytona / Modal / Vercel backends hibernate when idle and wake on demand; the official phrase is exactly these words: Official wording: "hibernates when idle and wakes on demand"

③ A resident gateway process. Once the gateway runs, multiple messaging platforms can trigger it any time.

Catch-up and re-run mechanics are officially documented (features/cron):

  • There is a misfire catch-up scan
  • After resume, "the next tick fires one catch-up run"
  • Catch-up can be disabled: cron.catch_up_missed: false
  • While globally paused via hermes pause, the hosted cron's fire webhook returns 503 Retry-After: 60 so the scheduler re-delivers
  • Officially: "nothing is lost: due work catches up on the first tick"
  • Running tasks are "never killed"

The gateway side also has an event-loop liveness watchdog. After 3 consecutive unresponsive probes it exits with code 75 and the supervisor restarts it. There is also a 60s heartbeat.

⚠ Unknown: state consistency across hibernate/wake — the official docs do not state it.

Verified: features/cron, features/tools, user-guide/messaging — three pages checked.

权限与限制Permissions & limits

官方文档里有一节独立的 "Security"，把权限面拆成了八层。

八层原文列的是：

  • user authorization（allowlists、DM pairing）
  • dangerous command approval
  • file write safety
  • container isolation
  • MCP credential filtering
  • context file scanning
  • cross-session isolation
  • input sanitization

逐项核验（官方 user-guide/security）：

① Command approval（默认值已核验）。 approvals.mode 有三档，默认 smart。

  • smart —— 用辅助 LLM 评风险；低危命令自动批准，真正危险自动拒绝， 不确定的升级为手动
  • manual —— 每次都问
  • off —— 等于 --yolo

超时默认 300 秒，未回复即 fail-closed。

另有始终生效的 hardline blocklist。它包含：

  • rm -rf /
  • fork bomb
  • dd 写块设备等

--yolo 或 approvals.mode: off 都不能越过它。

还有用户可编辑的 deny 规则：approvals.deny。 它用 fnmatch glob、大小写不敏感。 可以写成 "yolo 但除这些之外"。

② DM pairing（默认拒绝）。 授权检查按这个顺序走：

  • 平台 allow-all
  • DM pairing 已批准名单
  • 平台 allowlist（TELEGRAM_ALLOWED_USERS 等）
  • 全局 allowlist
  • 全局 allow-all
  • Default: deny

配对流程是 8 位码：

hermes pairing approve <platform> <code> unauthorized_dm_behavior 默认 pair。 另可设 ignore / decline。 配对码 1 小时过期、限速，5 次失败锁 1 小时。

③ Container isolation（默认关）。 terminal.backend 默认 local。 容器隔离只在改用特定后端时才启用：

  • docker / ssh / singularity
  • modal / daytona / vercel

启用后，官方列出一整套 Docker 加固 flag：

  • --cap-drop ALL
  • --security-opt no-new-privileges
  • --pids-limit 256
  • noexec tmpfs 等

迁移脚本会碰密钥。 hermes claw migrate 会导入五家 API keys：

  • Telegram
  • OpenRouter / OpenAI
  • Anthropic
  • ElevenLabs

The official docs have a standalone "Security" section that splits the permissions surface into eight layers.

The eight layers, verbatim:

  • user authorization (allowlists, DM pairing)
  • dangerous command approval
  • file write safety
  • container isolation
  • MCP credential filtering
  • context file scanning
  • cross-session isolation
  • input sanitization

Item-by-item verification (official user-guide/security):

① Command approval (defaults verified). approvals.mode has three settings, default smart.

  • smart — a helper LLM assesses risk; low-risk commands auto-approved, genuinely dangerous auto-denied, uncertain cases escalated to manual
  • manual — ask every time
  • off — equivalent to --yolo

Timeout defaults to 300 seconds; no reply means fail-closed.

There is also an always-active hardline blocklist. It includes:

  • rm -rf /
  • fork bombs
  • dd to block devices, etc.

Neither --yolo nor approvals.mode: off can bypass it.

There are also user-editable deny rules: approvals.deny. They use fnmatch globs, case-insensitive. You can write "yolo except these".

② DM pairing (deny by default). The authorization check runs in this order:

  • platform allow-all
  • DM pairing approved list
  • platform allowlist (TELEGRAM_ALLOWED_USERS etc.)
  • global allowlist
  • global allow-all
  • Default: deny

The pairing flow uses an 8-digit code:

hermes pairing approve <platform> <code> unauthorized_dm_behavior defaults to pair. It can also be ignore / decline. Pairing codes expire after 1 hour, are rate-limited, and 5 failures lock for 1 hour.

③ Container isolation (off by default). terminal.backend defaults to local. Container isolation activates only when switching to specific backends:

  • docker / ssh / singularity
  • modal / daytona / vercel

When enabled, the official docs list a full set of Docker hardening flags:

  • --cap-drop ALL
  • --security-opt no-new-privileges
  • --pids-limit 256
  • noexec tmpfs, etc.

The migration script touches secrets. hermes claw migrate imports API keys from five services:

  • Telegram
  • OpenRouter / OpenAI
  • Anthropic
  • ElevenLabs

The official docs provide --dry-run preview.

⚠ Unknown: gateway port security — the official docs have no dedicated section.

The dashboard side has OAuth / self-hosted OIDC authentication.

README 的文档目录里有一节独立的 Security，副标题原文：

Command approval, DM pairing, container isolation

逐项解读。

① Command approval —— 命令级审批。 默认 smart：辅助 LLM 评风险，低危自动批准、危险自动拒绝、不确定转手动。 超时 300 秒 fail-closed。 另有始终生效的 hardline blocklist，它不受这两个开关影响。

用户还能自己写 deny 规则：approvals.deny。 它用 fnmatch glob、大小写不敏感。

这与别家的做法不在同一层。

  • OpenHands 用 API key 机制
  • Codex SDK 有四种 ApprovalMode

② DM pairing —— 私聊配对，即只有配对过的用户能指挥它。 默认拒绝：授权检查顺序里，pairing 已批准名单排在平台 allowlist 之前。 全未命中即 deny。 配对流程是 8 位码：

  • hermes pairing approve <platform> <code>
这一项在六个消息平台入口的前提下极其重要。 一个能通过 Telegram / WhatsApp 接指令、还会在文件系统上动手的 agent， 「谁能给它下指令」就是最关键的安全问题 —— 这也是本站把它单独列出来的理由。

③ Container isolation —— 容器隔离。默认关。 terminal.backend 默认是 local。 改用下面这组后端时才会启用隔离：

  • docker / ssh
  • singularity
  • modal / daytona / vercel

The README's docs directory has a standalone Security section, subtitle verbatim:

Command approval, DM pairing, container isolation

Item by item.

① Command approval — command-level approval. Default smart: a helper LLM assesses risk; low-risk auto-approved, dangerous auto-denied, uncertain escalated to manual. Timeout 300 seconds, fail-closed. There is also an always-active hardline blocklist, unaffected by those two switches.

Users can also write their own deny rules: approvals.deny. They use fnmatch globs, case-insensitive.

This is not on the same layer as other products' approaches.

  • OpenHands uses an API-key mechanism
  • Codex SDK has four ApprovalMode values

② DM pairing — private-chat pairing: only paired users can command it. Deny by default: in the authorization-check order, the pairing approved list sits before the platform allowlist. If nothing matches, deny. The pairing flow uses an 8-digit code:

  • hermes pairing approve <platform> <code>
With six messaging entry points, this item is extremely important. For an agent that takes instructions over Telegram / WhatsApp and acts on the file system, "who can give it orders" is the most critical security question — which is why we list it separately.

③ Container isolation — off by default. terminal.backend defaults to local. Isolation activates when switching to this backend group:

  • docker / ssh
  • singularity
  • modal / daytona / vercel
