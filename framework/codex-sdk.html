适合与不适合When to use it, when not to

适合：要把 Codex 塞进 Node / Electron 应用或 CI。需要非交互执行。 需要精确到路径的权限规则。TS 或 Python 栈。 不适合：想要纯库、不愿多背一个 CLI 子进程的人。那种情况用 OpenAI Agents SDK。 目标目录不是 Git 仓库又不愿开 skipGitRepoCheck 的也不行。 需要 SDK 层直接暴露压缩 API 的也不行（CLI 侧可配 compact_prompt，见 axes.fit）。

A good fit in four cases:

  • You want to put Codex inside your own Node app, Electron app or CI
  • You need non-interactive execution
  • You need file-level permission rules
  • You are on a TypeScript or Python stack, have settled on OpenAI models, but want the model layer swappable

Not a fit in two cases:

  • You want a pure library and do not want to carry a spawned CLI child process — use the OpenAI Agents SDK instead
  • Your target directory is not a Git repository and you do not want to pass skipGitRepoCheck

⚠ One more capability boundary: if you need a compaction API exposed at the SDK layer, it does not have one. The CLI side has compact_prompt / experimental_compact_prompt_file plus PreCompact / PostCompact hooks, but the SDK layer has no dedicated compaction interface — config pass-through is the only route.

SDK 会在继承之上再注入自己需要的变量（如 CODEX_API_KEY）。

这条对 Electron / 桌面应用集成是决定性的 —— 官方明确点了这个场景。

README 原文：By default, the Codex CLI inherits the Node.js process environment

The process form is "your Node process + a spawned CLI subprocess."

The README's env parameter note is worth attention. By default the CLI inherits the Node process environment. So you can fully control which variables the CLI sees. The official use case given is sandboxed hosts (e.g. Electron apps).

The SDK injects its own needed variables (like CODEX_API_KEY) on top of the inheritance.

This is decisive for Electron / desktop-app integration — the official docs call out this scenario explicitly.

Local files are a native CLI capability; the SDK side only needs a working directory.

工具与扩展Tools & extensions

工具面完全由 CLI 决定 —— SDK 既不新增也不裁剪。

SDK 侧你拿到的是结构化事件流。runStreamed() 返回 async generator。事件类型有：

  • item.completed —— 工具调用、流式响应、文件变更通知
  • turn.completed —— 含 usage 统计

Structured output 是 SDK 明确支持的一等能力：outputSchema 可以传 JSON Schema， 官方还推荐 Zod 转换路径 zodToJsonSchema(schema, { target: "openAi" })。

⚠ 这里有个命名陷阱：那个 target 写的是 "openAi"。 但它产出的是通用 JSON Schema。给任何遵守该 schema 的模型用都行，不代表只能用 OpenAI。

MCP 的情况要说清。README 全文没出现 MCP。本站收录的 9 个 MCP server 里也没有它的位置。 但 Codex CLI 的 MCP 支持已核验（官方有独立 MCP 页）：

  • 传输：STDIO（command / args / env / env_vars / cwd）与 Streamable HTTP（url / bearer / headers）
  • 配置：codex mcp 命令行，或 config.toml 的 [mcp_servers.<name>]
  • 工具开关：enabled_tools / disabled_tools
  • 审批：per-server 与 per-tool 的 approval_mode（auto / prompt / approve）
  • 认证：codex mcp login 走 OAuth

官方原文：Codex supports MCP servers in both the CLI and the IDE extension SDK 侧：SDK 的 config 透传即写入 CLI 的 config.toml，故 MCP 可经此可用； 但官方未在 SDK README 明写这条衔接，本站只把它记作 CLI 能力， 仍不与 MCP 站的 server 建立关联。

The tool surface is entirely decided by the CLI — the SDK neither adds nor trims.

On the SDK side you get a structured event stream. runStreamed() returns an async generator. Event types:

  • item.completed — tool calls, streaming responses, file-change notifications
  • turn.completed — includes usage stats

Structured output is a first-class capability the SDK explicitly supports: outputSchema takes a JSON Schema, and the official docs also recommend the Zod conversion path zodToJsonSchema(schema, { target: "openAi" }).

⚠ There is a naming trap here: that target says "openAi". But what it produces is generic JSON Schema. Any model honoring that schema can use it — it does not mean OpenAI only.

The MCP situation needs stating clearly. The README never mentions MCP. None of the 9 MCP servers collected on this site involve it either. But Codex CLI's MCP support is verified (the official docs have a standalone MCP page):

  • transports: STDIO (command / args / env / env_vars / cwd) and Streamable HTTP (url / bearer / headers)
  • config: the codex mcp command line, or [mcp_servers.<name>] in config.toml
  • tool switches: enabled_tools / disabled_tools
  • approvals: per-server and per-tool approval_mode (auto / prompt / approve)
  • auth: codex mcp login via OAuth

Official wording: Codex supports MCP servers in both the CLI and the IDE extension SDK side: the SDK's config passthrough writes into the CLI's config.toml, so MCP is reachable this way; but the official SDK README does not spell out this linkage, so this site records it only as a CLI capability and still does not link it to the MCP-site servers.

上下文与记忆Context & memory

它提供的是「会话续接」，不是「上下文管理」。

证据是 resumeThread(threadId)。它能恢复对话继续跑，但没有压缩、摘要或落盘机制。

换句话说，Thread 解决的是可靠续跑（本站说的「状态」面）， 不解决长上下文（本站说的「上下文」面）。

要压上下文，只能靠 CLI 侧的配置或换模型 —— SDK 层没有暴露相关选项。

⚠ SDK 侧与 MCP 的衔接：SDK 的 config 透传会写入 CLI 的 config.toml， 所以 MCP 理论上可经此可用。但官方没有在 SDK README 里明写这条衔接 —— 本站只把它记作 CLI 的能力，不与 MCP 站的 server 建立关联。

What it provides is "session continuation", not "context management".

The evidence is resumeThread(threadId). It can restore a conversation and keep running, but there is no compaction, summarization or offloading mechanism.

In other words, Thread solves reliable resume (the "state" surface as this site defines it), not long context (the "context" surface as this site defines it).

To compact context you can only rely on CLI-side config or switch models — the SDK layer exposes no related options.

⚠ SDK-side linkage with MCP: the SDK's config passthrough writes into the CLI's config.toml, so MCP is theoretically reachable this way. But the official SDK README does not spell out this linkage — this site records it only as a CLI capability and does not link it to the MCP-site servers.

权限与限制Permissions & limits

这是本站核对下来最有价值的一处发现：它补上了 CLI 条目里遗留的审批枚举缺口。

证据来自 SDK 源码（不是文档）sdk/typescript/src/threadOptions.ts 的类型定义：

  • 审批模式四档 —— ApprovalMode = "never" | "on-request" | "on-failure" | "untrusted"
  • 沙箱三档 —— SandboxMode = "read-only" | "workspace-write" | "danger-full-access"
  • 网络单独控制 —— networkAccessEnabled?: boolean、 webSearchMode?: "disabled" | "cached" | "live"、webSearchEnabled?: boolean
  • 推理强度 8 档 —— ModelReasoningEffort：minimal / low / medium / high / xhigh / max / ultra / persistent

另一层是配置透传。SDK 支持 config，它会自动展平成 dotted path、转 TOML 传给 --config。 另有 configOverrides（原始 TOML 逐条透传）。官方示例直接给了文件系统级规则：

官方示例：permissions.audit.filesystem={":root"="read","/path/to/project/.env"="deny"}

也就是可以按路径精确拒绝读 .env 这类文件。官方说明的优先级： 原始 overrides > 结构化 config > SDK 托管设置。

沙箱与审批的官方口径已核验（agent-approvals-security 与 config-advanced）：

  • 本地默认 workspace-write + 网络关闭；非版本控制目录默认 read-only
  • 顶层键 approval_policy（untrusted / on-request / never / granular， 含 approvals_reviewer = "auto_review"）与 sandbox_mode 成对使用
  • [sandbox_workspace_write] 可设 writable_roots、network_access
  • 有命名 profile：:read-only / :workspace / :danger-full-access
  • workspace-write 下，.git / .agents / .codex 仍递归只读
  • 网络另有 features.network_proxy 域名 allowlist + DNS 重绑定防护

⚠ 三档沙箱在各平台的实现有差异。平台指 Windows / macOS / Linux。官方没有逐条给出这些差异。 官方只说「OS-level mechanisms enforce sandbox policies」，默认无网络、写入限工作区。

（已查 agent-approvals-security、config-advanced、config-reference 三页。）

This is the most valuable finding from this site's cross-check: it fills the approval-enum gap left in the CLI entry.

The evidence comes from SDK source (not docs), the type definitions in sdk/typescript/src/threadOptions.ts:

  • four approval modes — ApprovalMode = "never" | "on-request" | "on-failure" | "untrusted"
  • three sandbox tiers — SandboxMode = "read-only" | "workspace-write" | "danger-full-access"
  • network controlled separately — networkAccessEnabled?: boolean, webSearchMode?: "disabled" | "cached" | "live", webSearchEnabled?: boolean
  • reasoning effort has 8 levels — ModelReasoningEffort: minimal / low / medium / high / xhigh / max / ultra / persistent

The other layer is config passthrough. The SDK supports config, auto-flattened into dotted paths and converted to TOML for --config. There is also configOverrides (raw TOML passed item by item). The official example directly gives filesystem-level rules:

Official example: permissions.audit.filesystem={":root"="read","/path/to/project/.env"="deny"}

That means reading a file like .env can be denied precisely by path. The official precedence: raw overrides > structured config > SDK-managed settings.

Sandbox and approval official defaults verified (agent-approvals-security and config-advanced):

  • local default workspace-write + network off; non-version-controlled dirs default to read-only
  • top-level keys approval_policy (untrusted / on-request / never / granular, including approvals_reviewer = "auto_review") pair with sandbox_mode
  • [sandbox_workspace_write] can set writable_roots, network_access
  • there are named profiles: :read-only / :workspace / :danger-full-access
  • under workspace-write, .git / .agents / .codex remain recursively read-only
  • network additionally has features.network_proxy domain allowlist + DNS-rebinding protection

⚠ The three sandbox tiers differ in per-platform implementation. Platforms mean Windows / macOS / Linux. The official docs do not enumerate these differences item by item. They only say "OS-level mechanisms enforce sandbox policies", with no network by default and writes limited to the workspace.

(agent-approvals-security, config-advanced, config-reference pages checked.)

这个差别不是措辞问题，它决定了几件实际的事：

1. 行为边界 = CLI 版本边界。SDK 本身版本号是 0.0.0-dev（package.json 实测）， 真正决定能力的是它 spawn 的那个 CLI —— 当前 0.159.3（releases @ 2026-09-30， 另有 0.161.0-alpha.7 预发布）。升级 CLI 就等于升级 SDK 的能力与风险面。 2. 沙箱与审批不由你定。它们是 CLI 的能力，SDK 只能通过参数影响（见下文 permissions）。 3. 多一个进程就多一份开销和一个失败点。但换来的是 CLI 侧的全部能力不用你实现。

Of this site's three coding-base forms, this belongs to type 2 (wrapping an existing CLI):

② wrapping an existing CLIan external CLI subprocessCodex SDK, Claude Agent SDK
③ ships a full runtimevendor-hosted(none yet)

This difference is not a matter of wording; it decides several practical things:

1. Behavior boundary = CLI version boundary. The SDK's own version number is 0.0.0-dev (measured in package.json); what really decides capability is the CLI it spawns — currently 0.159.3 (releases @ 2026-09-30, with 0.161.0-alpha.7 pre-release). Upgrading the CLI equals upgrading the SDK's capability and risk surface. 2. Sandbox and approvals are not yours to define. They are CLI capabilities; the SDK can only influence them via parameters (see permissions below). 3. One more process means one more overhead and one more failure point. But in exchange you get the CLI's full capabilities without implementing them.

One layer deeper: reading files can be denied precisely by path. The SDK supports configOverrides passing raw TOML item by item, and the official example directly gives filesystem rules:

``ts configOverrides: ['permissions.audit.filesystem={":root"="read","/path/to/project/.env"="deny"}'] ``

This means files like .env can be denied individually. It is not coarse-grained "sandbox blocks all writes" protection. The official precedence, high to low: raw overrides, structured config, SDK-managed settings.

Sandbox / approval defaults verified (see axes.permissions): local default workspace-write + network off, non-version-controlled dirs default read-only; under workspace-write, .git / .agents / .codex are recursively read-only. The per-platform implementation differences of the three sandbox tiers are not enumerated officially: they only say "OS-level mechanisms enforce sandbox policies", without listing Windows / macOS / Linux differences separately (agent-approvals-security and config-advanced pages checked). Windows users especially should verify themselves.
