它是什么：Claude Code 的编程接口（Python 版）。

它把一个成熟的 coding CLI 变成 Python 能驱动的对象。

它不是一个自建 agent 的框架。

这也是本站十个对象里唯一不能换模型的编程底座 —— 后面所有取舍都由这条决定。

官方 README 首行："Python SDK for Claude Agent."

What it is: the Python programming interface to Claude Code. It turns a polished coding CLI into an object you can drive from Python. It is not a framework for building your own agent. It is also the only coding base among our ten objects that cannot switch models — every trade-off below follows from that.

Official README, first line: "Python SDK for Claude Agent."

适合与不适合When to use it, when not to

适合三类情况：

  • 想要一个已经被打磨过的 coding agent —— 工具集、权限链、hooks、session fork 都在
  • 团队用 Python
  • 愿意把推理完全交给 Claude

不适合三类情况：

  • 需要换模型，或接自托管权重 —— 直接排除
  • 需要框架级的自定义 agent loop —— 形状由 Claude Code 决定（备选 OpenAI Agents SDK 或 LangGraph）
  • 需要多 agent 编排 —— 它没有 agents-as-tools 那种一等委派机制

One line: it is a coding agent that has already been polished.

Swapping models and shaping the agent loop are the two things it cannot do.

Fits:

  • you want a coding agent that has already been polished — tool set, permission chain, hooks and session fork all included
  • your team works in Python
  • you are happy handing reasoning entirely to Claude

Not a fit:

  • you need a different model / self-hosted weights — ruled out outright
  • you need a framework-level custom agent loop — the loop shape is decided by Claude Code
  • you need multi-agent orchestration — it has no first-class agents-as-tools delegation

运行位置Where it runs

它是「你运营 Python 进程 + 它驱动一个 CLI 子进程」的双层结构。

实际形态：pip 包，内含 Claude Code CLI。

CLI 再去连 Anthropic API。换句话说，它不是「库」，是「带 CLI 的库」。

CLI 默认用捆绑版，也可以指向系统安装：

  • 换成本机已装的 CLI：ClaudeAgentOptions(cli_path="/path/to/claude")
  • 工作目录：ClaudeAgentOptions(cwd="/path/to/project")

核验：README 明说 CLI 随 wheel 捆绑；_cli_version.py 里 __cli_version__ = "2.1.286"。

A two-layer structure: "you operate a Python process + it drives a CLI subprocess."

Actual form: a pip package containing the Claude Code CLI.

The CLI then connects to the Anthropic API. In other words it is not "a library" but "a library with a CLI inside".

The CLI defaults to the bundled version but can point at a system install:

  • switch to a locally installed CLI: ClaudeAgentOptions(cli_path="/path/to/claude")
  • working directory: ClaudeAgentOptions(cwd="/path/to/project")

Verified: the README states the CLI ships bundled with the wheel; _cli_version.py has __cli_version__ = "2.1.286".

关机后的任务Tasks after shutdown

进程关了就停 —— 真正的「关机也跑」不存在。

但会话有官方持久化与续跑语义。存储位置已核验：

~/.claude/projects/<encoded-cwd>/*.jsonl；设 CLAUDE_CONFIG_DIR 则在其 projects/ 下。

续跑有三档：

  • continue_conversation=True：续最近会话
  • resume=<session_id>：续指定会话
  • fork_session=True：分叉

官方对 resume 的说明："picks up with full context from wherever the session left off"

官方 sessions 页原文：

官方原文："A session is the conversation history the SDK accumulates... The SDK writes it to disk automatically"

一个会话等于一个 claude CLI 子进程，进程停则 loop 停。

跨主机续跑要把 transcript 镜像到共享存储。适配器是 SessionStore。

⚠ 官方提醒：session 持久化的是对话而非文件系统。

文件回滚要用 file checkpointing。

官方原文："Sessions persist the conversation, not the filesystem"

Kill the process and it stops — true "runs after shutdown" does not exist.

But sessions have official persistence and resume semantics. Storage location verified:

~/.claude/projects/<encoded-cwd>/*.jsonl; with CLAUDE_CONFIG_DIR set, under its projects/.

Resume comes in three flavors:

  • continue_conversation=True: resume the most recent session
  • resume=<session_id>: resume a specific session
  • fork_session=True: fork

上下文与记忆Context & memory

容易忽略的一个机制：system prompt 的 snapshot 语义。

Claude Code 在会话首次请求时构建它，之后每次请求都复用。

恢复会话之后也照样复用。

改了自定义 prompt 不会立刻生效。

改了 claude_code preset 的 append 文本也一样。

要等会话被 compact，或者开一个新会话。

除非把 snapshot 设为 False（需要 CLI 2.1.257+）。

这实质上是「上下文快照不可变」的设计。

它保证了 prompt 的确定性，代价是改动生效有延迟。

这与本站「状态 ≠ 上下文」的讨论直接相关。

An easily overlooked mechanism: the system-prompt snapshot semantics.

Claude Code builds it on the session's first request, then reuses it on every later request.

It is still reused after resuming a session.

Changing a custom prompt does not take effect immediately.

The same goes for changed append text of the claude_code preset.

You must wait for the session to be compacted, or start a new session.

Unless snapshot is set to False (needs CLI 2.1.257+).

This is essentially an "immutable context snapshot" design.

It guarantees prompt determinism; the cost is delayed change effect.

This connects directly to this site's "state ≠ context" discussion.

权限与限制Permissions & limits

结论先给：默认全开，权限要你自己收。

官方给的求值链是本站目前见到的最详细的一份。README 原文：

allowed_tools is a permission allowlist: listed tools are auto-approved, and unlisted tools fall through to permission_mode and can_use_tool for a decision. It does not remove tools from Claude's toolset. To block specific tools, use disallowed_tools.

翻译过来是四条：

  • allowed_tools 是准入白名单：列进去 = 自动批准
  • 未列的工具走 permission_mode 与 can_use_tool 判定
  • 它不会把工具从工具集里移除
  • 要真正禁用某个工具，得用 disallowed_tools

hooks 提供确定性拦截：

  • 它是「Python 函数，由 Claude Code *应用*（不是 Claude）调用」
  • 拦截点：PreToolUse 返回 permissionDecision: "deny" 加理由
  • 官方示例：拦 Bash 命令

⚠ 默认起步是全工具 + 无沙箱，想收紧必须主动配置。

三个开关：

  • disallowed_tools
  • hooks
  • permission_mode

Conclusion first: everything is open by default; you tighten permissions yourself.

The official evaluation chain is the most detailed one seen on this site so far. README wording:

allowed_tools is a permission allowlist: listed tools are auto-approved, and unlisted tools fall through to permission_mode and can_use_tool for a decision. It does not remove tools from Claude's toolset. To block specific tools, use disallowed_tools.

Which unpacks into four points:

  • allowed_tools is an admission allowlist: listed = auto-approved
  • unlisted tools fall through to permission_mode and can_use_tool
  • it does not remove tools from the toolset
  • to actually disable a tool, use disallowed_tools

Hooks provide deterministic interception:

  • they are "Python functions invoked by Claude Code *applying* them (not Claude)"
  • interception point: PreToolUse returning permissionDecision: "deny" plus a reason
  • official example: blocking Bash commands

⚠ The default starting point is all tools + no sandbox; tightening requires deliberate configuration.

Three switches:

  • disallowed_tools
  • hooks
  • permission_mode
