任务：用编码 Agent 修一个真实 bugPlaybook: fixing a real bug with a coding agent

规划Planning

从仓库上下文、复现、计划、改动、测试到审查的六步流程；含权限设置、成本算式、失败模式与验收单。

A six-step flow from repo context and reproduction through planning, editing and testing to review, with permission settings, a cost formula, failure modes and an acceptance list.

准备：明确问题与范围Prepare: fix the scope

以下流程采用逐步审查的权限策略；是否逐条审批、如何接受改动，应按项目授权与实际风险配置，不是所有编码 Agent 的统一默认值。

  1. 选一个可复现的 bug：有明确复现步骤、预期行为与实际行为。
  2. 给仓库边界：只开这个仓库，不开家目录；密钥文件排除在工具可读范围外。
  3. 写清不许做什么：不许改无关模块、不许升级依赖、不许动 CI 配置。
  4. 先跑一次基线测试：记录失败用例与通过用例，作为改动后的对照。

决策点：改动涉及多个模块或难以一次审查时，先按原因和影响拆分；文件数量可以提示范围变化，但不是统一的停止标准。

This workflow uses stepwise review. Approval granularity and acceptance of changes depend on project authorisation and risk; these are not universal agent defaults.

  1. Choose a reproducible bug with steps, expected behaviour and actual behaviour.
  2. Restrict access to the repository rather than the home directory; exclude credentials from readable paths.
  3. Specify exclusions: unrelated modules, dependency upgrades and CI changes.
  4. Run baseline tests and retain passing/failing results for comparison.

If work spans modules or becomes difficult to review, split it by cause and impact. File counts can signal scope change but are not a universal stopping threshold.

复现：让 Agent 先看到失败Reproduce first

  • 把复现命令、日志、相关文件路径贴给 Agent。
  • 要求它先输出「失败原因假设 + 验证方法」，不要直接改代码。
  • 有两个以上假设时，让它按成本排序，先验最便宜的那个。

失败模式：Agent 跳过复现，直接给「可能的修复」。这种改动能通过代码审查，却可能没修到根因。

  • Supply reproduction commands, logs and relevant paths.
  • Request a cause hypothesis and a way to test it before editing.
  • For multiple hypotheses, start with a low-cost discriminating check.

Failure mode: a plausible patch without reproduction can pass review while missing the root cause.

计划：三段式Plan in three parts

要求输出三段：

段内容验收
根因哪个文件、哪一行、为什么错能被复现命令证实
改法改什么、不改什么、影响面列出受影响测试
回滚出问题怎么退回有明确命令或补丁

计划里出现「重构一下」「顺手优化」就删掉；修 bug 不是重构。

Request three parts:

PartContentsEvidence
Root causeFile, line and why it failsConfirmed by reproduction
ChangeScope, exclusions and impactAffected tests listed
RollbackHow to revert if neededExplicit command or patch

Exclude unrelated refactoring and incidental improvements from the bug-fix scope.

改动：小步与权限Edit with permissions

  • 终端 Agent：用权限确认模式，逐条看它要跑的命令；能白名单就白名单到具体命令，不要整个 shell。
  • IDE Agent：用内联 diff，逐块接受；不要一次接受整文件。
  • 云端 Agent：让它产出草稿 PR，人在本地接管后再跑测试。

权限红线：删除文件、改数据库、推远端、装全局包，四类操作必须人工确认。

  • Terminal agent: inspect execution approvals and allow specific commands rather than an unrestricted shell.
  • IDE agent: inspect inline diffs and accept the intended changes deliberately.
  • Cloud agent: obtain a draft PR and run the necessary checks during handoff.

For this review policy, file deletion, database changes, remote pushes and global package installation require explicit approval.

测试：三段证据Three pieces of evidence

  1. 复现用例转绿：原来失败的测试现在通过。
  2. 回归测试不红：原有测试集合仍通过。
  3. 手工验收：按 bug 报告的步骤再走一遍。

单元测试之外，还应根据改动风险补充回归与原始复现步骤的验收；记录哪些检查没有执行。

  1. The original failing case now passes.
  2. Relevant regression tests still pass.
  3. The original bug-report steps produce the intended behaviour.

Select regression and acceptance checks for the change's risk, and record checks that were not executed.

审查：让另一个视角看Review with a second pass

  • 让 Agent 生成「改动摘要 + 风险点 + 未覆盖场景」，人再审 diff。
  • 重点看：错误处理、边界条件、日志与隐私、是否引入新依赖。
  • 大改动拆成两个 PR：一个修根因，一个清理；不要把清理混进修复。
  • Review a change summary, risks, uncovered cases and the actual diff.
  • Inspect error handling, boundaries, logs/privacy and new dependencies.
  • Keep root-cause repair separate from broader cleanup when review scope requires it.

成本算式Cost formula

不写单价，只给算式（单价查官方定价页）：

模型费用 = Σ 每次调用的 (输入 tokens × 输入单价 + 输出 tokens × 输出单价) / 1,000,000
总成本 = 模型费用 + 实际工具费用 + 复核与其他费用
输入 tokens ≈ 仓库上下文 + 日志 + 对话历史

单价单位为每百万 tokens；缓存输入按对应费率另列，重试包含在实际调用次数中。只提供必要文件与日志，但保留复现证据和上下文。订阅不等于 API 额度；用 成本计算器 记录假设。

Use rates from the applicable official billing page:

Model cost = sum over calls of
  (input tokens × input rate + output tokens × output rate) / 1,000,000
Total cost = model cost + actual tool cost + review and other costs
Input tokens include repository context, logs and conversation history.

Rates are per million tokens; separate cached input at its applicable rate and include retries in actual calls. Provide necessary files/logs while preserving reproduction evidence. A subscription is not an API quota. Record assumptions in the cost calculator.

验收单Acceptance checklist

  • [ ] 复现步骤已记录，改动前能稳定失败
  • [ ] 根因写在计划里，且被复现命令证实
  • [ ] 改动只触及计划内文件
  • [ ] 复现用例转绿，回归测试全绿
  • [ ] 手工按原步骤验收通过
  • [ ] 无新增密钥、无无关依赖、无 CI 配置改动
  • [ ] diff 已由第二视角审查，风险点有记录
  • [ ] 回滚方式写在 PR 描述里
  • [ ] Reproduction recorded and failing before the change.
  • [ ] Root cause stated and confirmed.
  • [ ] Only planned files changed.
  • [ ] Original case and relevant regressions pass.
  • [ ] Original steps checked again.
  • [ ] No secrets, unrelated dependencies or CI changes added.
  • [ ] A second review pass records risks.
  • [ ] Rollback described in the PR.

常见失败模式Failure modes

  • 范围蔓延：修 A 顺手改 B，review 成本翻倍。
  • 假复现：Agent 没跑失败用例，直接给修复。
  • 测试替换：改测试让它通过，而不是修代码。
  • 权限过宽：整个 shell 白名单，命令注入面变大。
  • 上下文污染：把密钥、生产日志贴进对话。
  • Scope creep: fixing A while changing unrelated B increases review work.
  • No reproduction: a patch is proposed without demonstrating failure.
  • Test substitution: tests are changed to accept the bug rather than repair it.
  • Broad permissions: allowing the whole shell expands unintended execution scope.
  • Context disclosure: credentials or production logs are pasted into the conversation.

贯穿案例：空列表导致页面报错Worked example: an empty list crashes a page

以下是虚构的最小案例，演示修复记录应包含什么，不声称本站运行过该项目。

输入与现象：页面直接读取 items[0].title，当 items=[] 时出错。预期显示“暂无条目”；有内容时仍显示第一条标题。

先复现：准备空列表、单条、多条三种输入。先确认空列表失败，并记录其他两种输入的原行为。

修改范围：在读取第一项之前处理空列表。若接口约定还允许缺失字段或 null，另列对应输入；不要默默扩大数据契约。

验收记录示例：空列表显示空状态；单条与多条保持原规则；原报错不再出现。这里列的是应取得的证据，不是本页的测试结果。

如果仍失败：查看真实输入形状和错误位置，不只追加更多默认值。交付物是复现输入、改动、验证结果和未覆盖情况。

This fictional minimal case illustrates a repair record; it is not a project executed by this site.

Input and failure: a page reads items[0].title; items=[] fails. Expected behavior is an empty state, while populated lists still show the first title.

Reproduce with empty, single-item and multi-item lists. Establish the original failure and baseline behavior.

Scope: handle the empty list before reading its first item. If the interface also permits null or missing fields, document those inputs separately instead of silently widening the contract.

Required evidence: an empty state for no items, unchanged rules for populated lists and absence of the original error. These are acceptance requirements, not reported test results.

If failure remains, inspect the actual input and error location rather than piling on defaults. Deliver reproduction inputs, changes, validation results and uncovered cases.
