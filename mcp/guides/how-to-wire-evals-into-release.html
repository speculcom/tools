怎么把评测接进发布How to wire evaluations into release

评测Evaluation

评测跑通不等于会挡住坏版本；本篇写卡点位置、失败判定、放行例外与回滚，让分数进入发布决策。

A passing pipeline does not by itself stop a bad release. This guide covers where to gate, how to fail, which exceptions get signed off, and how to roll back.

这一篇讲什么What this guide covers

把评测接进发布，就是让分数有权阻止一次上线。 评测流程本身不产生约束力，卡点与判定规则才产生。 本篇写三件事：卡在哪一步、什么算失败、谁可以放行例外。 接不进决策的评测，只是仪表盘上的装饰。

Wiring evaluation into release means giving the score the power to stop a deployment. A pipeline on its own carries no authority; the gate, the failure rule and the sign-off do. This guide covers three things: which step blocks, what counts as failure, and who may grant an exception. An evaluation that never reaches the decision is dashboard decoration.

适用对象Who this is for

  • 已有一条能重复跑的评测流程，改动仍靠人工 review 把关。
  • 发布节奏按周或更快，回滚成本比你愿意承担的更高。
  • 团队对「能不能上」有分歧，需要一个共同判据。
  • 需要留下证据：某版本上线前测过什么、结果如何。

不适合：还没有可重复跑的评测。先把流程搭起来，再来接卡点。

  • An evaluation pipeline already runs repeatably, while releases still depend on human review.
  • You ship weekly or faster, and a rollback costs more than you are willing to absorb.
  • The team disagrees about "can we ship" and needs one shared criterion.
  • You must keep evidence of what was tested before a given version went out.

Not a fit: there is no repeatable evaluation yet. Build the pipeline first, then wire the gate.

前置条件Prerequisites

  1. 一个稳定跑通的评测集，含版本号与判据版本。
  2. 明确的关键子集：不能退化的那几条，例如权限、赔付、隐私。
  3. 发布流水线里能插入一个步骤，且失败能让流程停下。
  4. 一次运行的耗时与预算已知，否则卡点会被「太慢」否决。
  5. 例外放行的责任人写进流程文档，不是口头约定。
  1. A stable evaluation set with its own version number and grader version.
  2. A defined critical subset: the cases that must not regress, for example permissions, compensation, privacy.
  3. A step you can insert in the release pipeline, where a failure actually stops it.
  4. Known runtime and budget for one evaluation run, or the gate gets overruled for being slow.
  5. The exception approver written into the process document, not agreed verbally.

三个卡点Three gates

卡点目的判据形态失败时
合并前拦住明显退化关键子集全过 + 总体不低于基线阻断合并，附失败样本
预发用接近真实的配置再跑一次全量集 + 环境一致性检查阻断发布，回到改动
发布后对真实交互持续评分抽样在线判据 + 告警阈值触发回滚或降级评估

promptfoo 的 CI/CD 文档把这套作用说成两件事： 在改动进入生产前发现退化，以及质量阈值未达标时让构建失败。 官方原文（英文）："Fail the build when quality thresholds aren't met."

LangSmith 文档把评测按运行时机分成两类：开发期在整理好的数据集上跑， 生产里对真实交互实时评分。 官方原文（英文）："Run evaluations on curated datasets during development." 两个卡点用同一份判据，才能把差异归因到环境而不是判据本身。

Pre-mergeStop obvious regressionsCritical subset all pass, and total not below baselineBlock the merge with failing samples attached
Pre-productionRerun under near-live configurationFull set plus environment-consistency checkBlock the release, return to the change

The promptfoo CI/CD documentation frames this as two effects: finding regressions before changes reach production, and failing the build when thresholds are missed. Official text: "Fail the build when quality thresholds aren't met."

The LangSmith documentation splits evaluation by when it runs: curated datasets during development, live scoring of real production interactions. Official text: "Run evaluations on curated datasets during development." Use the same graders at both gates, otherwise the delta is attributable to the environment instead of the grader.

接入步骤Six steps

  1. 选卡点：先在合并前加一道，不要一次改三道。
  2. 定判定：把「失败」写成可执行条件，含关键子集与总体阈值（阈值由你的风险偏好定，本页不预设数字）。
  3. 控时长：给评测设超时与并发上限，超时的处理方式要么放行并记录，要么阻断，二者选一。
  4. 存产物：每次运行留下样本级结果，不只留一个百分比。
  5. 定例外：写明谁能放行、放行需要附什么说明、有效期多久。
  6. 接回滚：发布后卡点的告警要能直接连到回滚动作或降级开关。

判定条件要区分「测不过」与「没测成」。 评测服务返回 401 / 403 或 429 属于后者，按环境故障处理，不能当成质量结论。

  1. Pick one gate: add the pre-merge gate first, do not change three at once.
  2. Write the failure rule as an executable condition, including the critical subset and the total threshold — the numbers follow your risk appetite, and this guide does not preset them.
  3. Control runtime: set a timeout and a concurrency cap, and decide in advance whether a timeout releases with a note or blocks.
  4. Store artefacts: keep per-sample results for every run, not just a percentage.
  5. Define exceptions: who may release a block, what justification is attached, how long it stays valid.
  6. Connect rollback: the post-release alert must reach a rollback action or a downgrade switch.

The failure rule has to separate "did not pass" from "did not run". A grader service returning 401 / 403 or 429 is the second case: treat it as infrastructure, never as a quality conclusion.

贯穿案例：一次被挡住的合并Worked example: a blocked merge

情境与数字均为示例，是虚构假设，不是任何产品的实测阈值或结果。

  • 输入：一次改动把检索条数从 4 提到 8，同时改了两条提示词。
  • 处理：合并前卡点跑 60 条样本（示例规模），判定两条—— 关键子集 12 条须全过；总体通过率不低于基线减 2 个百分点（示例阈值）。
  • 结果判断（示例）：关键子集 12 条里 1 条失败，该条属于「不得承诺赔付」； 总体通过率高于基线。判定结果是阻断合并，因为关键子集不容豁免。 失败样本的检索片段里出现了另一区域的条款，方向指向检索召回而非提示词。
  • 失败后下一步： 把改动拆成两次提交——先只改检索条数复跑，确认失败是否消失； 若消失，说明召回片段变多引入了冲突证据，改回条数并给检索层加过滤； 若仍在，则把该样本连同上一版结果一起交给判据复核，确认不是判据本身写偏。

这条流程同时给出两样东西：挡住的理由与可复现的样本。 只有理由没有样本，例外放行时无从判断。

The scenario and the numbers are illustrative — invented assumptions, not measured thresholds or results for any product.

  • Input: one change raises retrieved passages from 4 to 8 and edits two prompts at the same time.
  • Processing: the pre-merge gate runs 60 samples (example size) with two conditions — the 12-case critical subset must all pass, and the total pass rate must not fall more than 2 points below baseline (example threshold).
  • Judging the result (example): 1 of the 12 critical cases fails; it belongs to "must not promise compensation". The total rate is above baseline. The verdict is a block, because the critical subset has no exemption. The failing sample retrieved a clause from another region, pointing at retrieval rather than the prompt edit.
  • What to do after a failure: Split the change into two commits — rerun with only the retrieval count changed and see whether the failure disappears; if it does, the extra passages introduced conflicting evidence, so revert the count and filter the retrieval layer; if it persists, hand that sample plus the previous version's result to a grader review, checking the grader itself.

A good gate yields two things: the reason for the block and a reproducible sample. With only the reason, an exception cannot be assessed.

验收Acceptance

  • [ ] 一次故意写坏的改动能被合并前卡点阻断，并有可点击的失败记录
  • [ ] 关键子集的选取与风险清单能对上，写明为什么是这几条
  • [ ] 环境故障与质量失败的记录字段不同，报表不会混算
  • [ ] 例外放行有留痕：谁、哪次、理由、有效期
  • [ ] 发布后卡点的告警能连到回滚或降级开关，且演练过一次
  • [ ] 评测产物含样本级结果，不只是汇总数字
  • [ ] A deliberately broken change gets blocked by the pre-merge gate, with a clickable failure record
  • [ ] The critical subset maps to your risk list, with the reason for each case written down
  • [ ] Infrastructure failures and quality failures use different record fields, so reports do not mix them
  • [ ] Exceptions leave a trace: who, which run, why, valid until when
  • [ ] The post-release alert reaches rollback or downgrade, and this has been drilled once
  • [ ] Evaluation artefacts include per-sample results, not only summary numbers

故障排查分支Troubleshooting branches

  • 卡点形同虚设：检查是否有人能一键跳过，且跳过不留痕。
  • 每次都被挡住：先看是不是判据漂移，再看基线是否长期未更新。
  • 运行太慢被关掉：把关键子集单独设为快速门，全量集放预发。
  • 分数与线上表现相反：优先检查样本是否停留在旧场景，把线上失败回补进集。
  • 判据互相矛盾：同一批样本给两个判据打出相反的结论时，人工复核并把结论写回判据说明。
  • 想加更多卡点：Anthropic 的工程博客建议从简单方案与充分评测起步， 官方原文（英文）："Start with simple prompts, optimize them with comprehensive evaluation" 先确认现有卡点没有被绕过，再加下一道。
  • The gate never blocks: check whether anyone can skip it in one click without a record.
  • It blocks every time: look for grader drift first, then for a baseline that was never refreshed.
  • The gate gets disabled for being slow: make the critical subset the fast gate and move the full set to pre-production.
  • Scores contradict production behaviour: check whether samples describe an old scenario, and backfill production failures into the set.
  • Graders disagree with each other: when two graders give opposite verdicts on the same output, review by hand and write the conclusion back into the grader notes.
  • Tempted to add more gates: the Anthropic engineering blog recommends starting simple and optimising with evaluation, Official text: "Start with simple prompts, optimize them with comprehensive evaluation" Confirm existing gates are not bypassed before adding another.

下一步Next steps

  1. 把发布后卡点的线上失败样本回补成回归项。
  2. 需要新的拦截点时，回到护栏的位置划分决定装在哪一层。
  3. 给评审与合规留一份发布前评测记录，含版本、判据与未覆盖项。
  4. 每季复核关键子集：它是否仍对应你担心出事的那几件事。
  1. Backfill post-release failures into the regression set.
  2. When a new blocking point is needed, return to guardrail placement to choose the layer.
  3. Keep a pre-release evaluation record for reviewers, with versions, graders and uncovered items.
  4. Recheck the critical subset quarterly: does it still describe the things you worry about.
