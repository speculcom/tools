先定义失败再谈改进Define failure before improving

提示词与工作流Prompts & workflows · 提示词指南Prompt guide

评测飞轮三步：人工标注失败模式、建自动评分器、校准 LLM 裁判，让每次提示词改动可比较。

The evaluation flywheel in three steps — annotate failures by hand, build automatic graders, calibrate the LLM judge — so every prompt change is comparable.

提示词效果未实测。Prompt effect has not been tested.

提示词是可复跑的模板，不是效果承诺。换模型、换版本、换输入都可能改变结果；用本页的检查点自己核对，并把官方出处当作机制依据而不是效果保证。A prompt is a re-runnable template, not a promise of results. Changing the model, version or input can change the outcome. 这一篇讲什么What this guide covers

评测回答一个问题：这次改动，比上次好还是坏。 OpenAI 给「有韧性的提示词」下了定义： "one that provides high-quality responses across the full breadth of possible inputs"。 要靠评测而不是感觉达到它。官方推荐的路径叫评测飞轮： 分析（Analyze）→ 测量（Measure）→ 改进（Improve），循环往复。 效果未实测；以下机制均出自官方教程与论文。

Evaluation answers one question: is this change better or worse than the last one? OpenAI defines a resilient prompt as "one that provides high-quality responses across the full breadth of possible inputs". Getting there takes evals, not feelings. The official path is the evaluation flywheel: Analyze → Measure → Improve, round and round. We have not run hands-on tests; the mechanisms below come from official tutorials and papers.

第一步：人工看失败Step one: examine failures by hand

飞轮从定性分析起步：人工检查错误样本并标注。 官方教程给了两步标注法： 开放编码：读约 50 条失败轨迹，给每个错误贴描述性标签，先求发现不求体系； 轴向编码：把标签归并成高层类别，得到失败分布的量化图景。 哪类失败占大头，改进就先打哪里。

为什么不能直接上自动指标？官方说得很直： 自动指标能跟踪进度，但回答不了「为什么失败」。 标注把散乱的错误变成可行动的路线图。

The flywheel starts with qualitative analysis: manually inspect and annotate failing examples. The official cookbook gives a two-step annotation method: open coding — read roughly 50 failing traces and attach descriptive labels to each error, discovery before taxonomy; axial coding — group labels into higher-level categories to get a quantitative picture of the failure distribution. Whichever category dominates is where improvement strikes first.

Why not jump straight to automatic metrics? The official answer is blunt: metrics track progress but cannot reveal why a failure occurred. Annotation turns scattered errors into an actionable roadmap.

第二步：建自动评分器Step two: build automatic graders

把失败模式变成测试集和评分器（grader），测量才能规模化。 OpenAI Evals 教程分两类评分： 代码逻辑判分——字符串匹配、JSON 可否解析，简单可靠； 模型判分——让模型按标准检查答案，覆盖开放式输出。

教程举的评分器例子：格式评分器看输出是否符合格式， 准确性评分器对照数据集里的真值列。 此后每次改动——换提示词、调参数、加边缘案例——都跑一遍。 官方建议把评分器接进 CI/CD，部署前先过线。

Turn failure modes into a test dataset and graders so measurement scales. The OpenAI Evals cookbook splits grading in two: code logic — string matching, JSON parseability; simple and reliable; model grading — a model checks the answer against criteria, covering open-ended outputs.

The cookbook's example graders: a formatting grader checks the output shape, and an accuracy grader compares against ground-truth columns in the dataset. From then on, every change — new prompt, tuned parameters, new edge cases — gets a run. The official advice is to wire graders into CI/CD and gate deployments on them.

LLM 裁判与偏差LLM judges and their biases

模型判分能规模化，但裁判本身要审。 论文系统检查了 LLM 裁判的偏差：位置偏差、冗长偏差、自我增强偏差， 以及推理能力不足。强裁判与人类偏好的一致性可达人类之间的水平（论文报告）。

官方教程给了校准裁判的流程： 用领域专家的标注当金标准；测试集通常不平衡，总准确率会骗人—— 一个永远判「过」的裁判也能拿高准确率，却抓不到任何失败。 要看 TPR（抓失败的能力）和 TNR（放行正确的能力）两个指标。 数据分三份：训练集给裁判提示词当示例，验证集用来调裁判， 测试集只在最后跑一次，防止过拟合。

Model grading scales, but the judge itself must be audited. The paper systematically examines LLM-judge biases: position, verbosity, and self-enhancement, plus limited reasoning ability. Strong judges can agree with human preferences at the level of human-human agreement (the paper's report).

The official cookbook gives a judge-calibration workflow: use subject-matter-expert labels as the gold standard; test sets are usually imbalanced, so overall accuracy lies — a judge that always says "pass" can score high while catching zero failures. Watch both TPR (catching failures) and TNR (clearing passes). Split the data three ways: a train set supplies few-shot examples for the judge prompt, a validation set tunes the judge, and the test set runs once at the end to guard against overfitting.

测试数据从哪来Where test data comes from

首选生产日志里的真实输入输出。 数据不够时用合成数据，但别只说「生成 N 个例子」——官方提醒这样会同质化。 结构化做法：定义查询的关键维度（如渠道 × 意图 × 角色）， 按维度组合生成，覆盖更广。 再加扰动：掺无关信息、故意写错、换口语说法，逼出边缘行为。

First choice: real inputs and outputs from production logs. When data runs short, use synthetic data — but do not just say "generate N examples"; the official warning is that this produces homogeneity. The structured approach: define key query dimensions (e.g., channel × intent × persona) and generate across their combinations for broader coverage. Then add perturbations: irrelevant information, deliberate mistakes, different slang — forcing edge behavior into the open.

失败模式Failure modes

  1. prompt-and-pray：改完就上线，祈祷不出事。官方用这个词形容无评测迭代。
  2. 裁判失真：不校准就信分数，偏差和盲区一起进了结论。
  3. 测试集泄漏：拿测试集调裁判或调提示词，最后的分数不再可信。
  4. 只看通过率：不知道失败集中在哪类，改进没有优先级。
  5. 以为飞轮会停：旧失败修好，更隐蔽的新失败冒出来，循环重新开始。

评测的产出不是分数，是「下一次改哪里」的路线图。

  1. Prompt-and-pray: ship the change and hope. The official term for iteration without evals.
  2. Uncalibrated judge: trusting scores without auditing the judge imports its biases and blind spots into your conclusions.
  3. Test-set leakage: tuning the judge or the prompt on the test set makes the final score untrustworthy.
  4. Pass-rate-only thinking: no idea where failures concentrate, so improvement has no priority.
  5. Assuming the flywheel stops: fix the old failures and subtler new ones emerge — the cycle restarts.

The output of evaluation is not a score; it is a roadmap of what to change next.
