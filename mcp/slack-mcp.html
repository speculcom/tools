Slack 自营的官方 MCP server（mcp.slack.com/mcp）：agent 能搜工作区、读线程、代拟消息、 管 canvas 与 Lists。两条硬口径：admin 审批是前置门；它只在会话里响应，不监视不触发。 诚实标注：旧 slackapi 仓已 404；reference 版已归档转第三方维护——本条目是 Slack 自营线。

Slack's self-hosted official MCP server (mcp.slack.com/mcp): agents search the workspace, read threads, draft messages, manage canvases and Lists. Two hard facts: admin approval is a front gate; it only answers inside a session — no watching, no triggers. The old slackapi repo 404s; the reference version was archived to a third party.

适合与不适合When to use it, when not to

适合：让 agent 拿「团队真实讨论」作上下文、频道总结、代拟消息草稿。 不适合：事件触发自动化（那是 Workflow 线的活）；要 bot-token 直连的旧路线。

Fits: agents grounding answers in real team discussions, channel summaries, drafted messages. Not a fit: event-triggered automation (that is the Workflow line); old bot-token direct routes.

模型与开放条件Model & openness

它自己不调模型——被 MCP 客户端调用的接口实现。它把 Slack 工作区能力 （搜索、读消息/线程、发消息、canvases、Lists）包装成工具给 agent 用。

It calls no model itself — an interface implementation called by MCP clients. It wraps Slack workspace capabilities (search, read messages/threads, send messages, canvases, Lists) as tools for agents.

上下文与记忆Context & memory

无 server 侧跨会话记忆——状态在 Slack 工作区本身；搜索工具是它的「取上下文」主手段。

No server-side cross-session memory — state lives in the Slack workspace itself; the search tools are its main means of "fetching context".

权限与限制Permissions & limits

权限面是这条目的核心：OAuth user-token scopes 逐工具映射（search:read、chat:write、 canvases:write 等）+ 工作区管理员审批（admin 决定哪些 MCP 客户端可连）—— 未发布 Marketplace/内部 app 连不上。写动作（发消息/建会话）跟着授权 scope 走。

The permission surface is the core of this entry: OAuth user-token scopes mapped per tool (search:read, chat:write, canvases:write etc.) + workspace admin approval (admins decide which MCP clients may connect) — unpublished Marketplace/internal apps cannot connect. Write actions (sending messages/creating conversations) follow the granted scopes.

适合什么任务Best for

适合：编码/研究 agent 取「团队在 Slack 里的决策与上下文」、总结频道、代拟消息。 不适合：要事件触发自动化（MCP 不是触发器——要自动化走 Workflow/automation 线）； 要 bot-token 无 OAuth 路线（官方走 user-token OAuth）。

Fits: coding/research agents fetching "the team's decisions and context in Slack", summarizing channels, drafting messages on your behalf. Not a fit: event-triggered automation (MCP is not a trigger — automation goes through the Workflow/automation line); bot-token routes without OAuth (the official line uses user-token OAuth).

The official docs state plainly that SSE and Dynamic Client Registration are not supported for now (third-party verification page paraphrasing the official docs) — clients must take the current remote MCP/OAuth path. 认证机制Authentication

OAuth 2.0 user-token 流（slack.com OAuth 端点授权）；工具逐一对应 scope。 管理员审批是前置门：工作区 admin 批准 MCP 客户端集成才能连。

OAuth 2.0 user-token flow (authorization at the slack.com OAuth endpoints); tools map one-to-one to scopes. Admin approval is a front gate: the workspace admin must approve the MCP client integration before it can connect.

权限范围Permission scope

读面：搜索/历史/用户档案/canvas 读；写面：发消息、建会话、reaction、canvas 写、 Lists 写、文件上传。全部跟着 OAuth scope 与 admin 策略走；无工具级独立审批机制的官方说明。

Read surface: search/history/user profiles/canvas reads; write surface: send messages, create conversations, reactions, canvas writes, Lists writes, file uploads. All of it follows OAuth scopes and admin policy; no official docs for a tool-level separate approval mechanism.
