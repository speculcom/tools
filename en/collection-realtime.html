Realtime voice agents: five latency points on one chain

Realtime voice is not “TTS + LLM”: end-to-end latency is the sum of transport, VAD/interruption, STT, LLM first token and TTS first packet. Write a budget for each segment before choosing vendors; otherwise swapping one model still leaves the user feeling half a beat behind.

This is a “who owns which layer” collection, not a duplicate of product dossiers; open an entry for its eight axes, sources and boundaries.

Which layer does what

LayerExisting entries
Realtime pipeline and transportLiveKit Agents: WebRTC, VAD, interruption, tool calls
Pipecat: observable frame-stream pipeline
Transcription and STTDeepgram: realtime streaming transcription
Speech synthesisCartesia: low-latency TTS and voice agents
Murf: TTS, voice cloning and API
Talking-head avatarD-ID: photo-driven and realtime interaction

Minimum working order

  1. Measure “user stops speaking → first audio back” end to end, not STT or TTS alone
  2. Make interruption a state machine: stop TTS when the user speaks, then decide what context to keep
  3. Record p50/p95 and failure reasons per segment; do not treat a vendor’s “low latency” as yours

Boundary

The sites have not run an end-to-end voice-latency comparison across vendors; latency depends on network, region, concurrency and utterance length, so re-test in your deployment region. Telephony and recording also require consent, retention and sensitive-data handling; recording is not a default.
