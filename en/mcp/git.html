11 questions, each comparable item by item with its peers.

Model & openness

It calls no model itself; it is an interface implementation called by clients. It invokes the local git command line directly, inheriting the local git version and configuration.

Where it runs

A local process communicating over stdio; container deployment (Docker / Podman) is also supported, but repository directories must be mounted explicitly.

A 2026-08-30 fix addressed security and compatibility issues of container bind mounts under Docker / Podman / SELinux.

Local files

Operates repositories through git; no arbitrary file read/write is needed. Every tool requires a repo_path, scoping it to that git repository. File contents inside the repository are read indirectly via git show / git_log and similar commands.

Tasks after shutdown

Not supported. The local process lives and dies with the client; under container deployment it depends on the container orchestration, not controlled by this server itself.

Tools & extensions

It provides 11 tools, including:

  • git_status
  • git_diff_unstaged
  • git_diff_staged
  • git_diff
  • git_commit
  • git_add
  • git_reset
  • git_log
  • git_create_branch
  • git_checkout
  • git_show

Including 4 write operations (commit / add / reset / checkout); output is structured text or diffs, ready for direct consumption.

Context & memory

No cross-session memory. State is carried entirely by the git repository itself; session disconnects do not affect repository state.

Permissions & limits

No separate approval mechanism. The permission boundary equals the local git user's file permissions, and it has full write capability, including committing, resetting the staging area and switching branches.

git_reset only unstages and does not discard working-tree changes; but git_checkout can switch to any branch.

Best for

Lets an Agent read repository status, history and diffs, and perform commits and branch operations under controlled conditions. Not a fit for scenarios needing push / PRs / remote repository management. This server provides no remote operations.

Transport

Supports stdio. The README also gives container deployment (Docker / Podman)

and uvx / pip local installation (full-text verification 2026-10-08); there is no official launch method for a remote transport (SSE / Streamable HTTP).

Authentication

No separate authentication layer. In stdio form it inherits the client user's git permissions; for the container form, authentication depends on the container orchestration configuration and is not stated in the repo.

Permission scope

The scope is confined to the git repository passed in — narrower than the filesystem server.

But it has full write capability (commit / add / reset / checkout), with no separate approval. Switching branches can change working-tree state — take care.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Assuming it is read-only — it can commit and switch branches
  • Assuming a container deployment can reach the host repo without help — without a mount it cannot read it
  • Assuming it can push or open PRs — this server only does local operations

Capability boundaries

This server does local operations only; it does not provide:

  • git push
  • creating PRs / issues
  • remote repository management

Remote operations need another solution (the old github server is archived, see below).

The archived alternative

The original github server provided repository management, file operations and GitHub API integration. It is archived to servers-archived. The archived repo has seen essentially no updates since 2025-05.
