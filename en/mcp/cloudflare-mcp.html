Cloudflare's official MCP server (Apache-2.0): agents write Workers, deploy, manage D1/R2/DNS, search official docs. It has the finest restricted-token granularity in its class — but remember 'can deploy = can run arbitrary code'; scope tokens to the minimum.

When to use it, when not to

Fits: deploy-debug loops on the Cloudflare stack plugged into agents. Not a fit: a hard 'config only, no deploy' boundary (narrowable, but token config must be careful).

Model & openness

It calls no model itself — an interface implementation called by MCP clients. It wraps the Cloudflare platform (Workers, Pages, D1, R2, DNS, docs retrieval, etc.) as tools for agents.

Where it runs

Primarily an official hosted remote server (the docs carry a remote-endpoint line) + runnable locally; GitHub 4,431★, last push 2026-10-22 (API verified).

Local files

Reads and writes no local project files — the scope is Cloudflare account resources (deploying Workers, writing D1/R2, etc.).

Tasks after shutdown

The remote form lives on Cloudflare's side; no background-task semantics (deploy actions complete immediately).

Tools & extensions

Grouped by product (Workers/Pages/D1/R2/DNS/Docs…), trimmable via configuration; write capability is complete (deploying Workers, creating KV/D1 databases, changing DNS records). The complete grouping follows the repo README.

Context & memory

No cross-session memory — state lives in the Cloudflare account resources themselves.

Permissions & limits

API-token permissions = agent permissions: Cloudflare tokens can narrowly restrict resources and operation surfaces — the official recommendation is to connect MCP with a restricted token. This is the finest-grained credential line among its peers, but "able to deploy code to Workers" means able to run arbitrary code — defend against that worst case.

Best for

Fits: the agent deployment flow on the Cloudflare stack (write Worker → deploy → check logs), docs retrieval. Not a fit: a hard "configure but never deploy" boundary (token granularity can narrow it, but must be configured carefully).

Transport

Remote Streamable HTTP (official hosted endpoints) + a local stdio line; the endpoint matrix is grouped by product (one remote server URL per product) — follows the repo README. Verified against: the repository and developers.cloudflare.com/changelog (2026-10-21).

Authentication

A Cloudflare API token (a restricted token is recommended: limit account/resources/operations); OAuth-line support status kept at the official category level.

Permission scope

Read surface: docs retrieval, resource queries; write surface: deploying Workers, creating/modifying D1/R2/KV, DNS record changes. Token granularity is the primary tightening control; no official statement of a tool-level approval mechanism.

Licence and terms of use

Apache-2.0 (GitHub API verified 2026-10-21).

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Plugging a full-scope global API key into an agent — the official recommendation is restricted tokens; the granularity difference is huge
  • Treating 'deploy a Worker' as a config operation — that is pushing arbitrary code to the edge
  • Reading tool-group trimming as an approval layer — trimming narrows exposure; it is not per-operation confirmation
