Model & openness

It calls no model itself; it is an interface implementation called by clients. This server produces no intelligence, only structure — what it constrains is how the Agent calls it (step-by-step thinking with revisions allowed); the actual reasoning is still done by the model behind the client.

Where it runs

A local Node.js process communicating over stdio. No file or network access needed.

Local files

No file-access capability whatsoever. It provides no read/write tools — one of the narrowest-permission entries in this section.

Tasks after shutdown

Not supported. A pure-computation tool: stateless, no background needed.

Tools & extensions

A single tool sequential_thinking,

whose parameters include:

  • thought
  • thoughtNumber
  • totalThoughts
  • nextThoughtNeeded

plus revision (isRevision / revisesThought) and branching (branchFromThought / branchId) controls.

Output is a structured object.

Context & memory

No cross-session memory. Each call receives the full thinking text; revisions and branches are passed explicitly via parameters, with no reliance on server-side storage.

Permissions & limits

No permission risk at all: no file access, no network access, writes no state. Its entire permission set is "being able to call one pure function".

Best for

Lets an Agent advance complex problems in a structured, revisable, branchable way. Not a fit for simple tasks (extra call rounds bring no benefit).

Transport

stdio only. npx / Docker local process (full README verification 2026-10-08); there is no official launch method for a remote transport. The Docker image is mcp/sequentialthinking.

Authentication

No separate authentication layer, but this is the only server in this section with no substantive permission boundary — no files, no network, no state; whether auth exists makes no security difference.

Permission scope

No file or network access; reads and writes no external resources. Its permission scope is empty — the lowest permission-risk class among MCP servers. Safe to use in sensitive environments.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Assuming it makes the model smarter — it only constrains the shape of the output; the reasoning comes from the model itself
  • Assuming it remembers previous thoughts — each call has to carry the full context itself
  • Assuming more tools are better — this server deliberately ships exactly one

Tool design

There is only one tool; its parameters fall into four groups:

GroupParametersPurpose
Progressthought thoughtNumber totalThoughts nextThoughtNeededwhat this step is, how many steps total, whether to continue
RevisionisRevision revisesThoughtacknowledge revising an earlier step
BranchingbranchFromThought branchIdfork another reasoning path from some step
ExtensionneedsMoreThoughtsdiscover mid-way that more steps are needed

"Revision" and "branching" are this server's core value — they let the Agent go back and change steps mid-reasoning, instead of one path to the end.

Key clarification: it does not boost model capability

This is the most easily misunderstood point.

This server calls no model and does no reasoning.
It constrains how the client calls it; reasoning is still done by the model.

It solves a "structure" problem, not an "intelligence" problem:

What it doesWhat it does not do
Makes reasoning visible step by stepMake the model smarter
Allows mid-way revisionImprove conclusion accuracy
Supports parallel branch explorationReduce token consumption (it increases it instead)
Lets the caller observe the processReplace thinking-budget control

Using it on simple tasks adds call rounds with no benefit. The applicable scenarios the README itself lists are also limited to: breaking down complex problems, analyses that may need correction, tasks with unclear initial scope, long tasks needing irrelevant information filtered out.
