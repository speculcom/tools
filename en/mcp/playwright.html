Model & openness

It calls no model itself; it is an interface implementation called by clients. It drives Playwright's accessibility tree rather than pixel input, so no vision model is needed and output is structured snapshots.

Where it runs

A local Node.js process (Node.js 18+ required), communicating over stdio. It also offers an HTTP endpoint mode, plus a browser-extension mode (Edge / Chrome). Headed mode is the default; switch with --headless.

Local files

No local file-access capability. The core capability is browser control. The user profile is persisted by default in the Playwright cache directory (isolated by workspace hash); --isolated switches it to in-memory only.

Tasks after shutdown

The browser process can stay resident. --idle-timeout controls idle shutdown: headless closes after 1 hour idle by default; headed mode never closes by default; the next tool call relaunches the browser.

Tools & extensions

It provides a full browser-automation toolset. This site has checked it item by item against the official README: 72 tools in total (2026-10-08):

  • navigation and tabs
  • click / drag-and-drop / hover
  • forms and keyboard input
  • accessibility-tree snapshots
  • screenshots and PDF
  • network requests and routing (route / unroute)
  • reading and writing cookies and localStorage / sessionStorage
  • file uploads
  • dialog handling
  • video recording and tracing (start / stop), plus the verify_* assertion group, etc.

Output is mainly accessibility-tree structure — structured data, ready for direct consumption.

Context & memory

Keeping the browser context is this server's core value — the README states explicitly that the MCP form suits agentic loops needing persistent state, rich introspection and iterative reasoning, e.g. exploratory automation, self-healing tests, long-running autonomous workflows.

Permissions & limits

The browser must be granted permissions, and the official docs state plainly that the restriction controls are not a security boundary.

--grant-permissions can grant geolocation, clipboard-read, clipboard-write and similar permissions.

The documentation for --allowed-origins and --blocked-origins states verbatim: "does not serve as a security boundary" and does not affect redirects. All origins are allowed by default.

Best for

Scenarios needing browser automation that must keep session state: exploratory automation, self-healing tests, long-running autonomous workflows.

Not a fit for high-throughput coding agents — the README itself recommends Playwright CLI + SKILLS for those, for better token efficiency.

Transport

Supports stdio, and offers an HTTP endpoint mode (--endpoint) plus a browser-extension connection mode (--extension; requires the Playwright extension, Edge / Chrome only).

--shared-browser-context shares a browser context; multiple HTTP clients can share one context.

Authentication

The stdio form has no separate authentication layer; it inherits the client user's permissions.

HTTP mode (official README verified 2026-10-08): the options table has no token/auth parameter. The Docker example listens bare with --host 0.0.0.0. The official docs state plainly

"Playwright MCP is not a security boundary", requiring users to harden it themselves (reverse proxy / network layer) per MCP security best practices. Add authentication yourself; do not assume it exists.

Permission scope

What it controls is the browser, not files — but the risk surface is just as wide: all origins are allowed by default (--allowed-origins allows everything by default), and browser permissions such as geolocation and clipboard read/write can be granted.

The official docs state plainly that origin restrictions are not a security boundary; for real isolation use --isolated or containerized network policies.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Treating allowed-origins as an access allowlist — the official docs state it is not a security boundary and does not guard against redirects
  • Assuming headless mode stays resident — headless closes after 1 hour idle by default, while headed never closes by default
  • Forcing MCP into high-throughput coding work — the official guidance itself suggests CLI + SKILLS instead

Core design: the accessibility tree, not pixels

Fast and lightweight — Uses Playwright's accessibility tree, not pixel-based input.
LLM-friendly — No vision models needed, operates purely on structured data.
Deterministic tool application — Avoids ambiguity common with screenshot-based approaches.

These three points are the fundamental difference between this server and other browser-automation approaches:

ApproachCostDeterminism
Screenshot + vision modelheavy token consumption, needs vision capabilitylow (the model may misread)
Accessibility treecontrollable tokenshigh (structured data)

⚠ The official self-limitation on origin restrictions (original wording)

The docs for --allowed-origins and --blocked-origins state:

Important: does not serve as a security boundary and does not affect redirects.

This means:

  • even with allowed-origins configured, redirects can still bypass it
  • it is a tool for "reducing accidents", not a mechanism for "blocking access"

The official docs writing this sentence themselves is worth more than our own inference. That is exactly what this site aims to do: record the boundaries the official side itself acknowledges.

MCP or CLI? The official docs give a clear recommendation

This is a rare passage in the README that gives a direct selection recommendation:

FormOfficial judgementReason
Playwright CLI + SKILLSbetter for high-throughput coding agentsCLI calls are more token-efficient; no large tool schemas or verbose accessibility trees to load
MCPbetter for specific agentic loopswhen persistent state, rich introspection and iterative reasoning over page structure are needed

Concrete scenarios: exploratory automation, self-healing tests, long-running autonomous workflows.

In other words: if you are a coding agent frequently driving the browser, the official docs recommend not using MCP.

Configuration options and security relevance

FlagDefaultSecurity impact
--allowed-originsallows everythingofficially stated not to be a security boundary
--blocked-originsunsetthe blocklist is evaluated before the allowlist; alone, unmatched origins still pass
--grant-permissionsnonecan grant geolocation / clipboard-read / clipboard-write
--isolatedoffwhen on, the profile is in-memory only, never persisted
--headlessoff (headed)affects idle-timeout behaviour

--isolated is the security option most worth noting here. It keeps the browser profile off disk. It suits scenarios handling sensitive login state.

Browser lifecycle

--idle-timeout: close the browser after this many ms idle; the next tool call relaunches it.
  headless  defaults to 1 hour
  headed    never closes by default
  0         disables the behaviour

This default-value difference matters a lot. Headless closes automatically (saving resources). Headed stays resident (keeping login state). If you depend on login state, headed mode is actually less hassle.
