Model & openness

It calls no model itself — an interface implementation called by MCP clients. It wraps Notion workspace capabilities (search, page read/write, database queries) as tools for agents.

Where it runs

Official hosted remote server (endpoint mcp.notion.com/mcp — direct fetch 401 = exists but needs auth, not a dead link); no official docs for a local form. notion.mcp.run direct-fetched 000 (noted as network-restricted).

Local files

Never touches the local file system — the scope is the Notion cloud workspace (pages, databases, comments).

Tasks after shutdown

The service is resident on Notion's side; MCP sessions are request-response, no background-task semantics.

Tools & extensions

Search, fetch pages, create/edit pages and database entries, etc.; the complete tool inventory follows the official docs, kept at category level. Write capabilities exist (create pages/edit blocks); the boundary follows workspace sharing and permissions.

Context & memory

No server-side cross-session memory — state lives in the Notion workspace itself; the Notion AI memory line is a separate product and does not count as this one.

Permissions & limits

OAuth user auth + the workspace permission model: what the agent can see/change follows the page-sharing permissions of the connected Notion account — this is the selection key: whose account you connect = whose visibility.

Best for

Fits: agents reading and writing the team knowledge base, writing meeting notes/tasks into Notion databases, retrieving context from the wiki. Not a fit: offline/self-hosted needs (no local form); tool-level isolation finer than account permissions.

Transport

Streamable HTTP remote hosting (mcp.notion.com/mcp); no official docs for a local stdio form. Verified: official docs page 200, endpoint 401 (direct fetch 2026-10-21).

Authentication

OAuth browser authorization flow (log into the Notion account on first connection); no official docs for a plaintext-token configuration route. Workspace admins can control connections (admin-approval surface details kept at the official category level).

Permission scope

Scope = the connected account's workspace visibility; both read and write (search/fetch pages/create pages/edit blocks). No official docs seen for a tool-level approval mechanism — tightening the write surface relies on account permissions and client-side confirmation.

Licence and terms of use

Closed-source official hosted service (under Notion's ToS); no open-source repo — official docs page direct-fetched 2026-10-21.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Assuming 'connected to Notion MCP' means 'the agent sees the whole workspace' — visibility equals the connected account's page permissions
  • Reading notion.mcp.run 000 as the service being dead — the live endpoint is mcp.notion.com/mcp (401 = auth required)
  • Writes take effect with no separate approval — think through the write surface before plugging in an agent
