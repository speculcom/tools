Model & openness

It calls no model itself — an interface implementation called by MCP clients. It wraps Neon's (serverless Postgres) management API and database operations as tools for agents.

Where it runs

A local process (npx stdio) + an official hosted remote line; GitHub 659★, last push 2026-10-29 (API verified). The old docs path (neon.com/docs/ai-and-mcp/mcp-server) direct-fetched 404 — the current line is the repo itself.

Local files

Reads and writes no local project files — the scope is Neon cloud projects/branches and databases.

Tasks after shutdown

stdio lives and dies with the client; Neon's branch capability is its signature — an agent can create database branches for isolated experiments.

Tools & extensions

Project management, branch create/delete, database query execution, schema inspection, etc.; write capabilities are complete (create branches, execute SQL). The complete inventory follows the repo README.

Context & memory

No cross-session memory — state lives in the Neon project itself.

Permissions & limits

Two credentials: a Neon API key (management surface: projects/branches) + a Postgres connection string (data surface: SQL). Neon's branch model enables the "agent tries things on a copy" isolation play — but when connected to the main branch by default the write surface is unchanged; defend on the assumption "it can execute SQL".

Best for

Fits: agent dev flows for the Neon stack (create branch→try changes→merge), hooking serverless Postgres management into an agent. Not a fit: non-Neon Postgres (it manages its own platform); hard read-only boundaries.

Transport

stdio (npx) is primary + an official hosted remote line (details follow the repo README, kept at the official category level). Verified: the repo and GitHub API (2026-10-21).

Authentication

Two routes: Neon API key (management surface) + Postgres connection string (data surface).

Permission scope

Management surface: project/branch add/delete/query; data surface: SQL execution (including writes/DDL). No official docs for a tool-level approval mechanism; the branch model is a structural isolation means, not an approval layer.

Top misconception

  • Looking for neon.com/docs/ai-and-mcp/mcp-server — that path 404s (direct-fetched 2026-10-21); the live line is the neondatabase repo
  • Treating 'branch isolation' as safe by default — the operating surface follows connection config; the main branch still gets writes
  • Mixing the management key with the data connection string — the management surface can delete projects; the data surface changes data
