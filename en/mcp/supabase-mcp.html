Model & openness

It calls no model itself — an interface implementation called by MCP clients. It wraps Supabase platform capabilities (projects, database queries, migrations, logs, docs retrieval) as tools for coding agents.

Where it runs

Two forms: local npx process (stdio) + an official hosted remote line; GitHub 2,983★, last push 2026-10-29 (GitHub API verified).

Local files

In the local form it does not directly read or write your local project files (that is the filesystem server's job) — it operates on Supabase cloud projects: tables, migrations, logs.

Tasks after shutdown

Local stdio lives and dies with the client; the hosted remote form lives on Supabase's side. No background-task semantics.

Tools & extensions

Database queries/migrations, project management, logs and diagnostics, docs retrieval, etc.; tools can be trimmed on demand (the official side supports selectively enabling tool groups); the complete inventory follows the repo README.

Context & memory

No server-side cross-session memory — state lives in the Supabase project itself (schema, data).

Permissions & limits

Credential = Supabase access token, a large permission surface: it can reach project-level APIs (including the SQL execution surface). The official side offers tool trimming and read-only tool distinctions, but SQL write/DDL capabilities genuinely exist — before hooking up an agent, defend on the worst-case assumption "you gave it a credential that can modify the database".

Best for

Fits: coding agents directly managing your own Supabase projects (inspect schema, run migrations, read logs). Not a fit: hard boundaries needing "read-only insurance" (trimming narrows but is not a sandbox); non-Supabase-stack projects.

Transport

Local stdio (npx starting a process) is primary; the official side also has a hosted remote endpoint line (details follow the official docs, kept at the official category level). Verified: repo README and GitHub API (2026-10-21).

Authentication

Supabase access token (scopes configurable); the local form passes the token via env var/parameter. The official docs give guidance on token rotation and least-privilege practices — details kept at the official category level.

Permission scope

Project level: read schema, execute SQL (including writes/DDL), manage migrations, read logs. Tool-group trimming can shrink the exposure surface; no official docs for a tool-level human approval mechanism.

Licence and terms of use

Apache-2.0 (GitHub API verified 2026-10-21; the old repo name mcp-server-supabase redirects to supabase/mcp).

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Treating tool trimming as a security sandbox — the SQL execution surface is real; credentials are the boundary
  • Using the old repo name mcp-server-supabase — it now redirects to supabase/mcp (direct-fetched 2026-10-21)
  • Treating it as a local database tool — it connects to Supabase cloud projects; local databases are out of scope
