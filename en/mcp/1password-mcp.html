11 questions, one table

11 questions, each comparable item by item with its peers.

Model & openness

It calls no model itself — a local server (stdio, running inside the 1Password desktop app) called by MCP clients. Its distinctive design is that the security boundary sits on the server side: the agent manages Environments (the secrets-holding containers), but by design the server never returns secret values to the client — the agent only ever sees variable names and environment names.

Where it runs

A local stdio server riding inside the 1Password desktop app (official docs: it runs locally as part of the 1Password desktop app); launch command 1password-mcp (client configuration) or registration via the official plugins (Claude Code /plugin install, the Cursor plugin marketplace, Codex/Kiro lines of their own). The MCP client must support stdio — remote-only clients are not supported (stated plainly by the official docs). The companion plugin repos are active (codex-plugin pushed 2026-10-29, claude-plugin pushed 2026-10-29).

Local files

It can create locally mounted .env files — secrets become available to processes on demand without writing them to disk (official wording); this is its only "local surface", and it is a controlled mount rather than free read/write.

Tasks after shutdown

No standalone background process — the server rides the 1Password desktop app and the MCP client session; when 1Password locks, the authorization window closes (an approval stays valid "until 1Password locks" without re-prompting).

Tools & extensions

Capability list (official docs wording): create/list/rename Environments; list the variable names in an Environment (never values); add variables to an Environment; create locally mounted .env files; list the mounts. There is no "read a secret value" tool — by design it cannot fetch values, which is the essential divide between it and every "credential-reading" community server.

Context & memory

No server-side cross-session memory; state lives in 1Password cloud Environments (cross-device sync is a 1Password account capability, not MCP-server memory). Approvals are granted per Environment.

Permissions & limits

The permission model is the core of this dossier: each sensitive operation triggers a secure authorization prompt in the 1Password desktop app (per-Environment approval); Enterprise admins can toggle the Local MCP server feature wholesale under Policies > Agentic permissions. Requires a 1Password account + the desktop app + an existing Environment. Beta stage (marked by the official docs).

Best for

Fits: letting coding agents (Claude Code/Codex/Cursor/Kiro) manage the "environment side" of dev secrets — create environments, add variables, mount .env — while the agent never touches plaintext secrets; governable by enterprises (policy toggle + audit). Not a fit: agents reading secret values at runtime (impossible by design); remote-only MCP clients (stdio required); scenarios outside the 1Password ecosystem.

Transport

stdio (command: 1password-mcp; rides the 1Password desktop app); the official plugin lines (Claude Code plugin/MCPB, Cursor plugin, Kiro Power) register the configuration for you. Verified: developer.1password.com/docs/environments/mcp-server (200 direct on 2026-10-31, 301 to www.1password.dev, same page).

Authentication

A 1Password account + desktop-app sign-in; sensitive operations pop an authorization window per Environment (an approval lasts until 1Password locks); Enterprise policy toggle (Policies > Agentic permissions). There is no API-token concept.

Permission scope

The Environments management surface (create/list/rename/add variables/mount .env); no secret-value read surface (by design); the local surface is only the controlled .env mount. Among the most conservative permission surfaces of credential-class MCPs.

Licence and terms of use

The core server is closed-source (shipped inside the 1Password desktop app); official companion plugin repos are MIT (1Password/1password-claude-plugin, 1password-codex-plugin, 1password-kiro-plugin, GitHub API verified 2026-10-31).

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Treating it as "an MCP that lets agents read 1Password passwords" — by design secret values never return to the agent; it is the Environments (dev-secrets container) management surface, not a vault-reading surface
  • Using a remote-only MCP client — the official docs require stdio support; the server runs on your machine riding the desktop app
  • Confusing Environments with the personal password Vault — it manages Developer Environments (.env scenarios), not the autofill vault
  • Assuming it works by default in enterprises — the admin policy (Agentic permissions > Local MCP server) can switch it off wholesale
  • Mistaking community "1Password MCPs" (the secret-value-reading bunch) for official — the official line is this Environments one only; value-reading implementations are all community, with a completely different security model
