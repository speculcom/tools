Model & openness

It calls no model itself; it is an interface implementation called by clients. It depends on @modelcontextprotocol/sdk (npm measured 2026.8.31: ^1.30.0); the protocol version is negotiated between SDK and client at the initialize handshake, not pinned to a single version.

Where it runs

A local Node.js child process communicating with the client over stdio. Its lifecycle is bound to the client process — it stops when the client exits.

Local files

The core capability. Unrestricted access is not the default: allowed directories must be given via command-line arguments, or delivered dynamically if the client supports the Roots protocol. If started with no arguments and the client does not support roots, the server errors out directly at initialization.

Tasks after shutdown

Not supported. A local stdio process lives and dies with the client; there is no standalone daemon or cloud-execution form.

Tools & extensions

It provides 11 tools: read_text_file, read_media_file, read_multiple_files,

write_file, edit_file, create_directory, list_directory,

list_directory_with_sizes, move_file, search_files, directory_tree. Output is structured content, ready for direct consumption.

Context & memory

Stateless. Each call is independent; no session memory is kept. list_allowed_directories can query the currently effective directories.

Permissions & limits

No separate approval mechanism; the permission boundary is defined entirely by the allowed directories. All file operations are confined to the allowed directories; anything outside is rejected.

Note: it provides write_file / edit_file / move_file / create_directory — a combination that is writable but has no delete tool.

Best for

Lets an Agent safely read and write text and media files inside specified directories. Not a fit for scenarios needing delete operations or cross-directory aggregation.

Transport

stdio only. A local Node.js process communicating over standard input/output. The official README (full-text verified 2026-10-08) gives only two local launch methods: npx and Docker. There is no official configuration for a remote transport. Directory control goes through command-line arguments or MCP Roots (dynamically updatable).

Authentication

No separate authentication layer. In stdio form it inherits all file permissions of the client user that launches it. The permission boundary is not an auth mechanism but a directory allowlist.

Permission scope

The default scope is narrow and explicitly forced: allowed directories must be given via command-line arguments, or delivered dynamically if the client supports the Roots protocol. With no arguments and no client roots support, the server errors out at initialization.

No delete tool is provided; write, edit, move and create-directory are. list_allowed_directories can query the currently effective directories.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Assuming the official repo's server is production-ready — the README states it is a reference implementation only
  • Starting it without a directory argument — it errors at initialisation rather than silently touching the whole disk
  • Assuming that withholding write tools prevents file changes — write_file / edit_file do write

Permission-design test notes

This is the most valuable design detail of this server.

ScenarioBehaviour
Directory arguments passed at launchThe arguments become the allowed directories
No arguments + client supports RootsClient roots fully replace server-side directories
No arguments + client lacks RootsError at initialization
Client roots change at runtimeUpdated via roots/list_changed notification, no restart needed

The "no arguments + no roots support = startup failure" design deserves credit — it turns a potential permission escape (unrestricted file access) into an explicit failure.
