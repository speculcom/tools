Skill structure: SKILL.md, scripts and resources

A usable Skill is not a Markdown note. It must be discoverable, executable and reviewable, and it must state its permission boundary.

SKILL.md: trigger first, then steps

Start with what the Skill solves, when to use it and when not to use it. Then write the steps: input, action, output, failure branches and acceptance criteria. Steps must be reproducible by another person: not “analyse it”, but “read these files, run this command, check these fields”.

scripts: runnable, with boundaries

State dependencies, input, output, exit codes and temporary-file locations. Mark every step that touches the network, secrets, writes or deletes. Do not execute remote scripts without explanation; do not put secrets in SKILL.md; do not make delete/overwrite the default action.

resources: templates, examples, references

Version templates, mark example sources and licences, and date the references. Images, fonts and table templates carry copyright; do not assume commercial use. Keep resources small: the value of a Skill is execution, not a pile of documents.

Trigger conditions and compatibility

State the supported clients, required tools, required permissions and working directory. If a Skill only works in one client, say so; do not hide the limit behind “universal”.
