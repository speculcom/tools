Warp is an open-source Agentic Development Environment — the vendor's own wording, verbatim. The same Warp Agent is reachable three ways: "In the Warp app", "In any terminal, with the Warp Agent CLI", and "In the cloud, as a cloud agent". Account, rules, skills and model access are shared across all three. The CLI is "a standalone terminal program that runs the Warp Agent" and "a native terminal multiplexer" with its own PTY, so it runs in any terminal emulator, including over SSH. Every proposed action is checked against an execution profile whose values are agent_decides / always_ask / always_allow; file edits are agent_decides by default but still prompt every time, so "you always review a diff before it's applied".

When to use it, when not to

Developers who run both shell commands and coding agent work in the terminal and want team collaboration plus cloud automation. Particularly good for: teams standardizing terminal workflows as Warp Drive Workflows / Notebooks; teams delegating background work such as issue triage or PR review to cloud agents; enterprises that need SSO, data governance or self-hosted cloud agents.

Not a fit for people who avoid terminal agents entirely and just want a classic terminal — the Free tier works as a modern terminal, but cloud agents, Warp Drive collaboration and codebase indexing are all capped.

Permissions & limits

Can do: execution profile + three-tier values + auto-approve, an in-terminal approval model.

Official wording:

Official wording: "Every action the agent proposes ... is checked against your active execution profile"

Permission values come in three tiers:

  • agent_decides — proceeds on its own when confident, asks when unsure
  • always_ask — asks every time
  • always_allow — never asks

By default shell commands, file edits, file reads and MCP tool calls are all agent_decides. File edits under agent_decides still prompt every time, to guarantee:

Official wording: "always review a diff before it's applied"

There are also these items:

  • command_allowlist / command_denylist (the denylist requires approval even under always_allow)
  • directory_allowlist
  • write_to_pty
  • run_agents
  • ask_user_question

Auto-approve (/auto-approve or Ctrl+Shift+I) grants full autonomy. Its scope is a single session; new sessions default to off. By default it bypasses the command denylist (can be turned off). But denylists set by team admins in the Admin Panel are never bypassed.

Execution profiles are stored locally only, not synced to the cloud.

Three entry points, one agent

The official docs explicitly place the same Warp Agent on three run surfaces:

In the Warp app · In any terminal (Warp Agent CLI) · In the cloud (cloud agent)

This means quotas, account, rules and skills are one shared set.

The CLI side additionally stresses it is "a native terminal multiplexer" — it ships its own PTY. So it can share the same terminal with the agent to run interactive commands, and it works over SSH.

This is what separates a "terminal agent" from a "GUI terminal emulator".

Warp Drive is its collaboration base

Warp Drive turns Workflows (parameterized commands), Notebooks (interactive runbooks), Prompts and environment variables into real-time-synced team objects.

This is its organizational surface, unlike a pure CLI agent.

But note only prompt-type objects are supported in the CLI.

Other Drive object types (Workflow / Notebook) are unavailable in the CLI. The official page states this explicitly.

Team sharing and Session Sharing are Business-and-above features.

Permission design: three-tier values + auto-approve

It sets permissions per operation type independently:

ValueMeaning
agent_decidesproceeds on its own when confident, asks when unsure
always_askasks every time
always_allownever asks

The default combination is the most worth recording. File edits default to agent_decides. But the official docs say they still prompt every time, to guarantee reviewing the diff.

And auto-approve by default bypasses the command denylist. Keeping the denylist requires turning that off manually.

But denylists set by teams in the Admin Panel are never bypassed.

"Individuals can bypass, admins cannot" — this asymmetry must be kept clear.
