The Codex IDE extension is an extension you install into VS Code / Cursor / Windsurf, not a standalone IDE — it shares the same session mechanism with the CLI through the app server.

When to use it, when not to

A fit for two groups:

  • People already in VS Code / Cursor / Windsurf who want Codex in the same environment without switching tools
  • People who need the IDE and the CLI to share sessions (the app server architecture)

Not a fit for people who need a standalone editor — this form must attach to an existing editor and cannot be used alone.

Also note: local tasks depend on the editor process staying alive, so "keep running after shutdown" requires cloud delegation (Codex Cloud).

Model & openness

It uses the CLI's agent and configuration; the model is switchable.

Official IDE page wording: "It uses the same agent as the Codex CLI and shares the same configuration"

Models listed on the official pricing page:

  • GPT-5.5
  • GPT-5.4
  • GPT-5.4 mini
  • Pro additionally has GPT-5.3-Codex-Spark (research preview)

Below the chat input there is a model switcher, with reasoning effort adjustable (low / medium / high).

The default model is set in the shared config.toml (model = "..."), shared by IDE and CLI, so custom providers go through the same model_providers configuration (see the CLI / SDK dossiers).

BYOK works: the official supports logging in with an API key; the JetBrains integration can also ride a JetBrains AI subscription. On the API-key path, the usable model range follows that key's API models.

Where it runs

It is an extension, not a standalone editor.

Official README wording: "If you want Codex in your code editor (VS Code, Cursor, Windsurf), install in your IDE."

That is: install into an existing editor such as VS Code / Cursor / Windsurf.

This is a different form from Zed (standalone editor) and Cline Desktop (native app).

Local files

Accesses workspace files through the host editor.

Context comes from open files, selections and @file references. There is also Auto Context: automatically pulling in recent files and IDE context (see /auto-context).

Official stance: workspace = current directory plus temp directories (e.g. /tmp); writes default to the workspace.

On Windows it can run natively (via the Windows sandbox) or switch to WSL2 (setting chatgpt.runCodexInWindowsSubsystemForLinux).

The official IDE docs describe no standalone semantic index — local file retrieval is done by the same agent's tools.

Verification: checked the official features and settings pages.

Tasks after shutdown

There is a cloud form: the official says tasks can be delegated from the IDE to Codex Cloud.

IDE page wording: "delegate tasks to Codex Cloud"

Features page wording: "Offload longer jobs to a cloud environment"

Switch with /cloud and /local.

Cloud tasks run in the background (including in parallel) inside OpenAI-managed containers, so cloud tasks keep going after the local editor is closed. Local tasks depend on the host editor process — close it and they stop.

Cloud tasks and local messages share plan usage (the official pricing page says a shared 5-hour window).

Tools & extensions

Built-in first-party tools and commands are all verified.

Tools:

  • web search — the official says enabled by default, via an OpenAI-maintained search cache, configurable web_search = "live" | "disabled"
  • image generation — $imagegen, model gpt-image-2, counts against usage and drains quota faster
  • code review — /review
  • editor context — @file, selections, drag-in images

Command-palette commands: chatgpt.newChat / addToThread / addFileToThread / implementTodo, plus TODO CodeLens.

Context & memory

The app-server architecture remains the key design — threads can be started, resumed and recovered; IDE and CLI share the same session mechanics and the same configuration.

The official adds three more points:

  • launching a cloud task from a local session remembers the session context (and context is kept when a cloud task returns to local to continue)
  • /status shows the thread ID, context usage and rate limits
  • /goal can set a persistent goal

Concrete context-window numbers and the automatic compaction policy are not given separately in the IDE docs.

Compaction on the CLI / SDK side goes through config keys such as compact_prompt;

Permissions & limits

IDE and CLI share the same sandbox and approvals.

Official settings page wording: "The Codex IDE extension uses the Codex CLI"

Same page: approvals and sandbox are configured in the shared ~/.codex/config.toml.

The UI side has three approval modes: Chat / Agent / Agent (Full Access).

  • default Agent — reads/writes and executes commands automatically inside the working directory, but outside the working directory or for networking it still asks
  • only Full Access skips approval for networking

Official security page stance (covering the IDE extension): by default no network + writes limited to the current workspace; .git / .agents / .codex recursively read-only.

Approval and sandbox keys are the same as the CLI: approval_policy / sandbox_mode / [sandbox_workspace_write] network_access and the network_proxy domain list. The Windows native sandbox defaults to elevated.

Best for

Fits two kinds of people:

  • those already using VS Code / Cursor / Windsurf-style editors who want Codex in the same environment without switching tools
  • those who need IDE and CLI to share sessions (the app-server architecture)

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Treating it as a standalone IDE — it is really an extension installed into an existing editor
  • Assuming the IDE extension and the CLI are two separate systems — the app server architecture lets them share sessions
  • Assuming the IDE extension has its own permission model — both share config.toml, and the sandbox and approvals are the same

Form clarification (the most easily misunderstood point)

It explicitly lists three supported host editors.

Key information: this shows the Codex IDE form is an "extension", not an "editor".
