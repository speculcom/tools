Where it runs

One process, three usages (README original wording):

"Use it in your terminal, IDE, or tag @claude on Github."

That is: terminal, IDE, and triggering via an @claude mention on GitHub. These three are different entry points of the same tool, not three implementations — unlike Cline's three forms (three independent forms).

Local files

The permission model is strongly tied to the working directory (official security page, "Working directory boundary"): in Manual mode, file tools ask before reading/writing outside the launch directory and its subdirectories.

To read a directory without asking, add it as an additional directory (--add-dir / /add-dir / additionalDirectories).

Reads can be allowed or denied precisely by path:

  • the official permissions.deny examples in settings are "Read(./.env)", "Read(./.env.*)"
  • the permissions.allow example is "Bash(npm run test *)"

Bash additionally has an OS-level sandbox (official sandboxing page, off by default):

with sandbox.enabled, writes default to the working directory + temp directory + added directories, reads default to the whole machine (including credential files like ~/.ssh, tightenable via denyRead).

1M context. These three mechanisms are read from the same settings files by the VS Code / JetBrains extensions and the terminal (official settings page), so the IDE form applies the same boundaries.

Tasks after shutdown

The IDE extension itself is a local process — quit and it stops (local sessions can be driven remotely from a phone/browser via Remote Control, but execution still happens on your machine).

But the same tool provides a "real background": cloud sessions (claude --cloud / claude.ai/code) run on Anthropic-managed cloud infrastructure.

Official wording: "The session keeps running after you close your laptop"

They can be started and viewed from browser, phone, desktop or terminal; there is also GitHub Actions (@claude, prompt automations, schedule timed runs) plus Routines scheduled/triggered runs — each execution counts as one cloud session.

Cloud sessions being available does not mean local IDE sessions can run in the background — the execution environments differ.

Tools & extensions

Built-in tools + MCP + extension mechanisms are all there.

Built-in file and web tools (Read / Edit / Write / WebFetch / WebSearch), Bash, LSP etc. (official tools-reference).

MCP support is complete (official mcp page):

transports include HTTP / SSE / stdio / WebSocket. Install scopes come in three levels: local / project (.mcp.json) / user, configured with claude mcp add, supporting mcpServers JSON import and OAuth auth.

v2.1.284 also added /mcp reconnect all and fixed the race where MCP tools reported "No such tool available" on session resume (now waits up to 10 seconds).

Extension mechanisms:

  • Hooks (ConfigChange / PreToolUse etc.)
  • Subagents (each with its own context and optional persistent memory)
  • Plugins
  • Skills
  • .claude/rules/ rules

The three entry points (terminal / IDE / GitHub) share the same set.

Context & memory

Cross-session memory has an explicit hierarchy (official memory page):

CLAUDE.md comes in four levels — managed policy / user (~/.claude/CLAUDE.md) / project (./CLAUDE.md or ./.claude/CLAUDE.md) / local (CLAUDE.local.md) — loaded broad-to-narrow and concatenated.

CLAUDE.md files in subdirectories are loaded on demand, when files in that directory are read.

There is also auto memory (notes Claude writes itself, first 200 lines / 25KB loaded per session) and .claude/rules/ (file types limitable via paths:).

Compaction runs automatically: near the limit it auto-/compact, and the official context-window page gives the retention rules for each mechanism after compaction (the project-root CLAUDE.md and auto memory are re-injected from disk).

v2.1.284 fixed the persistent "still too long after compacting" error (it compacts once more).

Models supporting 1M context have a separate [1m] variant.

The three entry points read the same CLAUDE.md set and use the same compaction strategy, so IDE and CLI are consistent.

Permissions & limits

The finest permission design in this category, shared across forms:

settings use allow / ask / deny rule classes keyed by tool and content, with official examples "allow": ["Bash(npm run lint)"], "deny": ["Read(./.env)"].

Rules come from four levels of settings files (user / project / project-local / managed), with managed settings taking highest precedence.

Permission modes include:

  • auto (reviewed by a classifier model)
  • manual (read-only start, ask one by one)
  • acceptEdits
  • plan
  • bypassPermissions
  • dontAsk

It also offers the third state "allow this once but keep asking".

Managed policies support availableModels and enforceAvailableModels, warning at startup on mismatch; /usage shows concrete dollar amounts rather than percentages.

Bash additionally has an OS-level sandbox (official sandboxing page, off by default):

once enabled, filesystem and network are doubly isolated (no network egress by default; a local proxy with a domain allowlist). Supported on macOS / Linux / WSL2; not supported on native Windows. Credential storage: macOS uses Keychain, Linux uses a 0600 file.

The VS Code and JetBrains extensions read the same settings files (official settings page), so the permission mechanisms above apply to the IDE form.

Permission design (the finest in this category, shared across forms)

This is the most valuable part of Claude Code, and because it is shared across forms, understanding it once applies everywhere:

① Asks per path + a third-state option

v2.1.284 added:

Added a "Yes, but ask again next time" answer to auto mode's prompt
before a read outside the working directories

Most tools' approvals have only two states — allow / deny. Here there is a third state: allow this once, but keep asking.

② Managed policies control usable models

In enterprise scenarios availableModels controls usable models, enforceAvailableModels decides whether it is enforced, and mismatches warn at startup — no silent degradation.

③ Quota shows concrete amounts

CHANGELOG original text (excerpt; amount examples not quoted per D9 policy):

Added dollar amounts to the Claude apps gateway spend limit in /usage
and the status line

/usage and the status line show amounts rather than abstract percentages.

Boundary handling of context compaction

Fixed "Prompt is too long" errors that persisted after compacting:
now compacts once more, keeping less of the recent conversation

After compaction a request may still be too long; then it compacts once more and keeps less of the recent conversation. This is honest boundary handling — not pretending one compaction solves everything.
