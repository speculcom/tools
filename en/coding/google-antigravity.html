8 questions, one table

8 questions, each comparable item by item with its peers.

Model & openness

The UI screenshot on the official overview page lists the model picker directly: Gemini-family and Claude-family, GPT-OSS etc. shown side by side as selectable (a screenshot-shown list; not presented as an exhaustive list). The CLI session header shows the current model (e.g. Gemini 3.8 Flash High). The model surface is decided by Google-side listing; third-party model availability changes with official adjustments.

Where it runs

Four official surfaces (overview page wording): Antigravity App (desktop, v2.5+, a standalone command center evolved from the Agent Manager), Antigravity CLI (a terminal client that runs on local shell / remote cloud environments / SSH), Editor extensions (extensions for 5 IDEs), Antigravity SDK (a Python programming runtime). App/CLI/IDE-extension execution all happen in your local environment; the SDK is "run an agent harness in a few lines of Python".

Local files

The official settings docs state the boundary explicitly: by default the agent can only access the active project folder and ~/.gemini/antigravity-ide/ (artifacts, knowledge items and configuration all live in this local directory); "non-workspace file access" is an explicit toggle, off by default.

Tasks after shutdown

The official narrative covers both synchronous pair-programming and asynchronous background agents: the App supports archiving conversations per project and scheduled messages/tasks that handle routine work automatically; the CLI can schedule background subagents.

Tools & extensions

The Artifacts mechanism (implementation plans / verification reports / proposed changes) is a core surface; browser-in-the-loop does front-end automated verification. MCP support status is outside the official docs navigation (no standalone MCP page; navigation checked 2026-10-08).

Context & memory

Knowledge items land in the local ~/.gemini/antigravity-ide/ directory (settings docs framing). How productized cross-session memory is: kept at official category level.

Permissions & limits

The official settings docs give a three-layer control surface: terminal-command auto-execution (request review vs always continue + configurable allow/deny lists), the non-workspace file access toggle (off by default), and strict mode (restricts external resources and sensitive operations). Accounts go through the Google system.

Best for

Good fit: wanting Google-family models plus multi-surface coordination (desktop command center / terminal / IDE extensions / SDK on one harness), scheduled tasks and background subagents, teams wanting an explicitly tunable "command execution policy".

Not a fit: mainland direct-connection scenarios (the main domain's direct connection is unstable), wanting artifacts kept outside the Google account system.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • The four surfaces (App/CLI/IDE extensions/SDK) are one harness with four entry points, not four separate products — don't map old Gemini Code Assist or Firebase Studio notions onto it (the official docs carry a Firebase Studio migration page; that line folds into this platform's narrative)
  • 'Always continue' mode = the agent auto-executes shell commands (official wording flags it: high autonomy, high risk) — the default is review-on-request; don't flip the switch and forget
  • The model list visible in the overview page's selector screenshot is an interface snapshot, not a promise — third-party model availability changes with official listings
