The terminal form of Cursor: it shares one account, one model catalogue and one mcp.json with the editor.

The command is agent. Officially it supports "print automation for scripts and CI pipelines", so you can put the agent inside a script.

Against the IDE form it adds two paths. One is headless non-interactive use. The other is handing a session to a Cloud Agent or a persistent session.

Three differences from the IDE form: the interaction surface (a terminal), scriptability (-p / --print plus --output-format text|json|stream-json), and the way it plugs into other clients (agent acp, which serves ACP over stdio and JSON-RPC).

When to use it, when not to

People doing engineering work in the terminal, writing scripts, or running CI/CD. The official GitHub Actions docs and cookbook cover this. People already on Cursor who want the editor and the terminal to share one account, model set and MCP config. People who need to hand a session to a Cloud Agent or keep it running through a persistent session.

Not a fit where an open-source licence or full self-hosting is required. Cursor CLI is a closed-source commercial product: it needs a Cursor account or an API key, and usage draws on the same account quota pools.

Where it runs

A local terminal process; the command name is agent.

The official install script puts it in ~/.local/bin; native Windows uses PowerShell. Auto-update is on by default; agent update upgrades manually.

The lifecycle is mainly bound to the terminal session. But the official docs offer several "detach from the terminal" paths (see background).

Compared with the IDE form in ./cursor.md, there are three differences. One is the interaction surface: here it is the terminal. Two is scriptability. Three is integration: agent acp can run the CLI as an ACP server, on stdio, for custom clients to connect.

Local files

Operates within the repo/workspace; Git worktrees can isolate changes.

Specify the workspace with --workspace <path>. Use -w/--worktree [name] to create a new worktree under ~/.cursor/worktrees/<reponame>/<name> (sharing retention rules with the editor).

Writing to disk is tightened by default. To land changes in scripts you need --force (or --yolo). Official headless-page wording:

Official headless-page wording: "Without --force, changes are only proposed, not applied"

Note the parameters page has a contradicting statement; both pages coexist:

Official parameters-page wording: "Has access to all tools, including write and shell"

Rules are read from .cursor/rules and AGENTS.md / CLAUDE.md at the project root. Read/write scope is precisely controlled by permissions Read(...) / Write(...).

Tasks after shutdown

The terminal process ends with the session, but the official docs provide three "detach from the terminal" paths.

One is Cloud Agent handoff. Prefixing a message with & in a session lets you pick it up on web or mobile at cursor.com/agents.

Official wording: "continue running while you're away"

Two is persistent sessions. Start with agent persist, detach with /detach, reconnect with agent persist attach, manage with agent persist list / stop. This capability came in v2026.08.26; changelog wording:

v2026.08.26 changelog wording: "Keep agents running after you disconnect"

Three is agent worker, officially described as starting a private cloud worker:

Official wording: "a private cloud worker that runs agents in your environment"

The execution-environment ownership and quota limits of each of the three paths are not spelled out separately on the official pages.

Tools & extensions

The tool surface has three layers, all three verified.

Layer one: built-in tools. Official using-page wording:

Official using-page wording: "Agent has tools for file operations, searching, running shell commands, and web access"

Within it, Shell Mode (/shell, aliases /sh, /run) runs commands in a login shell.

Layer two: MCP. The CLI automatically reads mcp.json:

Official wording: "automatically detect and respect your mcp.json"

Locations are .cursor/mcp.json or ~/.cursor/mcp.json, sharing the same servers with the editor. There is also the agent mcp subcommand (login / list / list-tools / enable / disable) and --approve-mcps.

Layer three: ACP. agent acp exposes an ACP server over stdio + JSON-RPC.

Extension mechanisms additionally include plugins (--plugin-dir, /plugin), skills (pasteable as a custom mode) and .cursor/rules.

Context & memory

Sessions are resumable, forkable, and compactable.

Continue sessions with --resume [chatId], --continue, agent resume, agent ls, /resume. /fork forks the current session into a new one; /rewind jumps back to earlier messages. Context compaction uses /summarize (alias /compress).

v2026.09.22 fixed a pitfall: earlier summaries could drop the latest request or the whole session. Now the most recent user message is preserved verbatim. If summarization fails or is aborted, the original session is kept.

Long-term context relies on rules and skills. .cursor/rules and AGENTS.md / CLAUDE.md load automatically. /goal can set a long-term goal, officially marked "Rolling out".

Where cross-session memory is stored is not explained on this page by the official docs.

Permissions & limits

The permission design is the finest-grained part of this form factor, with additional sudo credential protection.

There are two config files: global ~/.cursor/cli-config.json, project-level <project>/.cursor/cli.json.

Permission tokens come in five classes:

  • Shell(cmd)
  • Read(path)
  • Write(path)
  • WebFetch(domain)
  • Mcp(server:tool)

Controlled via permissions.allow / permissions.deny; deny takes precedence over allow.

By default, every terminal command requires approval. Official using-page wording:

Official using-page wording: "Before running terminal commands, CLI will ask you to approve (y) or reject (n)"

--force (alias --yolo) grants a pass. The sandbox is controlled by /sandbox or --sandbox enabled|disabled; the official docs say disabling uses "allowlist mode".

When sudo is needed, a masked password prompt appears. The official docs say the password goes straight to sudo via secure IPC:

Official wording: "The AI model never sees it"

For CI, the official docs recommend restricted autonomy + permission-based restrictions, writing instructions into permissions.json alongside Auto-review.

Best for

Fits three kinds of people:

  • those doing engineering tasks in the terminal, writing scripts, or running CI/CD (official GitHub Actions docs and cookbook)
  • those already using Cursor who want the editor and terminal to share one account / models / MCP config
  • those who need to hand sessions to a Cloud Agent or keep them running in a persistent session

Not a fit for scenarios requiring an open-source license. Cursor CLI is a closed-source commercial product, requires a Cursor account or API key, and its usage is folded into the account's quota pool.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Thinking Cursor CLI is a standalone free tool: it needs a Cursor account or an API key, and usage draws on the same account quota pools.
  • Assuming print mode writes files by default: the headless page states that without --force / --yolo changes are only proposed, not applied.
  • Expecting Shell Mode to run long tasks: commands time out after 30 seconds and the limit is not configurable.

Headless / non-interactive (the key point of this section)

The official headless page spells out the scripting contract:

  • one-shot execution: agent -p "...". Official wording "Use print mode (-p, --print) for non-interactive scripting and automation"
  • landing changes: batch file edits need --force (alias --yolo). Official wording "Without --force, changes are only proposed, not applied"
  • output: --output-format text | json | stream-json, with --stream-partial-output for incremental streaming; the example script parses tool_call events with jq
  • auth: export CURSOR_API_KEY=... (stored as a repo/org secret in CI)
  • trust: --trust trusts the workspace without interaction under headless

For CI, the official docs distinguish two autonomy levels and recommend "restricted autonomy" for production: leave commits, pushes and comments to deterministic CI steps; the agent only edits files. Then enforce hard constraints at the CLI layer via permissions.allow / deny.

Permissions and sandbox

Five permission-token classes, written in ~/.cursor/cli-config.json (global) or <project>/.cursor/cli.json (project-level). deny takes precedence over allow.

tokenexample
Shell(cmd)allow Shell(git), deny Shell(rm)
Read(path)Read(**/*.md), deny Read(.env*)
Write(path)Write(src/**), deny Write(**/*.key)
WebFetch(domain)fetches not in allow require approval each time
Mcp(server:tool)Mcp(datadog:*), Mcp(*:*)

In interactive mode, every terminal command requires approval by default. The sandbox toggles via /sandbox or --sandbox enabled|disabled; disabling degrades to allowlist mode.

When sudo is needed, the official docs say the password goes straight to sudo via secure IPC — the model never sees it in plaintext.
