AI Tools

AI coding

Finished AI coding tools you can run yourself, compared on eight shared dimensions (model access / where it runs / local files / tasks after shutdown / tools and extensions / context / permissions / best fit). Grouped into three forms — IDE, CLI and vendor cloud. The first two are different install forms of the same product, not competitors; vendor cloud is a different direction entirely: nothing to install, the work happens on someone else's machine.

In plain words

AI coding: who it works for

01

Who it is for

People who want AI to edit a real codebase, run tests and open a PR.

02

When not to use it

You only need one-line completion, or you are not ready to give it command permissions.

03

Three questions before paying

  1. How many files can it edit — can it refactor across files?
  2. What command, network and write permissions does it get?
  3. Does code leave my machine, and is my repo used for training?

Answer one question first: how much do you want it to do for you

This section holds 41 entries, split three ways: 19 are IDE-form tools installed on your own machine, 12 are CLI-form, and 10 are vendor cloud — nothing installs locally, the work happens on someone else's machine. Five pairs are the same product in two forms — Aider, Claude Code, Codex, Copilot and Cursor each have an IDE entry and a CLI entry; they are not competitors, and they differ in where they install, how they are invoked, and whether they drop into scripts. Deduplicated, that is 36 products.

  1. 1I want an editor I can launch myself
    See IDE · standalone editorCursor, Windsurf (now renamed Devin Desktop), Zed and AWS's Kiro are all in this group.
  2. 2I already use VS Code / Cursor
    See IDE · extension formClaude Code, Codex, Copilot, Cline, JetBrains' Junie and Continue all install into an existing editor. Note that Claude Code, Codex and Copilot also have CLI forms — do not compare them as if they were two products.
  3. 3I do not want to switch editors or install plugins
    See Aider (Watch mode)It is not an editor plugin but a background resident process: add an AI comment in any editor and it responds.
  4. 4I want it to ask me at every step
    See the CLIs that confirm every action by defaultCrush asks before every tool call by default; Aider has auto-commit but its sandbox mechanism is unverified.
  5. 5I want it to run on its own within a set scope
    See those with an explicit sandbox / trusted directoriesGemini CLI documents its sandbox and Trusted Folders separately; Claude Code CLI has the finest permission granularity, including "allow just this once".
  6. 6I need it to run in CI / scripts
    A whole batch now has official evidenceBeyond Gemini CLI and Codex CLI, the 2026-10 additions all document non-interactive execution: Cursor CLI (headless), Copilot CLI (-p), Continue (cn -p), goose (goose run), Droid (droid exec) and the Kiro CLI (--no-interactive).
  7. 7I want it to keep working after I close the client
    Start with the 10 vendor-cloud entriesThat layer is 'the whole machine is in the cloud': Dot, Muse, Grok Bot, Jules, Augment, Bolt, Devin, Lovable, Replit Agent and v0 — they differ in how approval and async flow are designed — Muse has a separate Sentinel agent, Dot reviews automatically, Grok Bot's official page does not say, and Jules gates on an approved plan (skippable via API). Some local forms also offer cloud execution for specific tasks (Cursor's cloud agents, Kiro's Cloud Sessions, Amp's orb, Copilot's coding agent) — so check the `background` dimension per entry instead of assuming by form.
  8. 8I need data never to leave my machine
    Nothing here fits eitherThe vendor-cloud machines are on someone else's (Dot is isolated from your machine by default and only touches it once authorised); among local forms, only the sandbox / trusted-directory tier can restrict write scope.

⚠ Two misconceptions people fall into most easily: "AI-native editor" does not mean "model is selectable" — form is `runtime`, model access is `model_access`, and the two dimensions are separate. Codex CLI's approval modes and sandbox tiers are not in its CLI documentation, only in its SDK source: four approval modes × three sandbox tiers (read-only / workspace-write / danger-full-access), plus per-path denies on reading `.env`. Cross-platform differences remain unverified.

What to look at when choosing

Every tool is broken down by the same questions, so you can compare them side by side. Open any entry to see the official wording and link; disagree and check it yourself.

01

Model & openness

Whose model does it use? Can you switch to a third party? How is multi-model routing configured?

02

Where it runs

Local, cloud or hybrid? Is the index local or remote? Remote control is not the same as cloud execution.

03

Local files

How wide an area can it reach? How does it read large files you have not opened? How capable is it at the symbol level?

04

Tasks after shutdown

Does it keep running once the computer is off? This is the most common misconception about local forms.

05

Tools & extensions

How wide is the toolchain: MCP · LSP · plugins · hooks · custom instructions?

06

Context & memory

Indexing algorithm, context window, session resume and fork, and the boundary of cross-session memory.

07

Permissions & limits

Sandbox and approval boundaries, credential handling, whether data leaves your machine, and how quota is charged.

08

Best for

What tasks is it best at? When should you not use it?

Why there is no overall ranking

This is not an omission but a deliberate methodological choice.

  • No shared measurement, no score. Benchmarks across tools use different rules — different questions, budgets and environments. A 90 and a B 88 are not comparable.
  • "Unknown" is a legitimate answer. If it cannot be found, we write "unknown" and explain why, instead of filling the gap with guesses. Missing information is itself information.
  • Every field carries a source link, so you can go back to the original.
  • A recent check does not mean it stays valid. When upstream archives or changes, the entry is marked active / maintenance / archived.
  • Families are not mixed. Ready-made tools, things you build yourself, and plug-in-and-run components are three different roles with different ways of judging them; forcing them into one master table would manufacture false comparability.

How to read the confidence marks

Both the detail pages and the table above carry confidence, which reflects how complete this site's data is, not a judgement of the product.

verifiedall 8 dimensions have official sources and were updated within 90 days
partialsome dimensions are marked unknown, the official docs were unreachable, or the info is over 90 days old
stalethe vendor has shipped a significant change that this site has not updated yet

Sources and how to re-check them

All data comes from the open-source repository speculcom/ai-handbook (CC BY 4.0).

Every entry is plain Markdown plus frontmatter, carrying dimension records and an evidence chain with links, checked dates and confidence marks. The repository contains:

  • tools/METHODOLOGY.md —— the methodology charter and core rules
  • tools/axes/ —— the definition and decision criteria for each dimension (with positive and negative examples)
  • tools/SCHEMA.md —— the data-format spec and build validation rules
  • tools/protocols/<category>/_protocol.md —— the measurement protocol (not yet run, so this site has no measured conclusions)

Found an error or have new evidence? Open an issue or a PR — each correction notes its basis and blast radius.
