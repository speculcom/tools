Junie is JetBrains' coding agent, installed as a plugin — the official install page states "The Junie plugin is not bundled and not enabled in JetBrains IDEs by default" — and extended in March 2026 by a standalone Junie CLI for the terminal, any IDE, CI/CD and GitHub / GitLab. Its official framing is LLM-agnostic: "Junie supports all the top-performing models from OpenAI, Anthropic, Google, and Grok." On the IDE side it plans before it codes and, since GA, drives your IDE's real debugger rather than adding println.

When to use it, when not to

People already using JetBrains IDEs (IntelliJ IDEA / PyCharm / WebStorm / GoLand and more) who want an agent in the same environment. Teams that value "plan before code" and multi-model / BYOK flexibility. Anyone who needs the same agent in the terminal or CI/CD (Junie CLI).

Not a fit for users in Mainland China — the official licensing page states "Junie coding agent is not available to users in Mainland China due to regional restrictions"; nor for AI Enterprise tier users (that page states the tier does not currently include Junie), nor for anyone who needs a vendor-hosted cloud background environment.

Model & openness

Conclusion: no model lock-in; you can bring your own API key, and local models work too.

The official pages position it as LLM-agnostic. The Junie CLI launch blog states it bluntly:

Official wording: "Junie supports all the top-performing models from OpenAI, Anthropic, Google, and Grok"

Official pricing builds BYOK (bring your own API key) into the model. The site and pricing page list two more routes:

  • Local models — via OpenAI-compatible APIs, including Ollama and LM Studio
  • Third-party cloud models — OpenAI / Anthropic / Google / xAI

The IDE-side default model has changed. The help page Models (revised 2025-10-14) says Default is OpenAI's GPT-5. The 2026-08-17 official blog then says the default became Gemini 3.7 Flash.

The local-inference story also changed over time. The help page then said "local models cannot be used in offline mode yet". Junie Local from 2026-08 supports running Qwen3.6-27B on your own machine.

The concrete model list and per-tier availability are not given in full on any single official page. (help Models page and the AI pricing page checked.)

Where it runs

It is a plugin, not a standalone editor; there is also a standalone Junie CLI.

The official Install page states:

Official wording: "The Junie plugin is not bundled and not enabled in JetBrains IDEs by default"

Hosts cover the whole JetBrains family plus Android Studio:

  • CLion, GoLand, IntelliJ IDEA, PhpStorm, PyCharm Pro
  • Rider, RubyMine, RustRover, WebStorm and Android Studio

The official pages also give per-IDE minimum versions. E.g. IDEA Ultimate / PyCharm Pro / WebStorm / GoLand need 2024.3.2+.

The second leg is Junie CLI (entered Beta in 2026-03). It runs in terminals, any IDE, CI/CD and GitHub / GitLab. ReSharper 2026.2 brings it into Visual Studio (Preview). Since 2026-08 there is also Junie Local with on-device inference.

Local files

It only touches files in your current project; leaving the project needs separate approval.

After each run, Junie lists the files added and modified. Every file has a diff-view link. In the Done panel you can selectively roll back file by file. Then you decide to accept or reject the whole run. Output of the commands it runs can be seen in Junie's terminal.

"Outside the project" is an explicit boundary. The Action Allowlist has two separate rules, both requiring approval by default:

  • "Read outside project"
  • "Write outside project"

To limit which files and directories it handles, use .aiignore. Its syntax is the same as gitignore. The official pages warn: it protects content only; file names and directory names remain visible.

Implementation details of the IDE semantic index are not broken out officially. (the aiignore and diffs-and-review pages checked.)

Tasks after shutdown

There is no vendor-hosted background: tasks run inside the environment you have open.

The IDE form depends on the IDE process staying open. In this form the official pages describe no vendor-hosted "keeps running after shutdown" background. In Code mode it can autonomously run multi-step tasks, tests and builds — but all of that happens in your open IDE and on your machine.

Junie CLI extends the runtime surface to terminals, CI/CD and GitHub / GitLab. Those are "your own execution environments", not a vendor sandbox.

The official blog also says Junie can:

Official wording: "run long tasks while you focus on other things"

But no background concurrency or duration quota is given officially.

A vendor-hosted background execution environment: not stated officially. (the modes, licensing and CLI launch blog checked.)

Tools & extensions

Capabilities are layered by mode; the signature move is using the real debugger.

Four modes:

  • Code mode — breaks work into a multi-step plan and executes autonomously: runs commands, creates files, edits code, runs tests
  • Ask mode — read-only exploration and analysis
  • Plan mode — first produces an editable structured plan, then implements
  • Auto — it picks

Debugging is not adding logs — it genuinely takes over the debug session. Since the GA release, Junie can start or take over debug sessions. It sets breakpoints in project code, library code and even decompiled .class files. It can inspect stack frames and thread state, and evaluate expressions.

Official wording: "uses the debugger, not println"

There is also PR review and git workflows. And /demo: runs through a feature and produces video / screenshots / an HTML report.

MCP is officially supported, but currently only the stdio transport. mcp.json comes in two levels: global ~/.junie/mcp.json, project .junie/mcp. It can auto-recommend relevant servers.

Official wording: "Only MCP servers that use the Standard Input/Output (stdio) transport type are currently supported"

Context & memory

Plans are committable artifacts; Guidelines are persistent context.

Plan mode's plan is not a throwaway conversation. Plan documents live in .junie/plans and can be committed to version control. They are paginated by product requirements, technical design, delivery phases (optionally a test strategy). When requirements are vague, Junie asks back first and only implements after confirmation.

.junie/guidelines.md is the persistent layer. It is added to every task, can be version-controlled and reused. The official pages also mention a junie-guidelines directory.

The official pages also call Junie context-aware by default and say it does next-task prediction. Connected to a JetBrains IDE, it adds semantic refactoring and smart search.

Context window and compaction strategy — no numbers given officially. (customize-guidelines and the out-of-beta blog checked.)

Permissions & limits

By default every action needs approval. Brave Mode opens everything at once, but the official pages do not recommend it.

The official pages split actions into safe and sensitive.

Official wording: "Most terminal commands, code execution, and execution of MCP tools are considered to be sensitive actions, and Junie by default requires explicit approval from the user"

Brave Mode can release all sensitive actions in one switch.

Official wording: "using brave mode is not recommended"

The Action Allowlist whitelists by type:

  • Terminal (regex supported), RunTest, Build, Preview
  • MCP, Read outside project, Write outside project
  • Edit build scripts — it can trigger code execution, so it gets its own gate

ls / cd / pwd need no confirmation by default.

.aiignore protects file content. But the official pages note: Brave Mode, or commands matching the allowlist, can bypass it.

Key designs: Plan mode and the real debugger

Plan mode makes the "plan" a first-class artifact (new in the GA release). When requirements are vague it asks back first and implements only after confirmation. The official usage advice is concrete: use a strong model for the plan, a cheap model for implementation.
