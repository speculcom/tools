Model & openness

A coding harness that plugs into many providers. Official models and providers pages:

OpenCode uses AI SDK and Models.dev, supporting 75+ LLM providers, and also supports running local models. The catalog includes:

Credentials go through /connect into ~/.local/share/opencode/auth.json;

enabled_providers / disabled_providers act as allow/deny lists, and custom providers can be defined (npm + baseURL, OpenAI-compatible included); there is also the official curated list OpenCode Zen. Local models can be connected —

the official docs name llama.cpp, LM Studio, Ollama, Atomic Chat.

Where it runs

A local process running in the terminal. Multi-platform installs are provided (macOS Homebrew / Windows Scoop etc.). Its lifecycle is bound to the terminal session.

Local files

Coding capability aimed at real code repositories. read/edit/write/grep/glob read and write the workspace directly. grep/glob use ripgrep underneath, following .gitignore by default.

Access is confined by default to the working directory at launch — paths outside it must be explicitly allowed via external_directory in permission (e.g. ~/projects/personal/**).

read is allow by default, but .env / .env.* are deny by default (.env.example allow). The @ key fuzzy-searches project files; file changes have a watcher (with configurable ignore).

Symbol-level capability comes from the LSP tool (experimental): it needs OPENCODE_EXPERIMENTAL_LSP_TOOL=true plus your own LSP servers, supporting goToDefinition / findReferences / hover and more.

No description of codebase vectorized indexing was found officially (tools / config / permissions pages checked).

Tasks after shutdown

Terminal form, local process, lifecycle bound to the session.

The official docs also have opencode serve (a headless HTTP server). There is also opencode web and a desktop app. They all run on your own machine. They expose a session API to clients, including prompt_async for async sending. The execution environment is yours, not a vendor-hosted cloud.

No cloud background capability that "keeps running after the client closes / survives shutdown" was found officially (server page and docs overview checked).

Context & memory

ACP (Agent Client Protocol) load capability is its differentiating design — preserving model, effort and mode boundaries across restore and fork.

Session mechanics verified: the /session API supports creating, forking (branching at a given message), revert/unrevert and summarize. The TUI has /undo, /redo, /share.

The compaction policy is configured officially — the compaction item:

  • auto (default true, auto-compacts the session when context fills up)
  • prune (deletes old tool output to save tokens, default false)
  • reserved (compaction buffer)

There are also three built-in agents: compaction / title / summary.

Permissions & limits

Permission policy verified: the permission config decides per operation whether it runs automatically, asks for approval, or is blocked — three tiers "allow" / "ask" / "deny".

Fine-grained per-tool config is supported, with wildcards and object syntax (for bash: git * allow, rm * deny, the last matching rule wins).

Configurable permission keys:

  • read
  • edit (covers edit, write, patch)
  • glob
  • grep
  • bash
  • task
  • skill
  • lsp
  • webfetch
  • websearch
  • external_directory
  • doom_loop

Defaults are permissive: most are allow, doom_loop and external_directory are ask; read is allow but .env / .env.* are deny by default.

The official config page also says "all operations are allowed by default, no explicit approval needed".

The approval UI offers once / always / reject. It can be overridden per agent.

Since v1.1.1 the legacy tools boolean config has been merged into permission.

Best for

For individuals and teams that need 75+ providers, TUI/headless server/desktop forms, and command-level permission checks. Not for newcomers who want zero-config pure GUI.

Permission design: asks before executing

This is the single most notable line in this entry, from the README:

Asks permission before running bash commands

Most terminal agents execute commands automatically by default; OpenCode asks.

This lowers the risk of "the model deleting files / running dangerous commands by mistake", at the cost of interrupting the flow. The README also mentions YOLO, likely an optional no-ask mode, but the exact switch was not verified the 2026-10-08 pass — recorded as unknown.

A built-in general subagent for complex searches and multistep tasks. This lets it handle "investigate first, then act" style tasks that need multiple rounds.

ACP: Agent Client Protocol

This is its architectural highlight:

ACP load/restore/fork preserves model, effort and mode boundaries (translated from the dossier's Chinese paraphrase)

"Preserving model and effort across forks" is a detail worth noting — many tools lose settings after a fork, forcing you to re-set them every time.
