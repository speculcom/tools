Google's official open-source terminal agent — npx, no install required. Explicit MCP support, plus a non-interactive script mode.

When to use it, when not to

Three scenarios fit:

  • You want a quick trial without installing anything (npx leaves no install footprint)
  • You need MCP extensions, especially wiring Gemini's multimodal generation (Imagen / Veo / Lyria) into an agent workflow
  • You need scripted non-interactive runs, for example in CI

Three kinds of people also fit:

  • Anyone who needs a large context window — 1M tokens, one of the few in this track that states a limit
  • Anyone who needs a revert guarantee — shadow Git checkpoints plus /restore
  • Anyone who needs a project-level long-term instruction file — GEMINI.md

Not a fit for treating quota as unlimited. The free tier has clear daily limits: 6,000 code requests + 240 chats/day. And CLI and agent-mode quota are counted together.

Model & openness

Uses Google's own Gemini family; models can be switched. The context ceiling is explicitly stated as 1M tokens.

README first-screen wording: "Powerful Gemini 3 models: Access to improved reasoning and 1M token context window"

Switching models: specify via gemini -m gemini-2.5-flash on the command line. When signing in with a Gemini API Key, the official description is:

"Model selection: Choose specific Gemini models"

Three access modes (README "Authentication Options"):

  • Google account OAuth login — the free tier uses this: 60 requests/min, 1,000 requests/day, no key to manage
  • Gemini API Key — get a key in AI Studio, pay per usage
  • Vertex AI — for enterprises, requires a project and region

Model routing: Plan Mode can use general.plan.modelRouting. It switches automatically between Pro (planning) and Flash (implementation). There is also experimental Local Model Routing (Gemma).

The exact list of switchable models on the CLI side and their version mapping: the official docs do not give a complete list. (Repository docs and the reference/configuration page both checked.)

Where it runs

A local process, running in the terminal, launchable without installation via npx.

The official docs make "no installation" a first-screen selling point of the repository — this is how it lowers the entry barrier.

README wording: "Using npx (no installation required)"

Local files

Built-in file tools default to the workspace as root, with a clear boundary.

Official "File system tools" page wording: All file system tools operate within a rootDirectory (the current working directory or workspace root) for security

Tool set:

  • list_directory
  • read_file — supports text / images / audio / PDF
  • write_file
  • replace
  • glob
  • grep_search

Which ones need your nod to act:

  • write_file and replace — officially marked "Requires manual user approval"

Extending directories: launch with gemini --include-directories ../lib,../docs. Within a session use /directory add <path> (disabled under restricted sandbox configs).

Ignore boundary: respects .gitignore, and supports .geminiignore with the same syntax.

Changes are revertible: when you approve a file-changing tool, the CLI commits a snapshot. It lands in a shadow Git repository, not interfering with your own project repo. /restore reverts.

The repo location recorded on the checkpointing page: ~/.gemini/history/<project_hash>

Original wording: "It does not interfere with your own project's Git repository"

The semantic-indexing (Code Customization / RAG) algorithm and large-repo time cost are not stated officially. (file-system and configuration pages checked; only debug switches like general.logRagSnippets exist.)

Tasks after shutdown

A local CLI; it cannot keep running after shutdown.

Non-interactive / headless is scripting, not background. It still runs on your own machine.

Official "Headless mode" page wording: "Headless mode provides a programmatic interface to Gemini CLI... without an interactive terminal UI"

Triggers:

  • non-TTY environments
  • -p/--prompt

Output can be JSON or stream-json for CI and automation to consume.

The execution environment is yours: the official docs provide no vendor-hosted resident execution environment. The GitHub Action in the repository also runs on your repo's CI runners.

Interruption is recoverable: checkpointing and /chat save / /resume can save and restore sessions. The switch is general.checkpointing.enabled. general.sessionRetention defaults to 30 days. Expired sessions are cleaned up automatically.

Quota is exactly the daily request ceilings in the official usage policy. The official docs set no separate cloud quota.

Tools & extensions

MCP is explicitly supported and is one of its headline features.

README wording: "🔌 Extensible: MCP (Model Context Protocol) support for custom capabilities"

MCP has its own docs page: /docs/tools/mcp-server. The example it gives is using MCP to connect multimodal generation:

"Use MCP servers to connect new capabilities, including media generation with Imagen, Veo or Lyria"

This example deserves its own note: here MCP is not just connecting tools, it can also connect Google's multimodal generation capabilities (image / video / audio). This usage is not emphasized on the first screen of other CLI tools' repositories.

Built-in tool list:

  • Google Search grounding
  • shell

There is also non-interactive mode for script automation. The official docs have a dedicated section "Non-interactive mode for scripts".

Context & memory

1M-token context + layered GEMINI.md context + automatic history compression — all three have dedicated official pages.

Context window: the README first screen says Gemini 3 models with 1M token context window.

Context layers (official "GEMINI.md" page):

  • ① global ~/.gemini/GEMINI.md
  • ② GEMINI.md in workspace directories and their parents
  • ③ JIT — when a tool accesses a directory, it scans that directory's and its ancestors' GEMINI.md (up to the trusted root)

The file name can be changed via context.fileName (e.g. AGENTS.md / CONTEXT.md).

GEMINI.md page: supports imports via @file.md syntax. /memory show and /memory reload inspect and reload.

Compaction strategy verified (official core page):

"When a conversation approaches the token limit... the core automatically compresses the conversation history"

The threshold is controlled by model.compressionThreshold. The default is 0.5. You can also /compress to manually replace the whole context with a summary.

Cross-session memory: the official Memory tool writes durable facts into GEMINI.md (project / global two levels), injected into later sessions via the layered context. Token caching is only available to API key / Vertex users.

Permissions & limits

Sandbox, approvals and trusted folders each have dedicated official pages — the most finely documented permission surface in this section.

Sandbox: the official "Sandboxing" page gives these mechanisms.

  • macOS Seatbelt — default profile permissive-open: deny by default, writes limited to the project directory, but reads and network allowed
  • Docker / Podman
  • native Windows
  • gVisor / runsc
  • LXC / LXD (experimental)

Enabling:

  • -s/--sandbox
  • GEMINI_SANDBOX
  • tools.sandbox

Tool-level additionally has security.toolSandboxing.

Sandbox expansion: when a command fails due to permission limits, a "Sandbox Expansion Request" pops up. Approving case by case relaxes it temporarily. Out-of-bounds directories can be mounted via SANDBOX_MOUNTS.

Approval modes (configuration page): general.defaultApprovalMode has three values:

  • default — ask each time
  • auto_edit
  • plan — read-only

--yolo (auto-approve everything) can only be enabled on the command line.

Policy engine ("Policy engine" page): ~/.gemini/policies/*.toml defines allow / deny / ask_user via rules. Match conditions can key on tool name, arguments, approval mode, and interactive / non-interactive environment. Rules have four tiers: Default / Extension / User / Admin. Admin can force-override.

Trusted Folders: off by default. The switch is security.folderTrust.enabled. When untrusted it enters safe mode — ignoring workspace .gemini/settings.json and .env, disabling tool auto-accept, not connecting MCP, not loading custom commands. To bypass in CI there are two routes:

  • --skip-trust
  • GEMINI_CLI_TRUST_WORKSPACE=true

The configuration page also has an environment-variable redaction section.

Two things worth noting separately

① Checkpoints use shadow Git, not polluting your repo

When you approve a file-changing tool (write_file / replace), the CLI commits a snapshot.

  • the snapshot repo lives at ~/.gemini/history/<project_hash>
  • it is a separate Git repository; it will not touch your project repo
  • to revert, use /restore

The source is the checkpointing doc:

original wording: "It does not interfere with your own project's Git repository"

This is one of the few in this section that builds the "safety net" into the mechanism — most tools rely on "auto-committing into your repo" or "letting you undo yourself".

② GEMINI.md is the project-level standing instruction

It is like writing "how this project does things" into a file; multiple forms (CLI / VS Code / JetBrains) all read it. This is the same class of mechanism as Cline's .clinerules and Claude Code's CLAUDE.md — worth a cross-tool comparison.
