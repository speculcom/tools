Local files

Two features: coordinated changes across the project, and rollbackable checkpoints.

The README's "Edits Code Across Your Project" means: read the project structure, understand relationships between files, then make coordinated changes across the codebase.

While editing it watches linter and compiler errors, proactively fixing missing imports, type mismatches and syntax errors — the things that "go wrong without the user ever seeing them".

  • In VS Code and JetBrains, every edit is presented as a diff — reviewable, modifiable, rollbackable
  • all changes carry checkpoint records and can be undone wholesale
  • the official Checkpoints page explains it tracks changes with a shadow Git repository, not interfering with your main Git workflow, creating a checkpoint after each tool call

Read scope has two tiers: by default "Read project files" (inside the workspace); "Read all files" (outside the workspace) only takes effect after enabling a base toggle first. Project-level ignores are controlled by .clineignore (the official also shows a hook-enforced approach).

⚠ It has no "full semantic index" stage. The built-in search tool is a "Ripgrep-powered codebase search"; the official advice for large repos is "use search instead of reading many files", and to break tasks down smaller. (checked the Tools page and the Context Window Guide.)

Tasks after shutdown

Long-running processes and scheduled tasks are both supported.

Commands execute directly in the terminal with output visible in real time — installing packages, running builds, running tests, deploying, managing databases. For long-running processes like dev servers, Cline keeps working in the background and reacts to new output: compile errors, test failures and service crashes are caught as they happen.

The Desktop App form additionally has scheduled tasks (schedule routines):

  • cron scheduling for periodic automation
  • examples: daily PR summaries, weekly dependency checks, codebase health reports
  • schedules persist across restarts and run independently of any terminal session

The CLI's headless mode targets CI/CD.

Context & memory

The project-level rules file is .clinerules.

It defines project-specific rules: coding standards, architecture conventions, deployment flows, testing requirements. Rules are read automatically by the CLI, VS Code extension and JetBrains plugin. Skills can additionally let the model load specific rules on demand.

The Desktop form mentions "run agent sessions in any folder", i.e. cross-folder session management.

The context mechanism has been verified: near the limit, Auto Compact summarizes automatically. Window size is decided by the chosen model — the official lists Claude Sonnet 4.5 at 1M, GPT-5 at 400K, Gemini 2.5 Pro at 1M+.

Cross-session memory runs on the Memory Bank: a set of structured markdown files (projectbrief.md / productContext.md / activeContext.md / progress.md etc.) kept in the repo, with reads/writes driven by .clinerules instructions.

The official also has Focus Chain (todo injection) and /newtask, /smol for context handoff.

Permissions & limits

A two-level approval design — the finest on this site.

Level one is the Plan / Act dual mode. In Plan mode Cline explores the codebase, asks clarifying questions, and lays out a strategy; once aligned, switch to Act mode to execute the plan.

Level two is "every file edit and terminal command needs approval", switchable to auto-approve for autonomous running. The VS Code extension form's wording is "human-in-the-loop approval".

⚠ But the CLI / headless default is the opposite. This must be known (verified against the official CLI Overview and CLI Reference):

  • --auto-approve <boolean> defaults to true — i.e. tools are allowed by default
  • with --auto-approve false, every tool call needs approval first
  • --yolo skips all approvals
  • ACP (editor-integration) mode defaults to the opposite, false

Also: the CLI has no shell-command allow/deny list. The official suggests intercepting with a PreToolUse hook.

CLI prompt original wording: Default to start in act mode with auto-approve enabled VS Code extension wording: use tools with human-in-the-loop approval

Best for

Fits four kinds of people:

  • those needing one tool to cover editor, terminal and desktop work forms
  • those needing model choice (not bound to a single vendor)
  • those needing CI/CD integration (CLI headless)
  • those needing a "changes are reviewable and rollbackable" guarantee — diff presentation + wholesale checkpoint undo

Top misconception

  • Assuming it is a single-form VS Code extension — it actually has CLI, Desktop and extension
  • Overlooking headless mode — the CLI form supports CI/CD integration in its own right
  • Assuming approval behaves identically across forms: the extension explicitly has human-in-the-loop, but behaviour under CLI headless was not verified
  • Assuming auto-commit is by design — by default every edit needs approval, and auto-approve enables unattended runs

Permission design: explicit human approval

VS Code extension form, README original wording:

use tools with human-in-the-loop approval

This is a rare explicit statement in this category — most tools do not state on the README's first screen that tool execution needs human approval.

The CLI / headless approval stance has been verified (official CLI Overview and CLI Reference): the prompt says "Default to start in act mode with auto-approve enabled", --auto-approve <boolean> defaults to true — headless runs allow tools by default, --auto-approve false switches to approval before every tool call. --yolo skips all approvals. ACP (editor-integration) mode defaults to the opposite, false. Also: the CLI has no shell-command allow/deny list. The official suggests intercepting with a PreToolUse hook.

So "approvals are consistent across the three forms" does not hold: the extension form requires human approval by default, the CLI defaults to autonomous allowance — when crossing forms you must align explicitly via --auto-approve.

Two designs worth recording separately

① Plan / Act dual mode

In Plan mode it only explores the codebase, asks questions and lays out a strategy — it does not execute; it only acts after switching to Act once aligned. This is the mechanized implementation of "think it through before changing".

② Monitoring linter and compiler errors

README original wording:

It monitors linter and compiler errors as it works, fixing issues like missing imports, type mismatches, and syntax errors before you even see them.

It proactively fixes "type mismatches" and "missing imports" — which happens to be the hardest part to judge in this repository's measured task set, and is worth verifying on its own.
