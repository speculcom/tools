Amp is Sourcegraph's frontier coding agent, spanning CLI + cloud orbs + runners. Send a prompt and you can close your laptop while it keeps working. It routes across frontier models, with the Oracle as a second-opinion model.

When to use it, when not to

Four kinds of use fit:

  • People who want an agent that keeps working in a cloud orb after you close your laptop
  • Teams that need multi-model frontier routing plus the Oracle second-opinion model
  • People already working in a terminal or a VS Code-family editor who want IDE integration
  • Organisations needing enterprise controls (SSO, audit logs, MCP allowlists, zero data retention)

Not a fit for anyone who assumes tools are gated by approval — officially, "By default, Amp does not ask for approval before running tools". Approval takes a custom policy plugin that you write yourself.

Model & openness

Multi-model frontier routing — tiered per task rather than locked to a single model.

Official "Why Amp" wording:

"Multi-Model: GPT-5.6, Claude Fable 5, fast models—Amp uses them all, for what each model is best at."

The four Agent Modes are capability presets, not fixed model selectors: low / medium / high / ultra.

Official wording: "Modes are capability presets, not fixed model selectors"

Routing is customizable. It looks at connected provider subscriptions, workspace limits and model availability to decide how the main agent and the Oracle run.

The Oracle is a "second opinion" model.

At high, the main agent uses GPT-6 Astra (medium) and the Oracle uses Claude Fable 5.1. At low / medium / ultra, the Oracle defaults to GPT-6 Astra.

BYOK is now open across all tiers (official news notes: for all tiers since 2026-09-30).

Supported: OpenRouter, Bedrock, Google Cloud Agent Platform, Azure Foundry, Vercel / Cloudflare AI Gateway, Ollama Cloud, OpenCode Go and custom endpoint URLs, and ChatGPT subscriptions can be used too.

⚠ The official sources disagree. The security reference page still says:

Official wording: "Amp doesn't support Bring Your Own Key or self-hosted deployments"

This contradicts the BYOK stance on the pricing page / news; when citing, treat the pricing page as authoritative.

Where it runs

Hybrid: local Client + cloud Server. Threads can additionally run on three execution surfaces.

The official security reference splits Amp into two components.

Amp Client runs locally: code and context management, local settings, local thread history.

Amp Server is a multi-tenant cloud service on ampcode.com, hosted on GCP. It handles authentication, thread sync and LLM proxying.

Thread execution surfaces come in three: local, orb (a machine Amp creates for you in the cloud), runner (your own machine, amp --no-tui --runner-id <id>).

The CLI picks the execution location with --executor local|orb|runner:<id>.

There are also Web and macOS / iOS apps. The same agent, the same thread — usable everywhere.

Local files

The Client carries only local context; the official explicitly does not index the whole repo.

Official security reference wording:

"The Amp Client and Amp Server do not see, store, clone, or index the entire codebase"

It only sends the Server the code snippets / whole files selected as context (partial code data).

Tool side: Read / create_file / edit_file / glob / Grep / Bash etc.

IDE integration (VS Code, Cursor, Windsurf, Zed, Neovim): once connected, Amp can see the currently open file and selection. It can also edit files through your IDE, with full undo support.

Tasks after shutdown

There is a real background form — orbs.

Official homepage wording:

"Run agents anywhere and they keep working after you close your laptop"

Each thread gets an orb (already carrying your code, tools and plugins); it keeps running after shutdown and can be continued from your phone.

Runners live on your own machines: --share can share a runner with the workspace, so others can start threads on it from ampcode.com too (the machine must be on).

Scheduling and self-wake: the official manual has Schedules.

Tools & extensions

Built-in tools + subagents + plugins + MCP — all four layers have official pages.

Built-in tools: amp tools list shows Bash, Read, create_file, edit_file. Also glob, Grep, web_search, read_web_page, Task, todo_*, undo_edit.

Subagents / tools: oracle (second opinion for complex reasoning), Librarian (cross-repo retrieval. Can read all public GitHub code, and your private repos too), Painter (GPT Image generation and editing), Search, Read Thread.

Plugin system: you can write custom policy plugins (including a permissions plugin example). Custom agent modes and subagents are also possible.

MCP: local (amp.mcpServers, command / args / env, stdio) and remote definitions (stored on ampcode.com, url / headers).

Transports include SSE and Streamable.

Auth includes automatic OAuth, bearer, Amp ID token, Workload Identity.

The official recommends packaging MCP servers into skills (mcp.json) — that keeps the tool list lean.

Context & memory

Threads are the core unit — saveable, searchable, shareable.

Official "Why Amp" wording:

"Threads: You can save and share your interactions with Amp."

You can @-reference other threads (URL or @T-...). Past threads are searchable by keyword / file / repo / author / date. Workspaces support thread sharing and multiplayer.

AGENTS.md layering: the official lists cwd / parent directories / subtrees, $HOME/.config/amp/AGENTS.md, system-level /etc/ampcode/AGENTS.md and other layers. A subtree AGENTS.md is pulled in when files in that subtree are read.

It also supports @-mention and globs conditional loading, and gives migration paths from CLAUDE.md / .cursorrules.

Compaction: the official Models page lists Compaction as "Context summarization for long threads".

Permissions & limits

No approval by default — this is the point that most needs calling out.

Official Tools page wording:

"By default, Amp does not ask for approval before running tools."

The official alternative is custom policy plugins (distributable as workspace-level plugins).

Workspace MCP servers require explicit approval. Servers in .amp/settings.json show awaiting approval on first detection; you need amp mcp approve.

Global settings and those passed via --mcp-config do not.

The data side is fairly hard-nosed: the official auto-detects and redacts common secrets. (AWS / GCP / Azure, GitHub / GitLab, OpenAI / Anthropic, Stripe / Slack / npm etc., replaced with [REDACTED:amp]), but admits it is best-effort.

Thread data is stored on ampcode.com (GCP). Your data is not used for training by default (never enableable on Enterprise). After deleting a thread, data is removed within 30 days; Enterprise offers zero data retention (ZDR).

Subscriptions and BYOK quotas are two different things. With your own key or subscription, there is no Amp token fee.

Best for

  • teams needing multi-model frontier routing + an Oracle second opinion
  • people already working in the terminal or VS Code-family editors who want IDE hookup along the way
  • organizations needing enterprise controls (SSO, audit logs, MCP allowlist, zero data retention)

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Assuming tools run only after approval — officially, Amp does not ask for approval before running tools.
  • Expecting a standalone VS Code extension — integration is via the CLI and ide connect (VS Code / Cursor / Windsurf / Zed / Neovim).
  • Treating $20/mo as the whole cost — orbs are billed by the minute and overage is charged against credits.
