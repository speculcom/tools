TabbyAPI: the official API backend server for ExLlamaV3 (AGPL-3.0, 1,502 stars, pushed 2026-10-30) — a FastAPI local inference server with OpenAI-compatible endpoints and official GHCR images covering CUDA 12.8/13 and AMD ROCm. Two hard wordings: the README's official warning says "the ONLY official source for TabbyAPI information is this repository" — tabbyapi.com is actually unofficial; rolling release with zero GitHub releases — the change-record line is commits.

Model & openness

The official API backend for ExLlamaV3 — the README says "TabbyAPI is also the official API backend server for Exllamav3": it runs local weights supported by ExLlamaV3 (the exllamav3 backend) such as GPTQ/GGUF, not a service calling an external model. Model files live in a local directory mounted into the process (Docker wording: mount the models directory into the container).

Where it runs

A FastAPI local server (Python 3.10–3.14); the official CUDA image is on GHCR (ghcr.io/theroyallab/tabbyapi), tags latest (CUDA 12.8)/cu13/latest-rocm (AMD RX 7900 series)/latest-extras (with the optional embeddings stack). GitHub theroyallab/tabbyAPI AGPL-3.0 1,502 stars, pushed 2026-10-30 (API verified); GitHub releases count is 0 — releases follow a rolling-release model (README self-description); the change-record line is commits.

Local files

Reads and writes local files — the model-weights directory, config.yml; the API defaults to localhost:5000.

Tasks after shutdown

A persistent local process (FastAPI server); no persistent cloud surface. The README disclaimer self-describes it as a "hobby project…not meant to run on production servers" — for production workloads the official advice is to look elsewhere.

Tools & extensions

An OpenAI-compatible API surface (chat/completions and similar endpoints) + an admin surface (admin UI/status page; admin features visible evolving in commits); not an agent-tool host — it is an inference-API server for frontends (SillyTavern-style) or clients.

Context & memory

No cross-session memory (it is an inference-serving surface) — context length follows the ExLlamaV3 backend config (max_context-style parameters); conversation state is carried by the frontend client (SillyTavern-style); the server stores no chat history.

Permissions & limits

Runs locally; an API key can be configured (config.yml); the permission surface = local files and GPU. The Docker wording requires a larger --shm-size (ExLlamaV3 uses POSIX shared memory for tensor parallelism and CPU MoE offload; the 64 MiB default is not enough — stated plainly in the README).

Best for

Fits: the ExLlamaV3 ecosystem (GPTQ-family quantization) wanting an OpenAI-compatible API — the standard answer; one-shot Docker CUDA/ROCm inference servers. Does not fit: production-grade serving (officially self-described as not production-oriented — that is the vLLM/TGI line); broad GGUF quant coverage (the llama.cpp root).

Top misconception

  • Waiting for GitHub releases — releases count is 0; it is a rolling release, watch commits and the Wiki
  • Using it as a production server — the README disclaimer plainly says hobby project, not production-oriented
  • Forgetting --shm-size in Docker — ExLlamaV3 tensor parallelism/MoE offload uses shared memory; the 64 MiB default breaks (the README says to keep the flag)
