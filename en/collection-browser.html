Let an agent drive a browser: which layer does what

A browser agent is often sold as one product, but it is four layers: browser runtime (sessions, cookies, proxies), page understanding (DOM / vision / accessibility tree), action execution (click, type, wait) and audit (screenshots, logs, replay). This page maps each layer to an existing entry.

This is a “who owns which layer” collection, not a duplicate of product dossiers; open an entry for its eight axes, sources and boundaries.

Which layer does what

LayerExisting entries

Playwright: deterministic scripts and selectors
Chrome DevTools MCP: performance, network, debugging
Fetch and searchFirecrawl MCP: crawl, search, browser interaction
Always-on orchestrationHermes Agent: always-on, approvals, cross-platform messaging

Minimum working order

  1. Run one site with a deterministic script first; confirm selectors, waits and error pages
  2. Then let the model choose the element, keeping screenshots and an action log
  3. Finally add session isolation, proxies and human approval; never share a browser session across logins

Boundary

The sites have not run a success-rate comparison across browser agents on the same site; success depends heavily on site changes, anti-bot measures and login state, so re-run on your target site. For accounts, payments and personal data, confirm the terms and authorisation first; do not use an agent to bypass CAPTCHAs or access controls.
