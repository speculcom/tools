What it is, in one line: Google ADK is a "code-first agent orchestration framework whose core asset is a graph execution engine". It organises several agents into one flow; it does not run a single agent for you.

The official README states its identity in the first feature it lists:

Workflow Runtime: A graph-based execution engine for composing deterministic execution flows for agentic apps, with support for routing, fan-out/fan-in, loops, retry, state management, dynamic nodes, human-in-the-loop, and nested workflows.

When to use it, when not to

Fits: organising multiple agents into deterministic flows with branches, loops and human intervention; defining agents and tools code-first so they are testable and versionable; a team inside the Google ecosystem (Cloud Run / Vertex / Gemini); needing built-in eval and a development UI; wanting one framework across Python and TypeScript; needing tool-level human confirmation, session persistence and resume. Not a fit: running a single agent with no graph structure (OpenAI Agents SDK or Deep Agents are lighter); needing built-in file- or network-sandbox boundaries — the official docs provide none, so file access goes through the Artifacts abstraction or a tool you wire up yourself; wanting self-hosted weights out of the box without going through the LiteLLM adaptor layer.

Model & openness

Official line: optimized for Gemini, but it is also model-agnostic.

README verbatim: "While optimized for Gemini, ADK is model-agnostic, deployment-agnostic, and compatible with other frameworks."

So non-Gemini models can be connected. The official "Models for Agents" page gives three integration mechanisms:

  • ① direct string / registry — Gemini, Claude, Agent Platform hosted models
  • ② model connectors — LiteLlm / ApigeeLlm wrapper classes
  • ③ model routing — runtime dynamic model selection + automatic failover

Official wording: "providing a standardized, OpenAI-compatible interface to over 100+ LLMs"

Local / self-hosted models have dedicated official pages: Ollama, vLLM, LiteRT-LM.

⚠ Not stated officially: what "optimized for Gemini" actually optimizes.

⚠ Nor is there a reliability comparison of tool calling and structured output under non-Gemini models. Checked: the Models page and the LiteLLM page.

Where it runs

Four run forms, all provided by the adk CLI or containers (README verified).

  • ① interactive CLI — adk run <agent-folder>
  • ② built-in Web UI — adk web <agent-folder>. The official docs state support for multi-agent directories or pointing directly at a single agent folder
  • ③ Development UI — the built-in development/debug console
  • ④ containerized deployment — adk deploy docker --with_ui <agent-folder>

Official wording: "A built-in development UI to help you test, evaluate, debug, and showcase your agent(s)"

⚠ All four are your local or your cloud processes. ADK itself provides no hosted service.

Hosting requires Vertex AI Agent Engine or Cloud Run — those are Google products, not this framework's.

Local files

The official answer to "files" is the abstraction layer Artifacts, not the raw filesystem (verified on 2026-10-08). In other words, it does not read or write disks itself.

Official Artifacts page verbatim:

Official wording: Artifacts "represent a crucial mechanism for managing named, versioned binary data associated either with a specific user interaction session or persistently with a user"

Where things land is decided by the ArtifactService you choose. Official wording: "Their storage and retrieval are managed by a dedicated Artifact Service"

Two backends:

  • InMemoryArtifactService — lost on restart
  • GcsArtifactService — persistent, versioned

ADK is a library; it does not ship Read/Write/Bash style file tools. Disk access means writing your own function tool, or connecting MCP. The official MCP page example is exactly a filesystem MCP server.

⚠ Not provided officially: any sandbox mechanism or filesystem permission model (Artifacts, tools, deploy pages checked). The default access boundary depends on whatever tools you connect.

Tasks after shutdown

It does not host a background. The official docs give two explicit pieces of evidence: session/state persistence, and resume-after-interruption.

① Persistence — SessionService comes in three tiers:

  • InMemorySessionService — official wording: "All conversation data is lost if the application restarts"
  • DatabaseSessionService — "Data survives application restarts"
  • VertexAiSessionService — hosted

MemoryService separately has InMemory and Vertex AI Memory Bank tiers.

② Resume — ADK Python 1.16+ can configure an App with ResumabilityConfig(is_resumable=True).

Official verbatim:

Official wording: "allows an agent workflow to pick up where it left off"

Resume by Invocation ID. Works via /run_sse or runner.run_async.

ADK itself is a library and hosts nothing. A true background means deploying to Cloud Run / Vertex AI Agent Engine — that is your cloud resource.

⚠ Two official boundaries:

  • Resume is currently "not currently supported" triggered from the Web UI / CLI
  • tools may be re-executed (the official docs remind: side-effectful tools need your own dedup)
Tools & extensions

The tool ecosystem is what it emphasizes most, and MCP is a first-class capability in the official docs.

README verbatim:

"Utilize pre-built tools, custom functions, OpenAPI specs, MCP tools or integrate existing tools"

There is also a dedicated MCP tools documentation page. It provides the McpToolset class, and it is bidirectional:

  • let ADK act as an MCP client, connecting external MCP servers (examples include filesystem / Google Maps MCP servers)
  • ADK tools can also be wrapped as an MCP server and exposed outward
  • transports cover stdio and Streamable HTTP

Tool-level human confirmation (HITL) Official wording: "a tool confirmation flow (HITL) that can guard tool execution with explicit confirmation and custom input"

Corresponding doc tools/confirmation. Mechanism details in the permissions axis.

This is a rare "tool-level human confirmation" among objects collected on this site. It is a different layer from the OpenAI Agents SDK's input/output guardrail.

Context & memory

The official docs draw a clear distinction among session / memory, and there is a dedicated context-compaction feature.

Three sentences on the official sessions page, official wording: Session is "single, ongoing interaction", State is "data within the current conversation", Memory is "searchable, cross-session information"

The first two are managed by SessionService. Long-term knowledge is managed by MemoryService.

Compaction: ADK Python 1.16.0+ provides Context Compaction. Official wording: "reduce the size of context as an agent is running by summarizing older parts of the agent workflow event history"

The mechanism is a sliding window:

  • configure EventsCompactionConfig(compaction_interval, overlap_size)
  • at the threshold, earlier events get summarized
  • summarizer can swap models

⚠ Per this site's "state ≠ context": state governs flow data. Compaction governs history compression. These are two mechanisms, and the official docs describe them separately.

Permissions & limits

The officially explicit mechanism is tool-level human confirmation, Tool Confirmation (HITL).

Doc tools/confirmation (since v1.14.0, labeled Experimental) official wording: "allows an ADK Tool to pause its execution and interact with a user or other system for confirmation"

Two usage styles verified.

  • ① simple confirmation — FunctionTool(..., require_confirmation=True) asks once yes/no; you can also pass a function returning a boolean (e.g. "only ask when amount > 1000")
  • ② advanced confirmation — tool_context.request_confirmation(hint, payload). Can pause the tool, collect structured data (e.g. approval days) and then resume

Without a UI, the ADK server's /run or /run_sse REST endpoints allow remote confirmation.

This is only "ask before executing", not boundary-setting. The official docs provide no sandbox or filesystem permission model. Checked: confirmation, Artifacts, deploy pages.

⚠ Official known limitation: DatabaseSessionService and VertexAiSessionService do not support this feature.

Top misconception

  • Assuming it is "Google's version of the OpenAI Agents SDK" — it is an orchestration framework whose core asset is the Workflow Runtime graph engine, not single-agent primitives
  • Reading state management as "has context management" — the former is process state; the latter is the separate Context Compaction mechanism (1.16+)
  • Treating MCP as a core dependency — the README lists MCP only as one tool source, which is not the same as OpenAI Agents SDK putting mcp>=1.19.0 in dependencies
  • Assuming Tool Confirmation equals a sandbox — it is "ask once before running", not a boundary
  • Assuming open source and free means zero cost — Cloud Run / Vertex Agent Engine costs are yours, and there is a GOOGLE_GENAI_USE_ENTERPRISE switch
  • Assuming it is Python-only — there is a separate TypeScript repo (google/adk-js, 1,426★); the Python body is the only thing indexed here
  • Mixing up repo names — the sample repo shows as google/adk-recipes while the description says adk-samples

Why it is classified as orchestration rather than coding-base

This site's first four coding bases are the OpenAI Agents SDK, Deep Agents, Claude Agent SDK, Codex SDK.

They all answer the same question:

how do you run one agent?

ADK answers a different question:

how do you organize multiple agents into a flow with branching, loops and human intervention?

The keyword is deterministic: what it sets out to solve is not "whether an agent can work". (deterministic means "certainty".)

What it sets out to solve is whether a flow composed of multiple agents is repeatable and predictable across runs.

This lands directly on the distinction this site cares about:

The surface this site watchesWhat ADK gives
state (flow control)✅ graph execution engine: routing / loops / retry / state management / nested workflows
context (long-task compression)✅ Context Compaction since 1.16+: sliding-window summarization of earlier events (EventsCompactionConfig(compaction_interval, overlap_size)), summarizer swappable

This is a rare "tool-level human confirmation" among objects collected on this site. input/output guardrails are a different layer from it:

  • guardrails validate content (is this input / output compliant)
  • tool confirmation gates execution (should this tool really run, optionally with custom input)

Deployment: four commands, from local to Google cloud

All four run/deployment forms given by the README are verified:

adk run <agent-folder>              # interactive CLI
adk web                <agent-folder>       # built-in Web UI
adk deploy docker   --with_ui <agent-folder>         # containerized
adk deploy cloud_run --with_ui <agent-folder>        # Cloud Run

Two more points this site considers notable.

① Built-in development UI and built-in eval.

Official wording:

A built-in development UI to help you test, evaluate, debug, and showcase your agent(s)

There is also the adk eval <agent-folder> <evalset.json> command and the .evalset.json config format.

This is the only object collected on this site that makes "evaluation" a framework-built-in command. Against the "no measured runs" rule, this kind of capability deserves a note: it lets users run their own evaluations.

② There is a deployment-level switch to note, and it is essentially a "billing-path switch."

The README's Cloud Run example contains GOOGLE_GENAI_USE_ENTERPRISE=1.

Verified clearly the 2026-10-08 check (2026-10-01, Google's official codelab and Cloud docs): it is not a switch that "unlocks enterprise features".

It is a routing switch: moving requests from the Gemini Developer API to the Google Cloud enterprise platform (Gemini Enterprise Agent Platform / Vertex AI), and the billing basis changes with it.

In other words, what changes is where requests go, not feature entitlements.

The official codelab's explanation of the three variables, verbatim:

VariableOfficial meaning
GOOGLE_GENAI_USE_ENTERPRISE"This tells the ADK that you intend to use Google's Gemini Enterprise Agent Platform service for your Generative AI operations."
GOOGLE_CLOUD_PROJECT"ADK needs this to correctly associate your agent with your cloud resources and enable billing."
GOOGLE_CLOUD_LOCATIONregion, e.g. global

The single most important line.

The official docs write "enable billing" explicitly against GOOGLE_CLOUD_PROJECT.

Set all three variables together and the agent lands in your Google Cloud project and starts billing. Unset, it goes the Gemini Developer API route (which has its own free tier and quotas).

Two more points worth recording:

  • the three variables must appear as a group — every official example (README, codelab, the Cloud docs' Live API guide) sets all three; there is no set-one-only style
  • values are inconsistent — the README and codelab .env files write 1, the Cloud docs write TRUE or True. All are truthy by boolean semantics, but the official inconsistency itself is worth noting
⚠ Still unverified: Gemini's specific unit prices. And the actual rates of Vertex AI Agent Engine and Cloud Run.
