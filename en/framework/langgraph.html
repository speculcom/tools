LangGraph is a low-level orchestration framework for building stateful agents.

The official description is deliberately modest — note that word, low-level:

Low-level orchestration framework for building stateful agents.

It does not claim to be a batteries-included high-level wrapper. It lays the groundwork for long-running, stateful work.

When to use it, when not to

Fits: agent flows that run long and must resume precisely from an interruption; a human stepping into the middle of a flow to change state; managing working memory and cross-session memory separately; an explicit graph structure (branches, loops, subgraphs); teams on Python. Not a fit: needing built-in sandboxing or file-level permission boundaries (official docs do not provide such a mechanism — checked the README and the interrupts page); wanting a filesystem and sub-agents out of the box (go with Deep Agents, the higher-level package built on LangGraph); not wanting an extra dependency on the LangChain ecosystem — model access usually goes through it.

Model & openness

LangGraph does not touch models at all — a design stance of a low-level framework.

The five capabilities in the official self-description are durable execution / HITL / memory / LangSmith debugging / production deployment. All five are model-agnostic; nowhere is a provider listed. The official overview files "models" under LangChain:

Official wording: "starting with models and tools"

The official overview also states:

Official wording: "LangGraph does not abstract prompts or architecture."

Models usually connect via the LangChain integration layer (init_chat_model or any SDK). But the official docs explicitly say it

Official wording: "can be used without LangChain"

This line is at the end of the official homepage — not a hard binding.

The official docs provide no provider list — models are simply outside its remit. Neither the overview nor the official homepage lists one.

⚠ Our judgment: it is not model-bound, and the official homepage has no provider list.

Where it runs

The OSS form is a pure library — no runtime service.

Installation is just pip install -U langgraph. No CLI to start a service, no container orchestration, no Web UI (the Web UI lives on the Deep Agents / LangSmith side).

Production deployment points to LangSmith Deployment in the official docs. The official overview links "Production-ready deployment" to LangSmith Deployment. That page defines it as:

Official wording: "a workflow orchestration runtime purpose-built for agent workloads"

It comes with langgraph deploy. Environments come in four tiers: Cloud / Hybrid / self-hosted K8s / Standalone Agent Server. Cloud requires the Plus tier or above.

In other words, hosted execution sits at the commercial-platform layer; OSS itself only covers "you run the process yourself".

Local files

⚠ The file system is outside LangGraph's remit.

The only place the official homepage mentions file systems is recommending Deep Agents as the higher-level package:

Official wording: "leverage file systems for complex tasks"

In other words, file capability is filed under the higher-level wrapper, not the low-level graph engine.

What LangGraph itself provides is a state container — checkpoints store graph state. Whether the agent reads/writes disks, and with which tools, is not its business.

Our judgment (inference): if you want a file system, wire your own tools. Or go up to the Deep Agents layer.

Tasks after shutdown

This is its strongest dimension, with explicit official wording.

The first feature, Durable execution, reads verbatim:

Build agents that persist through failures and can run for extended periods, automatically resuming from exactly where they left off.

The companion is the standalone subpackage langgraph-checkpoint. Check libs/checkpoint — the first paragraph of that subpackage's page:

Checkpointers provide a persistence layer for LangGraph: they save graph state at every superstep, enabling human-in-the-loop, memory between interactions, durable execution, and more.

The persistence granularity is the superstep (one graph step) —

not "at session end", not "after each turn"

The official docs give three persistence backends (persistence page):

  • InMemorySaver — stored in RAM; the wording says it "does not persist between restarts"
  • SqliteSaver — local file, for development
  • PostgresSaver — production; the wording is "In production, use a checkpointer backed by a database"

There are also langgraph-checkpoint-* implementations for MongoDB / Redis / Oracle.

Cross-process recovery relies on the database + the same thread_id. The official durable-execution page says you can Official wording: "resume workflows from the last successful checkpoint"

langgraph>=1.2 also adds SIGTERM graceful shutdown (drain, then persist a resumable checkpoint).

Unknown: conflict semantics of multiple processes writing the same thread concurrently — the official docs do not state it. ⚠ Neither the persistence nor the checkpointers pages cover this.

Tools & extensions

The LangGraph core contains no tool system, but the official ecosystem has a unified MCP access package.

None of the five official capabilities is a tool system. Tools connect via the LangChain ecosystem, or your own functions — LangGraph handles the graph and state; tools come from LangChain or your functions.

MCP: the official docs provide langchain-mcp-adapters (the langchain-ai org). The official homepage says of it

Official wording: "makes MCP tools compatible with LangChain and LangGraph"

and Official wording: "Convert MCP tools into LangChain tools that can be used with LangGraph agents"

Multiple MCP servers can be connected. This is the LangChain ecosystem's unified MCP access layer.

Note it is a standalone package (pip install langchain-mcp-adapters), not part of the langgraph core.

Context & memory

LangGraph splits "state" and "memory" into two mechanisms, both with official wording.

The third feature, Comprehensive memory, reads verbatim:

Create truly stateful agents with both short-term working memory for ongoing reasoning and long-term persistent memory across sessions.

Short-term memory: the official add-memory page gives three trimming techniques — Trim messages / Delete messages / Summarize messages. These three are how short context is managed: trim, delete, summarize. The page positions them as:

Official wording: "techniques to manually remove or forget stale information"

Long-term memory: a store holding JSON documents. The official docs say it supports semantic search and content filtering:

Official wording: "supports both semantic search and filtering by content"

It can recall across threads.

Unknown: "large tool outputs spilled to disk" — the official docs do not say LangGraph provides it. ⚠ Neither the memory nor add-memory pages do — that is the higher-level Deep Agents' context-management capability.

Permissions & limits

What the official docs give is human-in-the-loop. It is at the "inspect and modify state" level, not just confirmation.

The second feature, Human-in-the-loop, reads verbatim:

Seamlessly incorporate human oversight by inspecting and modifying agent state at any point during execution.

The docs are at langgraph/interrupts.

Compared with other listed objects, this point differs substantively. The three intervention levels escalate; listed inline because this parser does not support lists inside nested blocks:

  • OpenAI Agents SDK guardrails validate content (are inputs/outputs compliant)
  • Google ADK Tool Confirmation intercepts execution (should this tool run)
  • LangGraph interrupts modify state (inspect and modify graph state at any execution point)

⚠ But say clearly: what it explicitly does not give is a sandbox or permission boundary. The official docs mention no file-system permission model, network access control, or tool-level allowlist. Contrast with OpenHands on our site, which has an explicit Docker sandbox + API-key mechanism. Also contrast with the Codex SDK (three SandboxMode enum values in source). On this dimension, no official mechanism can currently be found for LangGraph.

Best for

Four scenarios it fits.

  • Agent flows that run long and must resume precisely from the interruption point
  • Human intervention mid-flow that modifies state
  • Managing "working memory" and "cross-session long-term memory" separately
  • You need an explicit graph structure (branches, loops, subgraphs); your team uses Python

Three scenarios it does not fit.

  • You need a built-in sandbox or file-level permission boundary — the official docs provide no such mechanism (README and interrupts page checked)
  • You want batteries-included file system and subagents — go to Deep Agents, the higher-level package on LangGraph
  • You don't want an extra dependency on the LangChain ecosystem — model access usually goes through it

Top misconception

  • Treating Deep Agents and LangGraph as two competitors — Deep Agents is a higher-level package built on LangGraph (the README says so)
  • Using releases/latest to judge the version — latest on a monorepo is unreliable: on this entry latest returned cli==0.4.32.dev0 (a sub-package dev build); the main package version has to be picked out of the release list (1.2.12 at the time of this check)
  • Reading checkpoint persistence as "context management" — a checkpoint stores graph state; context compression and memory are a separate layer the README calls memory
  • Assuming it ships a filesystem or a tool system — it handles neither; wire up your own, or go through Deep Agents
  • Assuming interrupts are a permission guardrail — they "check and modify state"; they do not draw file or network boundaries
  • Assuming that installing LangGraph is enough — the official front page points you at LangSmith for debugging and deployment, and that is a commercial product

Its answer on "state" is the most serious

Our core claim is "state ≠ context". LangGraph is the only listed object that spells this distinction out on its official homepage.

Durable execution: persistence granularity is the superstep

The first feature is called Durable execution:

Build agents that persist through failures and can run for extended periods, automatically resuming from exactly where they left off.

"exactly where they left off" is the key. Not restarting from scratch — continuing from the interrupted step.

The persistence mechanism lives in the standalone subpackage langgraph-checkpoint. Check libs/checkpoint — the first paragraph of that subpackage's page:

Checkpointers provide a persistence layer for LangGraph: they save graph state at every superstep, enabling human-in-the-loop, memory between interactions, durable execution, and more.

⚠ This is the clearest official definition of "state persistence" we have seen. The granularity is the superstep (one graph step) — not "at session end", not "after each turn". How we record this granularity: persistence granularity is the superstep (one graph step). It is not "at session end". Nor is it "after each turn".

⚠ But honestly: conflict semantics of cross-machine / multi-process concurrent writes to the same thread are not stated by the official docs. The persistence document only gives database backends and durability modes (verified 2026-10-08).

State and memory: it splits them into two mechanisms

The third feature is called Comprehensive memory:

Create truly stateful agents with both short-term working memory for ongoing reasoning and long-term persistent memory across sessions.

The distinction between two time scales is precisely an isomorphic expression of our claim:

  • checkpoint → stores flow state (state plane)
  • memory → a separate layer, split into working memory and cross-session long-term memory (memory plane)

⚠ The point we most want to stress: do not read checkpoint persistence as "context management". Checkpoints store graph state. How long context gets trimmed is the memory layer's business. The two are strictly recorded apart on this page — which is how the v3 rule "state ≠ context" lands.

⚠ Three items we have not verified:

  • exactly how short-term memory trims context (is it compression/summarization?)
  • the storage backend and retrieval method of long-term memory
  • whether "large tool outputs spilled to disk", which we care about, falls within its capability

Selection must-read: it and Deep Agents are layers, not two options

This is a relationship we must untangle for readers, or they will double-count.

The official homepage's first screen carries a TIP pointing to Deep Agents:

If you're looking to quickly build agents, check out Deep Agents — a higher-level package built on LangGraph for agents that can plan, use subagents, and leverage file systems for complex tasks.

In other words: Deep Agents is a higher-level package built on LangGraph.

"can be used without LangChain". This line is our key evidence that it is not hard-bound. Model access usually goes through LangChain, but you can skip it.
