8 questions, one table

8 questions, each comparable item by item with its peers.

Model & openness

Plugin-style multi-model access (each vendor's API and local lines have plugins; the catalog follows the official Plugin Registry); its core is not the model but the "character" abstraction — one agent configuration file defines persona + capabilities.

Where it runs

A TypeScript runtime (official repo description: "Open source agentic operating system"): run a resident process, the agent connects to channels per its character config. GitHub elizaOS/eliza 19,739 stars, last push 2026-10-30 (API verified, active).

Local files

Self-hosted, running in your own process/machine; memory and state are persisted through the AgentRuntime memory/state API and IDatabaseAdapter (official Memory and State docs), with recent/vector/keyword retrieval; the concrete database backend follows the deployment adapter.

Tasks after shutdown

Resident process + multi-channel connection is the default form: the agent stays online long-term receiving messages and acting per its character — the "character agent" is the core of its product narrative.

Tools & extensions

The plugin ecosystem is the main axis (channel plugins / action plugins); MCP is supported through @elizaos/plugin-mcp (npm 2.0.5, updated 2026-11-11; maintained by Eliza core members) for MCP servers.

Context & memory

The character file defines persona and knowledge surface, shared across channels (official docs: Character Interface / Agent Configuration on record).

Permissions & limits

Plugins and actions can reach external accounts/channels — which channels to connect and which credentials to grant is the configurator's responsibility; third-party plugin code must be audited by you.

Best for

Fits: "a resident agent with a persona" (social/companion/community bots), the TS ecosystem, plugin-style extension. Does not fit: coding-task bases, enterprise workflow orchestration, scenarios sensitive to third-party plugin supply chains.
