It is a self-hosted control centre for agents — the official README now calls it Agent Canvas.

It ships as a whole stack: a web GUI, a terminal UI, a CLI and a REST API all live in it. And it drives more than its own agent — Codex, Claude Code and Gemini can all run on top of it.

Official positioning: The self-hosted developer control center for coding agents and automations. Run OpenHands, Claude Code, Codex, Gemini, or any ACP-compatible agent across local, remote, and cloud backends.

When to use it, when not to

What it is good for:

  • Running agents 7×24 on your own server
  • Scheduled or webhook triggers (Slack / GitHub / Linear / Notion)
  • Managing several agents from one interface, including ACP-compatible ones such as Codex, Claude Code and Gemini
  • Per-conversation container isolation
  • Deploying the front end separately from the agent runtime
  • Long sessions that need the official condenser to hold down context cost

What it is not for:

  • Embedding an agent into your own Python process — use software-agent-sdk or OpenAI Agents SDK for that
  • A one-off job on a single machine — it is a whole stack, not a library
  • Multi-user, fine-grained permissions — the official comparison table puts Multi-user RBAC in Enterprise, so OSS self-hosting has a single key only

Where it runs

It has four official deployment forms — the most practically valuable part of this object. All four README Options verified.

  • Option 1 local without sandbox: npm install -g @openhands/agent-canvas then agent-canvas, starts the full local stack, requires Node.js 24+ and uv; --frontend-only / --backend-only split it apart
  • Option 2 Docker sandbox: docker run the official image, requires preparing a PROJECTS_PATH host directory beforehand; the agent can access projects under it
  • Option 3 per-conversation containers: OH_CONVERSATION_RUNTIME=docker agent-canvas, each new conversation starts its own container and Agent Server — good for running multiple agents concurrently
  • Option 4 from source: clone + npm install + npm run dev

Entry URL: http://localhost:8000 (the Docker image serves /canvas).

Backends can be switched remotely — the core capability of its scheduling layer: officially the Agent Server can run on a laptop / Mac Mini / cloud VM / OpenHands Cloud, and the Canvas frontend switches between multiple Servers.

On Option 3 the official docs note containers mount the conversation's workspace and persisted state. Files and conversation history survive container replacement.

Local files

How much of the local file system is reachable depends on which deployment form you choose — the official docs make this variable explicit.

  • No-sandbox form: the agent has full file-system access; the official docs WARNING twice
  • Docker form: access narrows to the directory mounted at PROJECTS_PATH
  • Per-conversation container form: the official docs caution that conversations sharing the same host workspace still share the same files; use separate directories or worktrees to avoid conflicting edits
  • When the backend is remote (cloud VM / Cloud backend): the agent runs in a remote workspace; the SDK specifies the remote working directory with Workspace(host=..., working_dir="workspace/project"); file and command operations execute server-side

The official docs do not describe a mechanism for "auto-syncing a local repo to a remote backend" (agent-server and runtime pages checked) — the repo must already live remotely, or be moved by you.

Official WARNING, verbatim: "This runs the agent-server directly on the machine you're installing on — the agent will have full access to your filesystem!"

Context & memory

On context, the official docs have an explicit mechanism: the context condenser. Evidence for this dimension is complete.

The default implementation is LLMSummarizingCondenser (extends RollingCondenser), with parameters max_size / keep_first. Over threshold it keeps recent messages intact and only summarizes older content.

On the Canvas side the entry is Settings > Condenser; the LLM settings page has "Enable memory condensation" and "Memory condenser max history size" toggles.

The official docs also explain: with a condenser configured, exceeding the window emits a condensation-request event instead of throwing LLMContextWindowExceedError. The agent summarizes old history and continues.

⚠ Per our "state ≠ context" framing: run history and persistence across container replacement belong to the state side. The condenser above is the official context-side mechanism. Count them separately.

Official SDK guide, verbatim: the context condenser "intelligently summarizing older parts of the conversation while preserving essential information"; over threshold it "Keeps recent messages intact", "Summarizes older content".

Permissions & limits

This is where the official docs are most thorough — and the part that most deserves careful reading.

Sandbox: the official docs give two containment measures (see local_files): the Docker sandbox and per-conversation containers. But the official docs also explicitly offer the no-sandbox form, WARNING twice.

Authentication uses an API key, not a user system:

  • generate a key: openssl rand -base64 32, assign to LOCAL_BACKEND_API_KEY
  • in --public mode the key is not baked into the frontend; users must paste the key manually on first UI open; afterwards every /api/* request carries the X-Session-API-Key header
  • loopback-only binding by default (127.0.0.1). The official rationale: keep the auto-injected session key from being reachable by other machines on the LAN
  • when listening on 0.0.0.0 the key is no longer injected; the same API-key input UI is used instead
  • the official docs advise export over command-line arguments for the key, to keep it out of ps aux process listings
  • exposing to the public internet carries official firewall requirements (Cloud Firewall / AWS Security Group / GCP firewall rule)

⚠ Multi-user and permission tiers are assigned by the official docs to Enterprise. The official deployment comparison table shows the Open Source tier "Users = 1"; Multi-user RBAC and SSO/SAML exist only in Enterprise (the OSS column reads "—").

So OSS self-hosting includes no user/role/audit system — that session key is all there is. Multi-user tiering and auditing require Enterprise.

docs/SELF_HOSTING.md (verified, 286 lines) covers exactly this API-key mechanism.

Top misconception

  • Assuming it is a Python SDK — the main repo is a TypeScript web control centre; the programming entry point is OpenHands/software-agent-sdk (a further 1,190★)
  • Judging by the repo name and description that it is an "AI-driven software development tool" — the README's front-page title is now Agent Canvas, and the positioning is a control centre
  • Assuming it competes with Codex SDK / Claude Agent SDK — it is their orchestration layer (the README says it can run those agents)
  • Going straight to Option 1 in production — the official docs put a WARNING on that option: the agent has full access to your filesystem
  • Reading --public mode as "more convenient" — it is the safeguard that keeps the key out of the front end, meant for non-local access
  • Assuming "has run history" means "has context management" — the former is state; the latter has its own mechanism (LLMSummarizingCondenser / RollingCondenser)
  • Assuming it uses ACP only and does not support MCP — the MCP Servers page says both the CLI and the Canvas can configure it (http / sse / stdio plus Bearer / API Key / OAuth); ACP is the separate line for orchestrating third-party agents
