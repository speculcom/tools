Pydantic AI is the Python agent library from Pydantic. Its selling point is type safety. The official self-description puts two keywords together: "Pydantic AI is the Python AI SDK: a typed, extensible agent loop with every model a string swap away." "Typed" is its worldview: Pydantic runs natively from the data layer all the way to agent output. "Agent loop" is its shape: it hands you primitives, not a finished product. It sits in the same bracket as the OpenAI Agents SDK, but goes noticeably deeper on two points — type safety and durable execution.

When to use it, when not to

A fit when: you are a Python team that wants type-safe structured output plus dependency injection for your agents; you need to turn an agent run durable, using an engine you already operate; you are doing multi-agent work (delegation / hand-off / graph); you want first-class MCP support and want MCP running locally so you keep control of credentials; you want a thin agent loop and also want the official ready-made Harness (Coder / Researcher / memory / guardrails). Not a fit when: you are on TypeScript / Node (see Mastra); you want the smallest possible dependency set and do not want to bring in Pydantic; you want to avoid every commercial component (Logfire and Gateway are official recommendations but optional); you need process-level sandboxing and network policy built into the framework — the sandbox lives in the Harness / Monty, not in the core SDK.

Model & openness

The most model providers connectable, with a full official catalog; switching models is one string.

The official first selling point is model-agnostic. Official overview, verbatim:

Model-agnostic: Supports virtually every model and provider: OpenAI, Anthropic, Gemini, DeepSeek, Grok, Cohere, Mistral, and Perplexity; Azure AI Foundry, Amazon Bedrock, Google Cloud, Ollama, LiteLLM, Groq, OpenRouter, Together AI, Fireworks AI, Cerebras, Hugging Face, GitHub, Heroku, Vercel, Nebius, OVHcloud, Alibaba Cloud, and SambaNova.

The official docs add a line leaving a door for in-house models. Official wording:

Official wording: "If your favorite model or provider is not listed, you can easily implement a custom model."

The official catalog splits providers into four groups.

  • 9 model developers — OpenAI, Anthropic, Google(Gemini), DeepSeek, Mistral, plus Cohere / xAI / Moonshot(Kimi) / Z.AI
  • 6 cloud platforms — AWS Bedrock, Google Cloud(Vertex AI), Azure Foundry, Alibaba Cloud, Snowflake Cortex, Heroku
  • 3 local & self-hosted — Ollama (ollama:), vLLM (vLLM:), LiteLLM (litellm:)
  • 8 inference platforms & gateways — Groq, Cerebras, Hugging Face, Together, Fireworks, OpenRouter (six inference platforms) plus Vercel AI Gateway and Pydantic AI Gateway (two gateways)

Usage is a <provider>:<model> prefix string, e.g. Agent('openai:gpt-5.2'). The official models/overview page gives a provider catalog table. Each provider row carries its service type and selection syntax.

There are also a fallback model and ModelProfile. The latter marks capabilities like supports_tools, supports_json_schema_output.

⚠ One boundary the official docs draw themselves: capabilities are not guaranteed equivalent across providers.

Official wording: "Feature support depends on the model and API you select, even when two services use the same API format."

Full behavioral equivalence after switching providers is not guaranteed by the official docs. The official position: the same agent is portable, but per-vendor behavioral consistency needs testing.

Where it runs

A pure Python library, not a service — after install, you decide where it runs.

Install is uv add pydantic-ai (or the slim variant). It does not start a server. The official position is "the same agent runs everywhere". Official README, verbatim:

"The same agent runs everywhere you need it: behind a web frontend, in the terminal, on a voice call, on a durable background queue, in GitHub Actions, or as a plain object you call run() on."

The runtime surface is yours; the official docs give these entry points:

  • embedded in a web frontend (AG-UI / Vercel AI event streams)
  • the terminal (official CLI clai)
  • on-device voice sessions
  • a durable background queue (that path requires wiring an engine — see the background axis)

Who runs the agent loop: you. Two optional official components — the Pydantic AI Gateway (self-hostable) for model routing, and Logfire for observability. Both optional; neither changes the fact that "the library is run by you".

The official docs also provide GitHub Agentic Workflows, running headless on issues / PRs. There is also a built-in web chat entry. Both are built on the same library.

Local files

The core agent carries no file system; the official Harness provides a complete local-file kit.

A plain Agent has no workspace concept. File capability lives in the Pydantic AI Harness. Official README, verbatim (Coding agent section):

"A complete coding agent in your terminal: workspace-rooted file access, allowlisted shell, repo orientation, planning, and context management that survives long sessions."

The implementation is a set of separable capabilities:

  • FileSystem('.')
  • Shell(cwd='.')
  • RepoContext()
  • SubAgents(...)
  • ClearToolResults()
  • ToolOutputLimits()

The official docs stress Coder merely composes them. Official wording:

Official wording: "use it whole, or use the blocks it bundles directly; the two are equivalent"

The key boundaries are written explicitly: file access is workspace-rooted (scoped to the workspace), shell is allowlisted (whitelist).

There is also Monty, officially "a sandboxed Python interpreter that runs model-written code". It runs code written by the model.

Unknown: the default file-access boundary at the core-SDK level (without Harness) is not stated by the official docs Verified: overview and harness pages checked.

Tasks after shutdown

Its hardest differentiator: the official docs list eight durable-execution engines, and "every model and tool call becomes its own durable unit".

Official durable execution page, verbatim:

"Pydantic AI allows you to build durable agents that can preserve their progress across transient API failures and application errors or restarts, and handle long-running, asynchronous, and human-in-the-loop workflows with production-grade reliability."

Mechanism, official wording:

"Each engine wraps every model request and tool call as its own durable unit"

The official README lists the engines as Temporal, DBOS, Prefect, Restate, AWS Lambda, Kitaru, Airflow, Absurd, with "the first five co-maintained with the vendor teams". Third parties also have a durable execution backend builder to plug in their own engine.

Connection example: the TemporalDurability() capability + PydanticAIWorkflow; officially:

"a run working through a background queue survives restarts, failures, and long waits"

⚠ Read the boundary out loud: the official docs dedicate one line —

"Durability is not storage"

Meaning: the durable engine only guarantees one run survives crashes. It does not store your conversation threads — that is a separate Persistence module.

Two more limits: run_sync() / run_stream_sync() cannot be used inside tools; use async def. Each agent can attach only one durable engine; attaching a second throws UserError.

Tools & extensions

The tool surface has four layers: function tools + MCP + A2A + capability composition. MCP is a core capability.

Function tools register with @agent.tool. Official wording:

Official wording: "the rest of its signature and its docstring become the tool schema, arguments are validated before your code runs"

Argument errors are fed back to the LLM for retry.

MCP officially supports two directions (mcp/overview page):

  • ① the agent connects to an MCP server and uses its tools
  • ② the agent is placed inside an MCP server

The recommended approach is the MCP capability. Officially:

"It runs the MCP server locally by default — keeping credentials, hooks, and tracing under your control"

and a single native=True flag opts into the model provider's native MCP (falling back to local when unsupported). Low-level: MCPToolset (toolsets=[...]). "Local by default" matters for credential control.

⚠ A2A is being retired. The official integrations/a2a page states explicitly:

  • Agent.to_a2a() and pydantic-ai-slim[a2a] are "deprecated and will be removed in 2.0"
  • fasta2a has moved to datalayer/fasta2a, with a Pydantic AI bridge

UI/interfaces: AG-UI, Vercel AI event streams, CLI, built-in web chat, voice. There is also the capabilities composition mechanism. And YAML/JSON agent specs for defining agents without code.

Context & memory

It explicitly splits "persistence" from "durability" — the core framing of this dimension.

Official durable execution page, verbatim:

"Durability is not storage — A durable engine keeps one run alive across crashes and restarts. It does not store your chat threads: saving a conversation and picking it up later is a different problem ... laid out in Persistence."

i.e. the durable engine manages run survival. Persistence manages saving and resuming conversation threads — a separate module.

Harness additionally provides context management: the official capabilities list includes memory, context management (compaction), persistence. Official README, verbatim says Harness:

Official wording: "has everything an agent needs for complex, long-running work, snapped on as capabilities"

So our "state ≠ context" is split by the official docs into three: the durable run (engine), the chat thread (Persistence), context compaction.

Unknown: the concrete trimming strategy and thresholds of compaction — the official docs give no defaults Verified: README and durable page checked.

Permissions & limits

Human intervention is "tool-level approval"; sandboxing sits in Harness / Monty; credentials default to local.

HITL tool approval is item 8 of the official overview:

"Human-in-the-Loop Tool Approval: Easily lets you flag that certain tool calls require approval before they can proceed, possibly depending on tool call arguments, conversation history, or user preferences."

This line comes from the deferred tools page. Its level differs from other listed objects: it intercepts "may this tool call run", and can decide dynamically from arguments and history.

guardrails also ship with Harness (the official Harness capability list includes guardrails).

Sandbox: the official Monty is "a sandboxed Python interpreter that runs model-written code". Harness's Shell is allowlisted; FileSystem is workspace-rooted.

Credentials: MCP runs locally by default; officially "keeping credentials, hooks, and tracing under your control".

Unknown: whether the core SDK has process/network-level sandboxing and built-in auth/permission boundaries is not stated by the official docs Verified: overview, durable, and mcp pages checked. Enterprise-grade permissions and auditing are handled on the Logfire / Gateway side.

Best for

Fits: Python teams needing type safety, and anyone turning agent runs into durable ones.

  • Python teams building agents with "type-safe structured output + dependency injection"
  • You need agent runs to become durable (across restarts, long waits, HITL), and want to use engines you already have, like Temporal / DBOS / Prefect
  • Building multi-agent systems (agent delegation / hand-off / graph)
  • You need first-class MCP support and want MCP running locally to control credentials
  • You want both a thin agent loop and the official ready-made Harness (Coder / Researcher / memory / guardrails)
  • You want Pydantic validation to run end to end from the data layer to agent output

Does not fit: non-Python stacks, minimalists, and anyone needing a core-SDK-shipped sandbox.

  • TypeScript / Node teams (look at Mastra)
  • Chasing minimal dependencies, not wanting Pydantic and optional capability packages (its worldview is typed end to end)
  • Wanting to avoid any commercial component entirely — Logfire and Gateway are officially recommended but optional; the official docs state OTel and self-hosting are both supported
  • Needing framework-shipped process-level sandbox and network policy in the core — sandboxing sits in Harness / Monty, not the core SDK

Top misconception

  • Assuming it is a purely thin harness — the official Pydantic AI Harness now bundles memory, guardrails, sub-agents and context management as capabilities, plus a complete Coder agent.
  • Reading "durability" as "conversation storage" — official docs state plainly that "Durability is not storage": the durable engine only keeps a run alive, while thread persistence is a separate module.
  • Assuming evals / observability require Pydantic Logfire — official docs state instrumentation is standard OpenTelemetry, so any OTLP backend works.
  • Assuming A2A is a long-term built-in — the official docs mark Agent.to_a2a() as deprecated in 1.x and removed in 2.0, with fasta2a moved to datalayer/fasta2a.

Durable execution: eight official engines, and "every model and tool call becomes a durable unit"

This is what distinguishes it from the OpenAI Agents SDK. Official durable execution page, verbatim:

Pydantic AI allows you to build durable agents that can preserve their progress across transient API failures and application errors or restarts ... Each engine wraps every model request and tool call as its own durable unit.

Engine list (README, verbatim): Temporal, DBOS, Prefect, Restate, AWS Lambda, Kitaru, Airflow, Absurd. The first five are "co-maintained with the vendor teams". Third parties can also use the backend builder to plug in their own engine.

⚠ The boundary that must be read out loud: the official docs dedicate one line —

Durability is not storage. A durable engine keeps one run alive across crashes and restarts. It does not store your chat threads: saving a conversation and picking it up later is a different problem ... laid out in Persistence.

i.e. the durable run and conversation-thread persistence are two things — precisely an isomorphic expression of our "state ≠ context".

MCP: both directions supported, local by default to control credentials

The official mcp/overview page describes two directions:

  • ① the agent connects to an MCP server and uses its tools
  • ② the agent is placed inside an MCP server

The recommended approach is the MCP capability. Officially:

It runs the MCP server locally by default — keeping credentials, hooks, and tracing under your control — and lets you opt into the model provider's native MCP support with a single native=True flag.

Low-level: MCPToolset (toolsets=[...]). "Local by default" is valuable for credential control. Versus "handing credentials to the provider's native MCP", this is an optional trade-off.

A2A: officially being retired — mind the version timing

This must be written clearly, or it will be misjudged as a long-term built-in capability. The official integrations/a2a page headline reads:

Deprecated in 1.x, removed in 2.0
  • Agent.to_a2a() and pydantic-ai-slim[a2a] are deprecated, removed in 2.0.
  • fasta2a is now maintained by datalayer/fasta2a. Since v0.6.1 it ships a Pydantic AI bridge (agent_to_a2a).

So the sentence "Pydantic AI supports A2A" needs a version timestamp to be accurate.

Harness and Graph are two independent upper layers

  • Pydantic AI Harness: officially packages memory, guardrails, sub-agents, planning, context management (compaction), and persistence into capabilities, and ships ready-made Coder / Researcher complete agents.

The official docs also stress Coder is not a black box. Official wording: "use it whole, or use the blocks it bundles directly; the two are equivalent".

  • pydantic-graph: the official graphs page says it can be used independently of pydantic-ai — "it has no dependency on pydantic-ai and can be considered as a pure graph-based state machine library". The official docs also humorously note: a graph is a nail gun, not the right tool for every job.

Conclusion: both are optional layers grown off the core library — which is why we still file this under coding-base.
