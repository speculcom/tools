In one sentence: LlamaIndex is a Python library. It pulls external data in for retrieval and question answering.

⚠ But one thing has to be said first.

The project has explicitly moved its company focus away from "orchestration frameworks":

The current focus of LlamaIndex is to build the best AI-powered engine for document parsing and extraction. LlamaParse is our enterprise platform for agentic OCR, parsing, extraction, indexing and more. ...the company itself has undergone an evolution since when this OSS framework first launched 3 years ago in 2023. While we still have the OSS framework available as an open toolkit that you're welcome to use, our primary focus has shifted towards LlamaParse...

The selection implication is direct. The company's resources really have tilted towards document parsing, but the orchestration capability has not left the OSS:

  • The README puts Workflows in the commercial-platform section (the link points at cloud/llamaagents)
  • The official framework docs state that llama-index-core still ships a stable version of Workflows (checked 2026-10-08)

What it actually provides now, the README itself lists best:

- data connectors to ingest your existing data sources and data formats (APIs, PDFs, docs, SQL, etc.) - ways to structure your data (indices, graphs) - an advanced retrieval/query interface over your data - easy integrations with your outer application framework

Put together, the OSS framework now really provides five things: data ingestion, indices / graph structures, a retrieval query interface, 300+ integrations, and Workflows orchestration.

The value of this entry lies elsewhere — it meets the v3 rule "a substantive update within 30 days" (pushed 2026-09-29, still active), but its real value is recording that turn honestly: behind 52,377★ the company is heading towards document parsing / agentic OCR, which is LlamaParse and ParseBench territory, not this open-source framework's.

When to use it, when not to

Fits: bringing external data sources in for retrieval and question answering; needing one of the 300+ ready-made integrations; a Python stack; explicitly wanting LlamaParse's parsing capability (that goes through the commercial platform).

Not a fit for: wanting the commercial platform's managed orchestration and Agent Builder (LlamaAgents); agents that read and write files in your project directory and run commands — that is the Deep Agents "workspace filesystem" category; needing explicit sandbox and permission boundaries — the official framework docs provide no such mechanism; needing managed "keep running after shutdown" execution — that is the LlamaAgents platform side.

Model & openness

The integration surface is "300+ separate integration packages", not a unified gateway.

  • The official integrations page calls them all "community integrations"
  • That is, most are community-maintained, not hand-fed by the vendor one by one

"There are over 300 LlamaIndex integration packages that work seamlessly with core, allowing you to build with your preferred LLM, embedding, and vector store providers."

The namespace rule is easy to remember:

  • With .core (from llama_index.core.xxx) = core
  • Without it (from llama_index.xxx.yyy) = an integration package

New integrations go through maintainer review.

The README states: "some integrations may be declined".

Unknown: the official docs publish no quality tiering or maintenance-activity grading for the integration packages. (Checked — README and the integrations page.)

Where it runs

The OSS form is a pure library with two install tiers; hosted execution lives on the commercial-platform side.

Two install tiers (README Getting Started):

  • Starter — llama-index (PyPI): core plus a bundle of common integrations
  • Customized — llama-index-core: core only, then pick packages from the integrations page

The framework itself is a library you import. The way in is to connect with your outer application framework, which is also the fourth item of the README's Proposed Solution:

"integrations with your outer application framework"

The vendor has a separate hosted/deployment path. LlamaAgents' llamactl CLI can be used like this:

Official wording: "serve locally, and deploy to LlamaCloud or export for self-hosting"

LlamaCloud also offers hosted Indexing.

  • Hosting is the LlamaCloud / LlamaAgents layer (commercial)
  • It is not a run form that ships with the OSS framework
Local files

It reads local files to build indexes, not to give an agent a workspace.

The official SimpleDirectoryReader docs put it plainly:

"the simplest way to load data from local files into LlamaIndex"

Parameters you can pass:

  • input_dir, recursive=True
  • exclude, required_exts, num_files_limit
  • Remote file systems go through fsspec (S3, GDrive, etc.)

Indexes live in memory by default. Two official example actions:

  • Persist: index.storage_context.persist() writes to ./storage
  • Reload: load_index_from_storage

This site records this axis from the "index layer" perspective.

It is not an "agent workspace" file system. It is local file reading at the "data-source ingestion + indexing" layer.

It reads disk to turn documents into retrievable indexes. That is not the same thing as Deep Agents' "agent editing files in a workspace".

Tasks after shutdown

There is no hosted execution that "keeps running after shutdown". But orchestration (Workflows) really is still in the OSS.

One spot is easy to misread from the README. The README lists Workflows under the LlamaParse platform's Agents section, while the official framework docs are explicit:

"llama-index-core comes with a stable version of Workflows included"

So orchestration has not been moved out of the OSS. Two entry points:

  • Import path llama_index.core.workflow
  • Also standalone: pip install llama-index-workflows

Background execution is the missing item. The official framework docs offer no hosted runtime for "keep-running-after-shutdown"; you run the process yourself. For hosting, go through LlamaAgents / llamactl:

"deploy them to LlamaCloud or your own infrastructure"

and that is the platform side.

Tools & extensions

Two things at the tool layer: community ToolSpecs, plus one official MCP connector package.

The official tools docs give FunctionTool. There is also QueryEngineTool. Plus "Community contributed ToolSpecs".

Handling "a tool returns an oversized output" is what Utility Tools do:

  • OnDemandLoaderTool
  • LoadAndSearchToolSpec

MCP is officially supported, as a separate package. Docs wording: "LlamaIndex provides robust support for consuming MCP servers through the llama-index-tools-mcp package"

Its MCP surface:

  • All three transports supported: SSE / Streamable HTTP / stdio
  • A Workflow can be re-published as an MCP server
  • The vendor also hosts mcp.llamaindex.ai (a docs-retrieval / LlamaParse MCP service)
Context & memory

This dimension has concrete official mechanisms; it is not blank.

The official docs call the framework a "data framework".

The core is structure your data (indices, graphs). Plus a retrieval/query interface.

That is, "turn external data into retrievable context".

How do retrieval results get packed into the context window? The official answer is the Response Synthesizer:

  • compact (default) — "stuff as many text ... that can fit within the context window"
  • refine — refine chunk by chunk
  • tree_summarize — recursive summarization
  • simple_summarize — truncate to a single prompt

That is its context-trimming and summarization mechanism: pack to the window first, split into chunks when it does not fit, compress via the summarize-style modes.

Permissions & limits

⚠ This is a clear, major information gap; confirm it yourself before choosing.

Things the official README never mentions: sandboxing, a file-permission model, network access controls, human-in-the-loop confirmation — not one.

Compared against the other orchestration frameworks this site files:

  • Google ADK has Tool Confirmation (HITL)
  • CrewAI has guardrails (mechanism undocumented)
  • LangGraph has interrupts (state can be inspected and modified)
  • LlamaIndex — the README does not even name the concept

⚠ The nature of the risk surface is different. Its main battleground is document parsing and RAG; what it handles is usually user-uploaded data.

That is a different class of risk from "an agent touching your local files" (data-leakage surface vs host-operation surface).

But the README does not discuss data permissions or isolation.
