A thin agent library from Hugging Face — the repository description is literal: "barebones library for agents that think in code".

The core difference is code-as-action. The default CodeAgent lets the LLM write its actions as Python code and execute them, instead of emitting JSON tool calls. The official claim is that this "uses 30% fewer steps" and reaches higher scores on difficult benchmarks (README cites arXiv 2402.01030 / 2411.01747). A ToolCallingAgent that emits JSON is also provided, officially positioned for scenarios that favour reliability and structured validation — either one works.

Model-agnostic by design. Several Model classes, one per route: InferenceClientModel on the Hub's Inference Providers, plus LiteLLMModel ("100+ different models"), OpenAIModel, AzureOpenAIModel, AmazonBedrockModel, and locally TransformersModel / MLXModel / Ollama. Swapping provider means swapping a Model class.

On safety the docs are blunt. The default LocalPythonExecutor is not a security sandbox — README states it "is not a security sandbox. It applies some restrictions but can be bypassed and must not be used as a security boundary." Real isolation requires a remote sandbox: Blaxel, E2B, Modal or Docker.

When to use it, when not to

Fits: teams that buy into code-as-action (officially ~30% fewer steps than JSON tool calls) and are willing to sandbox LLM-generated code; anyone who needs model-agnostic support and local models (transformers / Ollama / mlx-lm); developers who want a thin, hackable library — Python stack; projects that want MCP / LangChain / HF Hub Space as tool sources.

Not a fit: needing a vendor-hosted always-on background or resumable runs — it is a pure library and memory is not persisted to disk; unwilling to take on arbitrary-code-execution risk but also unwilling to run a remote sandbox; wanting batteries-included filesystem / memory / sub-agent orchestration.

Model & openness

The official self-description is model-agnostic: "supports any LLM" (README, verbatim).

The implementation is several Model classes, each covering one end:

  • On the HF side, InferenceClientModel goes through the Hub's Inference Providers. Officially named: Cerebras, Cohere, Fal, Fireworks, HF-Inference, Hyperbolic, Nebius, Novita, Replicate, SambaNova, Together
  • The rest go through LiteLLMModel (officially "100+ different models"), OpenAIModel (OpenAI and compatible endpoints, examples given for Together / OpenRouter), AzureOpenAIModel, AmazonBedrockModel
  • On the local side: TransformersModel, MLXModel, Ollama

Switching providers = swap one Model class. A provider= parameter also works. The code structure stays the same.

Unknown: after switching providers, the reliability alignment of tool calling / structured output is not stated by the official docs. (guided_tour and the models reference page checked.)

Where it runs

A pure Python library. You run the agent loop yourself in a local process. No hosted execution service officially.

The official positioning, verbatim (README):

Official wording: "run powerful agents in a few lines of code"

Install pip install smolagents (Python ≥3.10). It ships two CLIs: smolagent (general multi-step CodeAgent, with an interactive wizard) and webagent (a helium-based web-browsing agent).

Hierarchical multi-agent systems are expressed with managed_agents= for delegation.

The whole agent can also be shared to HF Hub as a Gradio Space via agent.push_to_hub() (README, verbatim: "share your agent to the Hub, as a Space repository").

But that is only a share / load form — not a vendor-hosted resident runtime — the process stays in your hands.

Local files

The framework itself presets no file-system tools.

The official default toolbox (smolagents[toolkit]) has only three items: DuckDuckGo/WebSearch, a Python code interpreter, Whisper transcription — no dedicated file read/write tool.

CodeAgent reads and writes files through the Python code it generates itself (e.g. open()) or custom tools you provide.

So the file boundary comes from the execution environment, not the framework. Locally it is constrained by LocalPythonExecutor's import allowlist. In a remote sandbox it is confined to the sandbox container. The two sandbox modes are on the secure_code_execution page.

Unknown: the default file-access scope allowed for CodeAgent is not stated by the official docs. (secure_code_execution and guided_tour pages checked; no file-permission section.)

Tasks after shutdown

Self-hosted = stop the process and it's gone; no hosted background option.

All run modes in the README are local code calls. The forms are Python API / CLI / sandbox. There is no cloud-resident or scheduled-execution form.

The only official mechanism related to "long tasks / checkpoints" is single-step execution. agent.step(memory_step) advances one step at a time. Memory lives in-process at agent.memory. The use case on the tutorials/memory page is exactly:

So resuming after interruption means serializing steps yourself.

Tools & extensions

The tool surface is wide, and MCP is first-class access. The README self-describes as "Tool-agnostic", with four tool sources:

  • ① Custom tools — the @tool decorator or subclassing Tool
  • ② MCP — ToolCollection.from_mcp(...) reads any MCP server (install smolagents[mcp])
  • ③ LangChain tools — Tool.from_langchain
  • ④ HF Hub Spaces as tools — Tool.from_space

The default toolbox (smolagents[toolkit]) = DuckDuckGo/WebSearch, Python code interpreter, Whisper transcription.

Multi-agent systems use managed_agents= to treat sub-agents as callable units. There are also final_answer_checks for custom termination validation.

Context & memory

Context = the step history (AgentMemory); no cross-session persistence.

The official tutorials/memory page says the agent "has a memory of past steps".

Step types: TaskStep / ActionStep / PlanningStep / FinalAnswerStep.

Three official manipulation options:

  • agent.replay() to replay
  • read/write agent.memory.steps directly (the example even moves steps between two agents)
  • step_callbacks (official example: delete old screenshots to save tokens)

There is also planning_interval=N to insert a planning step every N steps.

The official docs position this axis as "inspect / rewrite memory", not compression.

Unknown: deep context management like spilling large tool outputs to disk is not stated by the official docs. (tutorials/memory and guided_tour pages checked.)

Permissions & limits

The official docs are very blunt about execution safety. The default LocalPythonExecutor is not a secure sandbox.

README, verbatim:

"The built-in LocalPythonExecutor is not a security sandbox. It applies some restrictions but can be bypassed and must not be used as a security boundary."

What the local interpreter provides:

  • step-by-step AST execution
  • imports denied by default (open an allowlist with additional_authorized_imports)
  • submodules denied by default (numpy.* to allow all subpackages)
  • loop iteration caps
  • undefined operations error out

For real isolation you must use a remote sandbox: executor_type="blaxel" / "e2b" / "modal" / "docker".

The official docs distinguish two modes: sandbox only the code snippets; or put the whole agent in the sandbox (the latter required for multi-agent).

There is also a Human-in-the-Loop example (examples/plan_customization), but it is not a built-in approval mechanism.

Unknown: network access control is not stated by the official docs.

Top misconception

  • Treating LocalPythonExecutor as a security sandbox — the official docs state it is not a security boundary and can be bypassed.
  • Assuming it is only for writing code — the official positioning is a barebones library for *agents*; CodeAgent just expresses actions as code.

Sandbox: the security boundary stated plainly by the official docs

The README states the default interpreter's positioning directly:

The built-in LocalPythonExecutor is not a security sandbox. It applies some restrictions but can be bypassed and must not be used as a security boundary.

What the local interpreter provides:

  • step-by-step AST execution
  • imports denied by default (additional_authorized_imports allowlist)
  • submodules denied by default (numpy.* to allow all subpackages)
  • loop iteration caps
  • undefined operations error out

For real isolation the official docs give two sandbox classes:

  • hosted cloud sandboxes: Blaxel, E2B, Modal (pip install 'smolagents[blaxel|e2b|modal]')
  • self-hosted containers: Docker (executor_type="docker")

Keep the two modes apart: sending only code snippets into the sandbox (simple, but unavailable for multi-agent); or moving the whole agent (model and tools included) into the sandbox (stronger isolation, but you pass credentials and set it up manually).

The relationship with HF Hub: sharing, not hosting

In the README, agents and tools are both Hub objects:

  • agent.push_to_hub("user/agent") publishes the agent as a Gradio Space
  • agent.from_hub(...) loads community agents; same for tools

Multi-agent systems use managed_agents= (plus the official ManagedAgent wrapper class) for hierarchical delegation.

⚠ This is not "vendor-hosted execution": a Space is a share/load form; the agent loop still runs on your side, and there is no "keeps running after shutdown" semantics. Don't mistake it for a hosting service when selecting.
