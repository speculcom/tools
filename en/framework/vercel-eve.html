eve is Vercel's filesystem-first agent framework (1.0, Apache-2.0): an agent is a directory; model, instructions, tools, skills and channels are files, with durable execution, sandboxing, approvals and evals built in. It is closer to "Next.js for agents": production durability, sandboxing and approvals become default layers instead of something each project rebuilds.

When to use it, when not to

Fits TypeScript teams shipping production agents, teams already in the Vercel / AI SDK ecosystem, and teams that want to maintain an agent as code with evals, MCP and Slack/GitHub integrations. Not a fit for teams that only want a chat UI, Python-first teams, or deployments that must be fully offline without Vercel Workflows/Sandbox.

8 questions, one table

8 questions, each comparable item by item with its peers.

Model & openness

Any model: eve uses a TypeScript model string to connect to AI SDK / AI Gateway and does not lock you to a vendor. The official wording is "works with any model"; the default scaffold's OpenAI model is only an example.

Where it runs

A TypeScript framework with a filesystem-first design: an agent is a directory, and model, instructions, tools, skills and channels are files. Vercel supplies durable execution through Workflows and isolation through Sandbox; Docker, microsandbox and just-bash adapters can host the runtime yourself.

Local files

The working object is the agent directory in your repository; tools can read and write files, but production execution happens in a sandbox. It is not a desktop file agent and does not sync your local directories.

Tasks after shutdown

1.0 is built around durable execution: sessions can recover across crashes, sub-agents can run in parallel, and workflows can wait for approval before continuing. The official pitch is a "durable session for every conversation"; scheduled and background triggers come from Workflows and channels.

Tools & extensions

A tool is a TypeScript file and a skill is a Markdown file; MCP servers, OAuth/API keys and Slack/GitHub/Discord/Notion/Linear connections come through Vercel Connect. Write actions can require human approval; the model never receives connection URLs or credentials directly.

Context & memory

Session state is persisted in Workflows; 1.0 adds cross-session memory for user preferences, project facts and work history. Context is organized by session/thread rather than stuffed into a single window.

Permissions & limits

Three layers: approval gates, sandboxing and a connection broker. Vercel Connect handles OAuth consent and token refresh; on self-hosting, authentication, keys and sandbox isolation are your responsibility. Hosted organization permissions follow Vercel's team model.

Best for

Fits TypeScript teams shipping production agents (durable sessions, sandboxing, approvals, evals, sub-agents), teams already in the Vercel / AI SDK ecosystem, and teams that want to maintain agents as code rather than clicking through a UI.

Not a fit for teams that only want a chat shell, Python-first teams, or deployments that must be fully offline without Vercel Workflows/Sandbox.

When something fails

Authentication and permissions · Invalid tool inputs · Invalid output format

Top misconception

  • Treating eve as a hosted runtime — it is a framework; Workflows, Sandbox and Connect are a separate managed layer
  • Reading 1.0 as just a version number — 1.0 carries breaking changes; read the changelog before upgrading
  • Using GitHub stars as a production-maturity signal — this is a new framework that went from public preview to 1.0; run your own evaluation first
