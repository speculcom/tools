Langfuse is an open-source observability and evaluation platform. Its core difference is self-hosting: traces, scores, prompts and datasets can stay in your own environment.

When to use it, when not to

Fit: teams whose data cannot leave the boundary and who want what is visible online to become a regression gate before release. It connects observability and evaluation on one trace: observe, settle into a dataset, then block regressions in CI. Not fit: vendor-hosted red-team or compliance-audit scenarios, or teams unwilling to supply judge-model keys. This entry records supported evaluation surfaces, not scores.

Model & openness

The platform produces no content itself; the evaluation capacity depends on models you configure — LLM-as-a-Judge runs through an "LLM Connection" with credentials you supply (judge doc direct-fetched today). Observed apps can use any framework or model, and self-hosting carries a "Bring your own LLM API" line (self-hosting page fetched today). The full judge-model list and version mapping were not itemized today — recorded as unknown.

Where it runs

Open source and self-deployable (Docker Compose for testing, Kubernetes/Helm for production, per the self-hosting page fetched today), plus an official cloud (AWS US/EU/JP regions, security page fetched today); the interaction surface is a web console with SDKs and an API. What runs on your machine is the platform service and UI, not the models under evaluation.

Local files

When self-hosted, traces, scores, prompts and datasets live in your own PostgreSQL, ClickHouse, Redis and object storage (fetched today); data arrives via SDK, OpenTelemetry and the API — the platform does not read your local codebase; the export and deletion interface surface was not itemized today.

Tasks after shutdown

Online evaluation scores production traces asynchronously (evaluation overview and judge docs fetched today); Experiments run datasets in batch. Resume-after-shutdown is not a feature surface for this kind of platform. Sampling ratios, scoring latency and retry semantics were official docs do not itemize every sub-detail — recorded as unknown.

Tools & extensions

Python and JS SDKs, REST API, OpenTelemetry ingestion; the official documentation MCP server is on record from today's fetch and only exposes docs to agents — whether an authenticated MCP surface can read traces or scores is not itemized in official docs. CI/CD is used to "block deploys on regressions" (evaluation overview fetched today).

Context & memory

Observed objects are organized per project, with traces and scores linked to their source; the four score types NUMERIC, CATEGORICAL, BOOLEAN and TEXT are on record from today; turning traces into datasets and prompt versioning are on the product surface. Cross-project memory is not a platform feature and is not declared by the vendor.

Permissions & limits

Self-hosting can be air-gapped so data stays in your environment; the cloud is SOC 2 Type II with project-level RBAC and SSO (security page fetched today). Tier and quota facts (Hobby plus Core, Pro, Enterprise; usage units and data-access windows vary by tier) are on the pricing page from today, with price numbers excluded per D9. Whether customer data trains models was not found in clause text — recorded as unknown.

Best for

Fits teams that must keep data in their own environment (self-hosted or air-gapped), want observation and evaluation on one trace store, and turn production samples into datasets that block regressions in CI. Not a fit for those who only want a vendor-hosted red-team or compliance-audit service, or who will not bring judge-model credentials. This site does not measure scores and does not rank.

Core under MIT (the repository LICENSE page, direct-fetched today, reads "MIT Expat"); the /ee enterprise directory is covered by ee/LICENSE, whose text could not be fetched today — unknown.
