English summaries and interface labels are available. Detailed source notes below are currently in Chinese.

Presidio is the self-deployed redaction SDK: the docs describe fast text and image identification and anonymisation, with three APIs — AnalyzerEngine, AnonymizerEngine and Image Redactor — and official operators replace, redact, hash, mask, encrypt, keep and custom. The only line against hosted products in this category is whether text may leave your boundary: Presidio runs in your deployment and supports offline use. Its scores therefore carry no blocked-percentage meaning; the official analyzer page even says scores are not probabilities.

When to use it, when not to

Fit: inserting personal-data identification and transformation into your pipeline (before RAG ingest, before log persistence, before sending to a cloud model), operator-level composition and custom recognisers, text that must not cross the network boundary, and fully offline operation. Not fit: wanting a hosted console and compliance deliverables, modalities beyond text and images (the official surface stops there), or teams treating a score threshold as compliance proof.

Model & openness

It carries no generative model of its own: the Analyzer page states "Predefined recognizers leverage regex, Named Entity Recognition and other types of logic to detect PII in unstructured text." — the recognition surface combines regex, NLP (spaCy / Transformers class), rules and checksums, with context words weighting the score, and custom recognizers covered by an official tutorial. The full list of selectable NLP engines and model tiers: not itemised in this pass.

Where it runs

Everything runs inside your own boundary: the docs home page gives the install surface as pip packages or a Docker REST API, and states that offline usage is supported with data staying inside your own deployment. No hosted service surface is offered officially (no such statement captured). Image tags and their version mapping: not itemized in official docs word for word in this pass.

Local files

It does not read your workspace; it processes only the text and images you explicitly hand it, and returns results inside your own process or service. Where the recognizers' language-model files are downloaded and cached, and how they are packaged offline: no word-for-word official statement captured, recorded as unknown.

Tasks after shutdown

There is no hosted background task: one analyze / anonymize call is one invocation, or one pass inside your own service, with batching and retries owned by your orchestration layer. The docs table of contents (Getting Started / Analyzer / Anonymizer / Image Redactor / Samples / API Docs) contains no queue or resume concept.

Tools & extensions

Three API faces: AnalyzerEngine (recognition), AnonymizerEngine (transformation), Image Redactor (image masking). The operators on record from the Anonymizer page are replace, redact, hash, mask, encrypt, keep and custom, configured through OperatorConfig's type and params and combinable. MCP transport support: not described in the official docs, recorded as unknown.

Context & memory

Here "context" is a literal mechanism: recognizers weight candidate entities with context words, so neighbouring words in the same text change the result; the docs home page describes the project as "fast identification and anonymization modules" for text and images. It is a stateless one-pass handler with no cross-session memory — batch context-window management belongs to your calling code.

Permissions & limits

See the licence field (MIT, taken from the PyPI licence metadata; the LICENSE text was not read directly). Two measured facts about ownership: the old address microsoft.github.io/presidio displayed "This page has moved" on the verification date, and the intermediate host data-privacy-stack.github.io 301s to presidio.dataprivacystack.org, whose home page states the project is governed by Data Privacy Stack. Data flow: recognition and anonymisation complete inside your own deployment and offline use is supported, meaning text need not be sent to any third party. Red line: the Analyzer page states on record "Scores are not probabilities", so a score threshold is not a detection probability; this site publishes no detection rate, no miss rate and no product rankings. Whether it satisfies an anonymisation obligation under any given law is not a legal conclusion the project makes.

Best for

Fits: inserting personal-data recognition and transformation into your own pipeline (before RAG ingestion, before logs are written, before a call to a hosted model); needing operator-level composition and custom recognizers; requiring text not to leave your network boundary; needing the whole chain to run offline. Not a fit: teams wanting a hosted console and compliance deliverables; modalities beyond text and images (the surface on record stops there); anyone treating a score threshold as proof of compliance.

Test notes

This site has not run it end to end: AnalyzerEngine/AnonymizerEngine were never installed or called, no corpus was run to test hit behaviour, so no detection rate, miss rate, precision or ranking is produced, and the number of official recognizers is not tallied. This archive only organises statements on record at the docs home page, the Analyzer and Anonymizer pages, the PyPI project page and its release history.

Suggested measurements (four):

  • The real cost of wiring a custom recognizer (the tutorial is on record; the amount of change is yours to test)
  • How language models are obtained in an offline deployment (download and cache locations are not spelled out officially)
  • Reversibility and audit trail of combined operators (what the restore boundary looks like when replace meets encrypt)
  • Entity coverage differences outside English (this site draws no ratio conclusion — only whether the mechanism works)
