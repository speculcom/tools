It is a self-deployed unified entry point, with governance on keys and budgets. Officially an open-source AI gateway: one OpenAI-format interface accepts many providers, then turns who can call which model, what it costs and which tools are reachable into configurable objects.

When to use it, when not to

Fit: teams consolidating multi-model access, needing key/team/organisation-level authorisation, and insisting keys and logs stay in their own environment. Not fit: wanting only a thin client SDK, or teams needing vendor-backed hosted guardrails and compliance promises; here guardrails are external services you attach, not a vendor guarantee.

8 questions, one table

8 questions, each comparable item by item with its peers.

Model & openness

This is one of its two main axes: the providers page records '100+ LLMs' behind one OpenAI-format API with bring-your-own keys, and self-hosted endpoints on the same page (Ollama, vLLM, Llamafile). Release notes record providers still being added (the 2026-11 entries include Microsoft 365 Copilot and Azure PTU capacity). No guardrail judgement is built in; it comes from external rails you attach.

Where it runs

Self-hosting first: the simple-proxy page records pip install then litellm --config config.yaml, default port 4000. The deploy page records the ghcr.io/berriai/litellm image, a docker run example, Helm / Terraform, a Postgres dependency and the /health/readiness check. The site also records a hosted cloud usage path. Production requiring a database is stated plainly on the simple-proxy page.

Local files

It reads your own config.yaml (model list, key references, guardrail settings); keys and routing definitions stay in your environment, and spend and logs go into the Postgres you manage. It does not read your application source tree - the file surface is configuration plus where you persist data.

Tasks after shutdown

It is a long-running gateway process: queueing, retries and routing happen service-side, and surviving a shutdown depends on how you deploy it (Helm or a VM). The batch and asynchronous job surface (videos / batches) has only appeared in release notes; dedicated pages were official docs do not itemize every sub-detail and are recorded as unknown.

Tools & extensions

The MCP page records it acting as an 'MCP Gateway' offering 'governed access to tools': servers configured through config.yaml or the UI, transports HTTP / SSE / stdio, authentication via OAuth, API keys and AWS SigV4, with access scoped by key, team and organization. A2A, Auto Router, logging and OpenTelemetry pages sit in the documentation navigation.

Context & memory

Context passes through from the caller; the gateway itself keeps no memory and does no compression. Virtual keys, budgets and teams are access-layer boundaries, not context-layer ones, and the effective window is whatever the routed model gives you.

Permissions & limits

Access control is its core: the virtual-keys page records keys minted through /key/generate, model, budget, rate-limit and team scoping, a master key for administration, and scheduled rotation as an Enterprise capability. The guardrails page records that most integrations run in the open-source build while dynamic parameters and per-key rail control need Enterprise. Data flow follows whichever providers you attach. SSO and audit logs sit in the Enterprise framing (simple-proxy page). Compliance certifications and third-party audits were not found on official pages and are recorded as unknown.

Best for

Fits: teams collapsing many providers into one OpenAI-compatible entry point, governing spend and access per key or team, and insisting on self-hosting. Not a fit: anyone wanting only a thin client SDK, nor anyone for whom a vendor-backed hosted guardrail with compliance attestations is a requirement - rails here are external services you plug in, not a vendor guarantee.

Licence and terms of use

MIT (on the PyPI project page, direct-fetched 2026-11-06). The docs record that some operational and governance capabilities belong to the Enterprise edition; the item-by-item boundary is not duplicated here —see the official enterprise pages.

Test notes

This site has not completed measured runs; nothing here covers routing success rates, latency, guardrail block rates or accounting error.

Suggested measurements (three):

  • Whether per-key spend accounting stays accurate for failed requests, batches and Bedrock inference profiles
  • The real visibility of one MCP tool across key / team / organization layers
  • Latency and blocking behaviour of pre_call versus post_call rails

Capability boundaries

What it governs is on record: model access, budgets and rate limits, team membership, which MCP tools a principal can see, and where external rails attach. What it does not claim: any training-use promise about content safety, or published numbers for how well anything blocks. Per-key rail control and dynamic parameters sit in the Enterprise framing, so the open-source / Enterprise split has to be checked line by line against the official pages.
