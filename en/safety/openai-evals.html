OpenAI Evals is a run-it-on-your-machine evaluation framework plus a public eval registry: evals are YAML, run in batch with oaieval / oaievalset, and land as local JSONL logs you can inspect. It is also the open-source code whose README now points to hosted Dashboard Evals; this entry covers the open framework only.

When to use it, when not to

Fit: putting public benchmarks and your own YAML evals into local scripts or CI, reading log files rather than opening a console, and implementing CompletionFn for your own system. Not fit: wanting only a hosted UI and hosted data plane (that is Dashboard), depending on non-OpenAI models without writing an adapter, or needing runtime boundaries such as sandboxes and tool approval.

Model & openness

Your own model access is required: the README states that running evals needs an OPENAI_API_KEY and warns about API costs. docs/run-evals.md: by default any model on the OpenAI API is supported, any implementation of the CompletionFn protocol can be run by oaieval, and ready completion functions live in evals/registry/completion_fns. First-class support for other hosted providers: not stated officially.

Where it runs

A local Python process; the README states "Minimum Required Version: Python 3.9". pip install evals to run evals, clone + pip install -e . to author them. The entry points are the terminal commands oaieval (single eval) and oaievalset (eval set), so it scripts into CI. The README's first line points hosted usage to the OpenAI Dashboard Evals docs; that cloud line was not captured in this pass.

Local files

Eval definitions are YAML in the repo (evals/registry/evals, evals/registry/eval_sets) with implementations under evals/elsuite; dataset files come through Git-LFS into evals/registry/data. Logs default to local JSONL in tmp/evallogs, overridable with --record_path. Per the FAQ, a template-based or model-graded eval needs JSON data plus YAML and no evaluation code.

Tasks after shutdown

A local long run, not a hosted queue. The official docs state oaievalset records finished evals in /tmp/oaievalset/{model}.{eval_set}.progress.txt, so a rerun picks up where it stopped; a single eval cannot be resumed mid-way and must restart. Concurrency is EVALS_THREADS / EVALS_THREAD_TIMEOUT (default 10 threads, 40-second timeout). What happens after the machine shuts down: not stated officially.

Tools & extensions

Extension points are the CompletionFn protocol, eval templates and model-graded YAML; the README routes prompt chains and tool-using agents to the Completion Function Protocol. Contribution is restricted: the README says evals with custom code are not accepted at present, while model-graded YAML files still are. MCP support, guardrails or interception mechanisms: not stated officially.

Context & memory

There is no cross-session memory layer: one run is one round, and the artifacts are the local JSONL log plus the end-of-run report. Multi-turn or long-text workloads go through the eval templates in the repo (the FAQ shows the same dataset scored under different templates). Window truncation rules and default sample limits: no official text captured in this pass.

Permissions & limits

The code is MIT; you run with your own API key, and the README describes private evals for testing your common LLM patterns without exposing the data publicly. The contribution terms need reading literally: contributed eval logic and data fall under the same MIT license, and "OpenAI reserves the right to use this data in future service improvements", with contributions subject to the platform Usage Policies. Server-side retention and training use: not stated officially.

Best for

Fits: running public benchmarks plus your own YAML evals in batch on your machine or in CI, reading logs as files rather than a console, and implementing CompletionFn for your own systems. Not a fit: wanting only a hosted console and hosted data plane (that is the Dashboard line), depending heavily on non-OpenAI models without writing an adapter, or needing sandboxing and tool approval as runtime boundaries.

First run

  1. First decide which line you want: the open-source framework described here, or hosted Evals in the Dashboard (the README's first line points to the latter).
  2. Set OPENAI_API_KEY (required by the README to run evals) and note the official warning that API use is billed.
  3. To run existing evals only: pip install evals; registry data lives in Git-LFS, fetched with the git lfs fetch / git lfs pull steps in the README.
  4. In the terminal run oaieval <model or completion function> <eval name>; eval names come from the YAML under evals/registry/evals, batches via oaievalset.
  5. Read the local JSONL logs under tmp/evallogs before considering Snowflake logging.
  6. To attach your own system, implement a CompletionFn - but do not submit custom-code evals as contributions, which the README says are not accepted.
