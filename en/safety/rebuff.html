Protect AI's open-source self-hardening prompt-injection detector: heuristics, a dedicated LLM judge, a historical attack-vector library and canary-leak rechecks stacked together; one leak stores that embedding for the next detection. It is an SDK embedded in your app and a self-hostable service, not a gateway that runs your model.

When to use it, when not to

Fit: teams adding an injection alert to their own product input and doing leak self-checks along the way, and research reproductions that accumulate attack samples into a vector library. Not fit: production pipelines needing maintenance promises and compliance terms (the repo is archived), or fully offline deployment; the official roadmap's Local-only mode is still unchecked, and README SDK setup already needs OpenAI and Pinecone credentials.

8 questions, one table

8 questions, each comparable item by item with its peers.

Model & openness

One of the four layers the README declares is literally "use a dedicated LLM to analyse incoming prompts", so the model is an explicit configuration item: RebuffSdk(openai_apikey, pinecone_apikey, pinecone_index, openai_model), where openai_model is optional and defaults to gpt-3.5-turbo. On the vector side the official text gives Pinecone, with Chroma allowed in the self-hosting section. LLM providers other than OpenAI are not stated officially.

Where it runs

Both paths sit on your side: the pip install rebuff SDK runs inside your application process, and the self-hosted Playground/API server is a Node app — the README has you work in server/, run npm install then npm run dev, and it comes up at http://localhost:3000, after you stand up the SQL and vector databases via Supabase / Pinecone. No official text was reachable today for the hosted playground domain.

Local files

The object of processing in the official text is always prompt text and completion text; no ability to read workspace files, directories or attachments is declared. What the self-hosted form needs is database and vector-store connectivity rather than access to your repository. File-level capability is not stated officially.

Tasks after shutdown

The SDK form lives and dies with the host application; the self-hosted server form is a resident service backed by Supabase and a vector database. Task queues, scheduled re-checks and continuation after shutdown are not stated officially.

Tools & extensions

The four declared layers are Heuristics, LLM-based detection, VectorDB and Canary tokens; the SDK surface is three entry points — detect_injection, add_canary_word, is_canaryword_leaked. The official roadmap checks off the JavaScript/TypeScript SDK and leaves "Python SDK parity" unchecked. MCP or other extension points are not stated officially.

Context & memory

Its "memory" is the vector store: the official description is embedding previous attacks in the VectorDB to recognise similar ones, and when a canary leaks, writing the embedding of that input prompt back — the roadmap calls this attack signature learning. Store capacity, retention period and cleanup policy are not stated officially.

Permissions & limits

Licensed Apache-2.0 (see the license field). Data flow is determined by configuration: the official example requires an OpenAI key and a Pinecone key, meaning the text under inspection is handed to the external services you configure; no privacy or data-processing terms were found in the official text reached today. The self-hosting environment list also includes MASTER_API_KEY, MASTER_CREDIT_AMOUNT and BILLING_RATE_INT_10K, i.e. the server ships with a credit and per-request deduction concept (the README states an integer conversion rule for it). Compliance certifications and training use are not stated officially.

Best for

Fits research and engineering experiments that add an injection alert plus canary-leak self-check inside your own app and accumulate attack samples in a vector store. Does not fit production pipelines that need a maintenance commitment or explicit data-processing terms — the repository is archived — nor fully offline deployments: "Local-only mode" is still an unchecked roadmap item and the documented SDK needs OpenAI and Pinecone credentials.

Licence and terms of use

Apache-2.0 (the official LICENSE file is the full Apache License Version 2.0 text; the PyPI classifier says the same). Open source, but the documented usage requires bring-your-own credentials: the SDK is initialised with an OpenAI key and a Pinecone key plus index name, and the self-hosted server additionally needs Supabase — the library is free, the services and keys are on you.

Capability surface as declared officially

The README (fetched 2026-11-06) describes the four layers as: Heuristics filter suspicious input before it reaches the LLM; LLM-based detection uses a dedicated LLM to analyse prompts and identify possible attacks; VectorDB stores embeddings of previous attacks to block similar ones; Canary tokens are added to prompts to detect leakage, which lets the framework store the embedding of the incoming prompt and prevent future attacks.

The Disclaimer, original wording:

Rebuff is still a prototype and cannot provide 100% protection against prompt injection attacks!

This sentence is the first thing to read when choosing: it is the vendor's own qualitative statement about its capability boundary. This site quotes no detection or bypass figures.

Deployment prerequisites (official self-hosting terms)

The self-hosting section requires Supabase, OpenAI and a vector database (Pinecone, or Chroma per the docs) set up first; then a .env.local in server/ carrying OPENAI_API_KEY, MASTER_API_KEY, BILLING_RATE_INT_10K, MASTER_CREDIT_AMOUNT, the Supabase anon key and URL, the Pinecone key / environment / index name, SUPABASE_SERVICE_KEY and REBUFF_API; afterwards npm install and npm run dev, which serves at http://localhost:3000. The README explains BILLING_RATE_INT_10K as the credit amount deducted per request and states an integer conversion rule for it; this site does not carry the figure.
