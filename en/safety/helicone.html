Helicone is an open-source AI gateway and LLM observability platform: officially a Rust router with one OpenAI-compatible interface for 100+ models, plus caching, rate limits, fallback and tracing; it can be cloud-hosted or deployed as a gateway binary or full stack on your own infrastructure. It solves centralised call management and observability, not model-quality judgement.

When to use it, when not to

Fit: teams connecting more than one model, wanting logs, usage and fallback in one place and accepting a cloud form; or teams that must keep data in-house and will maintain ClickHouse, Minio and Supabase for self-hosting. Not fit: treating the gateway as model capability itself, or teams unwilling to own self-hosting dependencies.

Model & openness

The official AI Gateway docs describe an open-source Rust router exposing one OpenAI-compatible interface to 100+ language models, with provider keys centralised in the gateway; both cloud-hosted and self-hosted forms are listed. It is not a model provider.

Where it runs

The cloud-hosted gateway runs on the platform, with an official 99.9% SLA and global edge network. The self-hosted gateway ships as one lightweight Rust binary for Docker, Kubernetes, bare-metal or sidecar use; the full observability stack can run via Docker Compose or Helm.

Local files

In cloud form, requests and logs live on Helicone's side. In self-hosted form, Web, Jawn, Supabase, ClickHouse and Minio run on your own infrastructure, so logs and object storage stay under your control. The gateway itself does not run local models.

Tasks after shutdown

The gateway sits in the request path and forwards or falls back per call. The official material does not list a durable task queue as a product surface; background jobs are left to the caller's orchestration. Log writes are part of the cloud or self-hosted stack.

Tools & extensions

The docs list integrations including the OpenAI SDK, Anthropic, LangChain, Gemini and Vercel AI SDK. The gateway provides OpenAI-compatible syntax, caching, rate limits, fallbacks and built-in tracing. An MCP server is not part of the AI Gateway capability surface as documented.

Context & memory

The gateway keeps no conversation memory: context is the request body, and length belongs to the upstream model. The observability layer stores traces and sessions for debugging, but the docs do not feed historical traces back as model context.

Permissions & limits

Cloud use centralises keys and spend controls in the account; self-hosting leaves key and data permissions to your deployment. Team tiers, audit logs and export details are not itemised in the official docs.

Best for

Fits: teams standardising several model providers with fallback, caching, rate limits and observability, or teams that need data inside their own infrastructure and will run the self-hosted gateway. Does not fit: those expecting the gateway to supply model capability, or those unwilling to operate ClickHouse, Minio and Supabase dependencies.

Licence and terms of use

Apache-2.0 — the official open-source page read on 2026-11-21 states "licensed under the Apache License 2.0"; the GitHub repository README also marks Apache-2.0 on the same date.

When something fails

Account and permissions · Rate limits and retries · File-reading issues

Top misconception

  • Treating a unified entry point as unified capability — model parameters and behaviour still differ behind the gateway
  • Using the observability panel without checking what sensitive content goes into request bodies
  • Treating platform-managed keys as a reason to skip key rotation and least privilege
  • Choosing self-hosting for “one binary” while ignoring the ClickHouse / Minio / Supabase stack you must operate

第一次怎么用

  1. 先过一遍你要送出去的数据：客户姓名、订单号、密钥、源码片段。任一项不能离开自己环境，就选自托管而不是云端。
  2. 接入时把「谁在调用哪个模型、失败会怎样」写清楚。网关只保证集中，不保证行为一致。回退条件与超时阈值要显式设定并演练一次。
  3. 密钥仍在你的账上：平台代管不等于免轮换，按你的离职与泄露预案设定轮换周期。
  4. 选自托管时先按官方 Docker Compose / Helm 文档核对 ClickHouse、Minio、Supabase 的备份与升级路径，再上线。
  5. 上线后核对日志范围：确认记录里没混进不该长期留存的内容，再决定保留多久、怎么导出。
