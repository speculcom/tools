It is a verifiable statement of where a piece of content came from and what changed; the site describes an encrypted manifest that lets audiences prove authenticity in AI-generated content. The keywords are manifest and verification, not blocking.

When to use it, when not to

Fit: publishers that need to issue credentials, review and forensics teams separating a missing credential from a broken one, and teams writing credentials into asset management. Not fit: using it as a content filter or a true/false verdict, or expecting it to verify authenticity when no issuer wrote anything. This entry does not rank it against content-filtering products: they answer different questions.

Model & openness

It neither connects nor guards models: the manifest is written by whichever tool produced the content, declaring the application, device or AI service used. Adobe's AEM documentation page records that the asset panel lists the applications, devices and AI tools used to produce an asset (Adobe Firefly is the example given) together with later changes. Which models end up disclosed depends on what each issuer writes; this site does not infer it.

Where it runs

The browser verifier is the main entry point: contentcredentials.org redirects to verify.contentauthenticity.org, direct-fetched 200 on 2026-11-06, though that page serves a script shell with no static prose. Locally there are SDKs and the C2PA Tool listed on the CAI open-source docs hub; integrated products such as AEM Assets render the manifest inside their own UI.

Local files

The web verifier asks you to upload or drop a file; the local libraries and CLI read and write files on your own machine and parse the manifest (the Reader / validate flow is on the docs hub). How uploaded files are retained on the verifier side is not stated in anything fetched and is recorded as unknown.

Tasks after shutdown

There is no background-task surface: verification is on demand, and the libraries and CLI are single-shot calls. No queue, resume or subscription-style batch verification is declared officially; batching means scripting the CLI yourself.

Tools & extensions

The extension surface is a specification plus its implementation family: the docs hub lists c2pa-rs / Python / C++ / JS / Node / Mobile libraries, the C2PA Tool, and conformance and durable-credentials entries. The site carries the 500+ adopters narrative. No MCP or other plug-in protocol statement was found; recorded as unknown.

Context & memory

There is no conversational context: one verification reads one file's credential chain. The AEM page records that credentials stay intact when an asset is downloaded, published or shared, and that the panel shows the issuer name plus issuance date and time. Cross-asset indexing or memory is outside the product.

Permissions & limits

The trust root is cryptographic: the docs hub records signature verification with the public key, checking of referenced assertions, reliance on PKI / X.509 chains and C2PA trust lists, and identity assertions bound separately from signature validation. Compliance certifications, the data-processor list and retention terms were not found on official pages and are recorded as unknown. Trademarks and terms belong to Adobe / the CAI and to C2PA.

Best for

Fits: publishers and platforms turning provenance and edit history into verifiable claims, and audit workflows that must separate 'no credentials present' from 'credentials tampered with'. Not a fit: anyone wanting harmful-content blocking (that is the content-filtering line) or expecting verification with no issuer involved at all. This site does not rank it against filtering products - the two lines answer different questions.

Test notes

This site has not completed measured runs; nothing here covers credential coverage, signature-success rates or detection rates.

Suggested measurements (three):

  • Verifier conclusions across three states of the same image: no credentials, intact credentials, damaged credentials
  • How trust-list status differs between issuers' certificates
  • Whether the local CLI and the web verifier agree on the same file

Capability boundaries

What verification can do: check the signature, compare content bindings, inspect referenced assertions, judge issuer trust against a trust list, and explicitly separate 'missing' from 'invalid'. What it cannot do, in this site's view: guarantee that content is not misleading - an honest edit history can still accompany a deceptive narrative; the official pages scope verification to signatures, bindings and assertions. One often-missed detail: identity assertions are bound separately from signature validation, so 'who signed it' and 'who they claim to be' are two different findings (docs hub on record).
