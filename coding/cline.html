适合与不适合When to use it, when not to

需要同一工具覆盖编辑器、终端、桌面三种工作形态的用户。 需要模型自选（不绑定单一厂商）的人。 需要 CI/CD 集成（CLI headless）的人。 需要「改动可审查、可回滚」保证的人。每次编辑以 diff 呈现，checkpoint 可整体撤销。 需要周期性自动化的人（cron 调度，重启后仍生效）。

不适合要求「审批默认最严」的场景—— CLI / headless 默认 --auto-approve true 全程放行， 要收紧得显式传 --auto-approve false（或用 PreToolUse hook 拦命令）。

Users who need one tool across editor, terminal and desktop. People who need model choice (not locked to one vendor). People who need CI/CD integration (CLI headless). People who need reviewable, revertible changes — every edit appears as a diff plus a checkpoint to undo wholesale. People who need periodic automation (cron scheduling that survives restarts).

Not a fit for requiring approval to behave identically across all forms — the extension form confirms human-in-the-loop, but behaviour under CLI headless was not verified.

本地文件Local files

两个特点：跨项目协调改动，以及可回滚的检查点。

README 的「Edits Code Across Your Project」说的是：读取项目结构、理解文件间关系， 然后在代码库里做协调改动。

改动过程中它会盯着 linter 与编译器的报错，主动修掉缺失的 import、 类型不匹配、语法错误 —— 那些「用户看不到就会出问题」的东西。

  • 在 VS Code 与 JetBrains 里，每次编辑都以 diff 形式呈现，可审查、可修改、可回滚
  • 所有改动都有 checkpoint 记录，可以整体撤销
  • 官方 Checkpoints 页说明它用 shadow Git repository 跟踪改动， 与你的主 Git 工作流互不干扰，每次工具调用后建一个检查点

读取范围分两档：默认「Read project files」（工作区内）； 「Read all files」（工作区外）需要先打开基础开关才生效。 项目级忽略用 .clineignore 控制（官方还给了用 hook 强制的做法）。

⚠ 它没有「全量语义索引」这个环节。 内置 search 工具是 「Ripgrep-powered codebase search」；官方对大仓库的建议是 「用搜索代替大量读文件」，并把任务拆小。 （已查 Tools 页与 Context Window Guide。）

官方对大仓库的建议：Use search instead of reading many files

Two features: coordinated changes across the project, and rollbackable checkpoints.

The README's "Edits Code Across Your Project" means: read the project structure, understand relationships between files, then make coordinated changes across the codebase.

While editing it watches linter and compiler errors, proactively fixing missing imports, type mismatches and syntax errors — the things that "go wrong without the user ever seeing them".

  • In VS Code and JetBrains, every edit is presented as a diff — reviewable, modifiable, rollbackable
  • all changes carry checkpoint records and can be undone wholesale
  • the official Checkpoints page explains it tracks changes with a shadow Git repository, not interfering with your main Git workflow, creating a checkpoint after each tool call

Read scope has two tiers: by default "Read project files" (inside the workspace); "Read all files" (outside the workspace) only takes effect after enabling a base toggle first. Project-level ignores are controlled by .clineignore (the official also shows a hook-enforced approach).

⚠ It has no "full semantic index" stage. The built-in search tool is a "Ripgrep-powered codebase search"; the official advice for large repos is "use search instead of reading many files", and to break tasks down smaller. (checked the Tools page and the Context Window Guide.)

The official large-repo advice: Use search instead of reading many files

关机后的任务Tasks after shutdown

长进程与定时任务都支持。

命令在终端直接执行，输出实时可见 —— 装包、跑构建、跑测试、部署、管数据库。 对 dev server 这类长进程，Cline 会在后台继续工作并对新输出做出反应： 编译错误、测试失败、服务崩溃都在发生时被捕捉。

Desktop App 形态另有定时任务（schedule routines）：

  • 可用 cron 调度做周期性自动化
  • 例子：每日 PR 摘要、每周依赖检查、代码库健康报告
  • schedule 在重启后仍保留，且独立于任何终端会话运行

CLI 的 headless 模式则面向 CI/CD。

Long-running processes and scheduled tasks are both supported.

Commands execute directly in the terminal with output visible in real time — installing packages, running builds, running tests, deploying, managing databases. For long-running processes like dev servers, Cline keeps working in the background and reacts to new output: compile errors, test failures and service crashes are caught as they happen.

The Desktop App form additionally has scheduled tasks (schedule routines):

  • cron scheduling for periodic automation
  • examples: daily PR summaries, weekly dependency checks, codebase health reports
  • schedules persist across restarts and run independently of any terminal session

权限与限制Permissions & limits

两级审批设计，是本站里最细的一套。

第一级是 Plan / Act 双模式。 Plan 模式下 Cline 探索代码库、提出澄清问题、 列出策略；对齐之后切到 Act 模式执行计划。

第二级是「每次文件编辑与终端命令都需要批准」，也可以切到 auto-approve 让它自主运行。VS Code 扩展形态的表述是「human-in-the-loop approval」。

⚠ 但 CLI / headless 的默认行为是相反的。这点必须知道 （已核官方 CLI Overview 与 CLI Reference）：

  • --auto-approve <boolean> 默认 true —— 即默认放行工具
  • --auto-approve false 时，每个工具调用前都需批准
  • --yolo 跳过全部审批
  • ACP（编辑器集成）模式默认相反，为 false

另：CLI 没有 shell 命令的允许/拒绝清单。官方建议用 PreToolUse hook 拦截。

CLI 提示语原文：Default to start in act mode with auto-approve enabled VS Code 扩展表述：use tools with human-in-the-loop approval

A two-level approval design — the finest on this site.

Level one is the Plan / Act dual mode. In Plan mode Cline explores the codebase, asks clarifying questions, and lays out a strategy; once aligned, switch to Act mode to execute the plan.

Level two is "every file edit and terminal command needs approval", switchable to auto-approve for autonomous running. The VS Code extension form's wording is "human-in-the-loop approval".

⚠ But the CLI / headless default is the opposite. This must be known (verified against the official CLI Overview and CLI Reference):

  • --auto-approve <boolean> defaults to true — i.e. tools are allowed by default
  • with --auto-approve false, every tool call needs approval first
  • --yolo skips all approvals
  • ACP (editor-integration) mode defaults to the opposite, false

Also: the CLI has no shell-command allow/deny list. The official suggests intercepting with a PreToolUse hook.

CLI prompt original wording: Default to start in act mode with auto-approve enabled VS Code extension wording: use tools with human-in-the-loop approval
