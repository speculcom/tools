Copilot 在终端里的编码 agent 形态，与 GitHub 订阅同源。

它能在终端里走完一条链。

"读仓库 / 改代码 / 跑测试 / 开 PR / 管 Issue" 都在终端里完成。

官方 README 说它

「Powered by the same agentic harness as GitHub's Copilot coding agent」

它与既有 GitHub Copilot（IDE 形态）是同一产品的两种装法。

本条目只写 CLI 的差异点：

  • 程序化入口
  • 终端级审批
  • 按提示词扣 premium requests 的额度扣减方式

GitHub Copilot CLI is the Copilot coding agent that runs in your terminal, carried by the same GitHub subscription as the IDE form factor. The official README says it is "Powered by the same agentic harness as GitHub's Copilot coding agent." Three things differ from the IDE form. It has a programmatic entry point (copilot -p / --prompt) that can go into scripts and CI. Approval is terminal-level: three choices on first use of a writing or executing tool, plus --allow-all-tools / --allow-tool / --deny-tool for unattended runs, and some official docs say denial wins. Billing is per prompt too: "Each time you submit a prompt to Copilot CLI, your monthly quota of Copilot premium requests is reduced by one."

适合与不适合When to use it, when not to

适合三类人：

  • 已在 GitHub 生态、想在终端把「读仓库 → 改代码 → 跑测试 → 开 PR / 管 Issue」一条链走完的人
  • 需要脚本化 / headless 的人（copilot -p 配审批选项，可进 CI）
  • 需要 MCP / 插件 / 自定义 agent 生态的人

不适合不想付 Copilot 订阅的人：CLI 随订阅、不能单独买。

也不适合想「全自动又零风险」的人：自动批准必须与隔离环境配套。官方对此有明确风险提示。

People already in the GitHub ecosystem who want to walk the whole chain from reading a repo to opening a pull request in the terminal. The official use case gives tasks such as "create a pull request on GitHub.com".

People who need scripted or headless use: copilot -p with approval flags is CI-friendly. Anyone who wants the MCP / plugin / custom-agent surface.

Not a fit for people who don't want a Copilot subscription, because the CLI ships with the subscription and cannot be bought on its own. Nor for anyone who wants "fully autonomous and zero risk": auto-approval has to be paired with an isolated environment, and the official docs warn about that plainly.

本地文件Local files

以「信任目录」为界。 启动会话时，官方要求你确认信任「confirm that you trust the files in, and below, the directory from which you launched the CLI」。

这个受托目录控制 "where Copilot CLI can read, modify, and execute files"。

关键限定：官方明写

官方原文："Scoping of permissions is heuristic and GitHub does not guarantee that all files outside trusted directories will be protected"

别把信任目录当成强沙箱。

想要更硬的边界，可开本地沙箱：官方原文："run /sandbox enable inside a session"， 用以限制文件系统、网络与系统能力。或者用 copilot --cloud 把整个会话放进云隔离环境。

Bounded by "trusted directories". When starting a session, the official docs require you to "confirm that you trust the files in, and below, the directory from which you launched the CLI".

This trusted directory controls "where Copilot CLI can read, modify, and execute files".

Key caveat: the official docs state plainly

Official wording: "Scoping of permissions is heuristic and GitHub does not guarantee that all files outside trusted directories will be protected"

Do not treat trusted directories as a hard sandbox.

For a harder boundary, enable the local sandbox: Official wording: "run /sandbox enable inside a session", which restricts filesystem, network and system capabilities. Or use copilot --cloud to put the whole session in a cloud-isolated environment.

权限与限制Permissions & limits

审批是本条目最值得记的一维，颗粒度比 IDE 形态更细。

首次使用可写 / 可执行工具时，官方给三个选项：

  • 1. Yes
  • 2. Yes, and approve TOOL for the rest of the running session
  • 3. No, and tell Copilot what to do differently (Esc)

官方原文：

官方原文（审批提示的三个选项）："1. Yes" / "2. Yes, and approve TOOL for the rest of the running session" / "3. No, and tell Copilot what to do differently (Esc)"

选项 2 的含义是本会话内该类命令全部放行。 官方举例：批准 rm ./this-file.txt 后，本会话可跑任意 rm。

程序化 / 无人值守模式有三个开关：

  • --allow-all-tools —— 任何工具都不问
  • --allow-tool —— 放行指定工具
  • --deny-tool —— 禁止指定工具，优先级最高

取值支持「shell(COMMAND)、write、MCP_SERVER_NAME」，且 --deny-tool 优先于 --allow-tool / --allow-all-tools。

官方对自动批准的警告值得原样记住：

官方原文："Copilot has the same access as you do to files on your computer, and can run any shell commands that you can run, without getting your prior approval"

官方并建议在 VM / 容器 / 无网环境里用自动批准，以限制影响面。

内容排除方面，Business / Enterprise 用户的 CLI：

官方原文："respects content exclusion policies configured at the enterprise, organization, and repository levels"

企业与组织策略可整体禁用 CLI。

Approval is the axis most worth remembering in this entry, with finer granularity than the IDE form.

On first use of write / executable tools, the official docs give three options:

  • 1. Yes
  • 2. Yes, and approve TOOL for the rest of the running session
  • 3. No, and tell Copilot what to do differently (Esc)

Official wording:

Official wording (the three approval-prompt options): "1. Yes" / "2. Yes, and approve TOOL for the rest of the running session" / "3. No, and tell Copilot what to do differently (Esc)"

Option 2 means all commands of that tool class are allowed for this session. Official example: after approving rm ./this-file.txt, any rm can run in the session.

Programmatic / unattended mode has three switches:

  • --allow-all-tools — never ask for any tool
  • --allow-tool — allow specified tools
  • --deny-tool — forbid specified tools, highest priority

Values support "shell(COMMAND), write, MCP_SERVER_NAME", and --deny-tool takes precedence over --allow-tool / --allow-all-tools.

The official warning about auto-approval is worth remembering verbatim:

Official wording: "Copilot has the same access as you do to files on your computer, and can run any shell commands that you can run, without getting your prior approval"

The official docs also recommend using auto-approval inside VMs / containers / offline environments to limit blast radius.

For content exclusion, the CLI for Business / Enterprise users:

Official wording: "respects content exclusion policies configured at the enterprise, organization, and repository levels"

Enterprise and organization policies can disable the CLI entirely.

程序化与安装Programmatic use and installation

安装以 npm 包为主。官方前置条件是 Node.js 22 or later：

`` npm install -g @github/copilot ``

另有 WinGet（winget install GitHub.Copilot）、Homebrew（brew install --cask copilot-cli）与安装脚本。

认证除 /login 外，支持细粒度 PAT + 「Copilot Requests」权限，放进 GH_TOKEN 或 GITHUB_TOKEN。

官方示例：copilot -p "Show me this week's commits and summarize them" --allow-tool='shell(git)'

加 -s 只输出回答、省去用量信息。

Installation is primarily via the npm package. The official prerequisite is Node.js 22 or later:

`` npm install -g @github/copilot ``

There are also WinGet (winget install GitHub.Copilot), Homebrew (brew install --cask copilot-cli) and an install script.
