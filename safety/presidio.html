Presidio 是「自己部署的那一层脱敏 SDK」：文档首页把它写成面向 text 与 images 的快速识别与匿名化模块， 三面 API 是 AnalyzerEngine、AnonymizerEngine、Image Redactor，变换算子官方在册 replace / redact / hash / mask / encrypt / keep / custom。它和本大类托管那几份的区别只有一条：文本要不要出你的边界——Presidio 官方口径是在你自己的 部署里完成、支持离线；也因此它的输出没有任何「拦住了多少」的比例含义，官方 analyzer 页甚至专门写着 「Scores are not probabilities」。

适合与不适合When to use it, when not to

适合：把个人数据识别与变换插进自己的管线（RAG 入库前、日志落盘前、发给云端模型前）、需要算子级组合与自定义 recognizer、要求文本不出网络边界、需要离线跑完整链路。不适合：要托管控制台与合规交付物；要 text/image 之外的模态 （官方在册面止于这两类）；把 score 阈值当合规证明的团队。

上下文与记忆Context & memory

这里的「上下文」是字面机制：recognizer 用上下文词对候选实体加权，因此同一段文本里邻近词会改变结果；文档首页把项目 表述为面向 text and images 的「fast identification and anonymization modules」。它是无状态的一次处理，不存在跨会话记忆， 批量场景的上下文窗口管理属于你自己的调用方。

Here "context" is a literal mechanism: recognizers weight candidate entities with context words, so neighbouring words in the same text change the result; the docs home page describes the project as "fast identification and anonymization modules" for text and images. It is a stateless one-pass handler with no cross-session memory — batch context-window management belongs to your calling code.

能力边界

  • 模态面：官方在册只有文本与图像两条（image redaction 是独立组件）。
  • 判定面：输出是候选实体与 score，官方明确 score 不是概率；把它读成任何百分比都是越界。
  • 变换面：算子是动作（遮、替、哈希、加密、保留、自定义），不承诺「脱敏后不可逆推」这类结论，那是你选算子与密钥管理的责任。
  • 合规面：它不产出法律结论；GDPR/个保法意义上的匿名化是否成立，取决于你的整体处理方案，而不是这一个 SDK。

部署建议

  1. 先定边界：如果「文本不出内网」是硬约束，本档案这条线是唯一可选项；否则才需要比较托管方案。
  2. 装两个包（analyzer 与 anonymizer），先用官方 tutorial 跑一遍 replace 与 mask，再决定要不要自定义 recognizer。
  3. 需要服务化时用官方 Docker REST 路径，但把镜像标签与版本钉住——本批次未取到标签对应关系。
  4. 记录配置而非结果分数：把 recognizer 集、上下文词与算子参数进版本控制；把 score 阈值写进文档时要同时写明官方那句 「Scores are not probabilities」。
